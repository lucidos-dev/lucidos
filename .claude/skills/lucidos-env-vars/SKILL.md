# Lucidos Environment Variables

Full reference. The `DATABASE_URL` password-in-argv rule also lives in the root
`CLAUDE.md` (it is a safety rule, so it must be resident even when this skill
is not loaded) — the two must stay in sync.

**Where a packaged macOS launch gets these from.** A GUI launch inherits
launchd's environment, not the user's: `~/.zprofile` and `~/.zshrc` never ran, so
anything exported there is absent and `PATH` is the bare
`/usr/bin:/bin:/usr/sbin:/sbin`. So the packaged **service** role
(`Lucidos --service`, the launchd job at the root of the gateway → engine →
coding-agent chain) hydrates a login shell first, in
`crates/lucidos-app/src/shell_env.rs`. It runs `$SHELL -ilc` (falling back to
`/bin/zsh`) with a hard 5s bound, and applies an **allowlist**, not the shell's
whole environment: `PATH`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`,
`LUCIDOS_OPENROUTER_API_KEY`, `LUCIDOS_XAI_API_KEY`, `LUCIDOS_LOCAL_BASE_URL`,
`LUCIDOS_LOCAL_API_KEY`,
`VERTEX_PROJECT_ID`, `VERTEX_REGION`, `GOOGLE_APPLICATION_CREDENTIALS`,
`CLOUDSDK_CONFIG`, `CODEX_HOME`, `CLAUDE_CONFIG_DIR`. Three properties matter for
anything you reason about below: a variable **already set in the process always
wins** (`PATH` excepted, which is merged shell-first over the inherited one,
since launchd always sets one); a run started **from a terminal** is detected by
`SHLVL` and skipped entirely, so dev behaviour is unchanged; and everything
**not** on that list (`LUCIDOS_MODEL`, `LUCIDOS_BIND_*`, `LUCIDOS_TLS_*`,
`DATABASE_URL`, the proxy variables, …) is deliberately excluded, so a shell
profile can never repoint a packaged install's model, topology or storage. Add a
variable to that allowlist only when its absence makes a provider or a tool
unreachable. The headless tarball install does not need any of this: `install.sh`
runs from a terminal and bakes the provider variables it was given straight into
the plist/unit.

- `LUCIDOS_WORKSPACE` — workspace dir (default `./workspace`)
- `DATABASE_URL` — Postgres connection string for the engine. **Never hardcode the URL or password into a `psql`/Python invocation** — the engine sets `PGUSER`/`PGPASSWORD`/`PGHOST`/`PGPORT`/`PGDATABASE` in every spawned subprocess (CC sessions, bash + python tools, scheduled scripts), so just run `psql -c '…'` bare. Putting the URL in argv leaks the password into the persisted `Bash` tool-call payload that the steps UI renders.
- `LUCIDOS_MODEL` — LLM model (default `claude-opus-5@default`). `[1m]` = 1M context. `gpt-*` = OpenAI.
- `VERTEX_PROJECT_ID` / `VERTEX_REGION` — GCP (default region `europe-west1`). The project also resolves WITHOUT this env var, so a packaged build works from a user's existing `gcloud auth application-default login`: the engine reads the ADC file (`$GOOGLE_APPLICATION_CREDENTIALS` → `$CLOUDSDK_CONFIG`/`~/.config/gcloud/application_default_credentials.json`) and refreshes the access token itself — no `gcloud` binary — and resolves the project from the ADC `quota_project_id` or the gcloud config `[core] project` (resolution order: env → ADC/config files → `gcloud config` subprocess). Only the `authorized_user` ADC type is read in-engine; other types fall back to the `gcloud` subprocess (dev only). See `crates/lucidos-engine/src/llm/vertex/adc.rs`.
  - Region resolution order: the `vertex_region` preference, then a
    non-empty `VERTEX_REGION`, then `europe-west1`. The constant is
    `DEFAULT_VERTEX_REGION` (`crates/lucidos-engine/src/core/preferences.rs`),
    mirrored in `crates/lucidos-app/src/store/actions/preferences.ts`. So the
    Settings dropdown beats the env var. An exported value counts only if the
    engine process inherited it. Startup logs which input won, and warns when
    the preference read failed. A preference change hot-swaps into a running
    engine via `spawn_vertex_region_subscriber`.
- `OPENAI_API_KEY` — for `gpt-*` models (fallback for the `openai` provider when no `openai` credential is set). Below this the engine has a further, lowest-precedence fallback: it auto-detects a key from the Codex CLI's auth file (`${CODEX_HOME:-~/.codex}/auth.json`, `apikey` login only — a `chatgpt`/OAuth login is ignored), the parallel of Vertex reading the gcloud ADC file. Full resolution order: stored `openai` credential → `OPENAI_API_KEY` → Codex-detected key. The detected key is read fresh at provider-build time and never persisted. See `crates/lucidos-engine/src/llm/openai/codex_detect.rs`.
- `ANTHROPIC_API_KEY`: fallback for the direct `anthropic` provider (e.g. Fable 5) when no `anthropic` credential is set. Full resolution order: stored `anthropic` credential → `ANTHROPIC_API_KEY`. There is no third level. A Claude Code login (`~/.claude/.credentials.json` / keychain) is deliberately NOT auto-detected, unlike the Codex login OpenAI reads, because whether a subscription OAuth token may serve as an API provider is a separate question. An env-sourced key is always sent as `x-api-key`, never as an OAuth bearer. Resolved by `resolve_anthropic_auth` (`crates/lucidos-engine/src/llm/anthropic/mod.rs`), which also feeds the Anthropic web-search backend and the builtin `anthropic` app proxy, so all three agree on which source won.
- `LUCIDOS_OPENROUTER_API_KEY` — fallback for the `openrouter` provider (e.g. GLM 5.2 `z-ai/glm-5.2`) when no `openrouter` credential is set
- `LUCIDOS_XAI_API_KEY`: fallback for the `xai` provider (the Grok family, e.g. `grok-4.6`) when no `xai` credential is set. xAI's API is OpenAI chat-completions compatible at `https://api.x.ai/v1`. The engine serves it with the same `OpenAiProvider` as OpenRouter and local, only the base URL differs. Ids are bare here; the same models via OpenRouter carry an `x-ai/` prefix and use the OpenRouter key instead
- `LUCIDOS_OPENCODE_FREE`: turns on the keyless `opencode-free` provider, OpenCode's free tier on the Zen relay at `https://opencode.ai/zen/v1`. Truthy values are `1`, `true`, `yes`, `on`. Below the `opencode_free_enabled` preference (Settings → Models → Providers), which wins when set. There is no key and no credential: the relay serves the free models anonymously and rejects a bearer it does not recognise, so the engine sends no `Authorization` header. Off by default, because a request carries the user's prompt to a third party and several free models may train on it.
- `LUCIDOS_LOCAL_BASE_URL` / `LUCIDOS_LOCAL_API_KEY` — base URL + optional key for the `local` OpenAI-compatible provider (Ollama / LM Studio / vLLM / llama.cpp). Base URL defaults to Ollama `http://localhost:11434/v1`; also settable via the `local_base_url` preference (Settings → Providers). The local provider is built only when a base URL or key is configured.
- `LUCIDOS_EMBEDDING_MODEL` — embedding model (`bge-small-en-v1.5` or `multilingual-e5-small`, default `multilingual-e5-small`)
- `HF_HOME` / `FASTEMBED_CACHE_DIR` / `HF_ENDPOINT`: where the ~465 MB embedding model is cached, and which hub it comes from. **Neither cache variable is Lucidos's.** Both are read by `fastembed` itself, so the engine mirrors its resolution order exactly (`HF_HOME`, then `FASTEMBED_CACHE_DIR`, then a default) in `memory::model_download::cache_dir`. Drift between the two downloads the model twice, since the engine pre-fetches the files through `hf-hub` directly to get byte progress and `fastembed` then loads them. **The cache is per user or per install, never per workspace** (ADR 0061): a spawned engine INHERITS it, the packaged app sets `<app-data>/fastembed` and the headless service `<data>/fastembed`, and with neither set the engine defaults to `${XDG_CACHE_HOME:-$HOME/.cache}/lucidos/fastembed` (the path `scripts/e2e-embedder.sh` also seeds), or to `<workspace>/.lucidos/fastembed` when there is no per-user cache root at all. That default is applied by SETTING `FASTEMBED_CACHE_DIR` early in `main`, before `apply_to_process_env`, so both halves agree and a value the user stored in Settings still wins.
- `LUCIDOS_EXTRACTION_MODEL` — default model the memory extractor falls back to when no per-call override is passed and the `model_memory` preference is also empty (default `gemini-3-flash-preview`)
- `LUCIDOS_EVAL_JUDGE_PROVIDER`: which provider serves the ADR 0087 context-mode eval's judge, one of `vertex`, `anthropic`, `openai`, `openrouter`, `xai` or `local`. The judge calls its model through the engine's provider layer, so it reaches every provider the engine reaches. Unset, the engine's routing decides from the judge model id, so a `claude-` id goes to Vertex. When that provider is not configured here, and exactly one other is, the judge uses that one and prints which. One call proves the pair before the first probe, so a bad credential or a missing model fails the command, not the results file. The other `LUCIDOS_EVAL_*` variables live in `scripts/eval-context-mode.sh`'s header, and the judge itself in `crates/lucidos-eval/src/judge.rs`.
- **Frontend preview** (dev only, `engine::frontend_preview`, ADR 0055). `LUCIDOS_FRONTEND_PREVIEW_PORT` overrides the port the supervised Vite dev server listens on; unset, it is `LUCIDOS_API_PORT + 1000`, walked forward up to 9 if busy. 1000 clears the workspace port bands entirely (`scripts/lib/ports.sh` spaces API at 3000+offset and Vite at 5173+offset), so an offset would have to exceed 1000 to collide. `LUCIDOS_FRONTEND_PREVIEW_API_ORIGIN` is set BY the engine ON the spawned Vite, never by a human: it carries this engine's own loopback origin, and `vite.config.ts` builds its `server.proxy` for `/api`, `/app` and `/data` from it, so the preview page is same-origin with its own API. Unset, that proxy block does not exist and a manual `npm run dev` is unchanged. The preview inherits `LUCIDOS_TLS_CERT` / `LUCIDOS_TLS_KEY` from the engine's environment, which is how it serves https on a worktree where `.certs/` is gitignored.
- `LUCIDOS_FORCE_QUERY_CLASSIFICATION`: pins what a chat turn's query classifier answers, instead of asking the LLM. `all` uses `QueryClassification::default()`, so all three needs are true with no sub-queries, and the Flash call never happens. `none` sets all three false, and any other value, including unset, classifies exactly as it always did. Read once per process, trimmed and case-insensitive, and a typo pins nothing rather than failing the boot. **Set by the context-mode eval harness on both arms** (`crates/lucidos-eval/src/workspace.rs` § `arm_engine_env`), because a classifier disagreement voids the whole task pair. It pins `all` so the curated context mode still has a memory section to drop (see `engine/chat/process_helpers.rs` § `forced_classification`, and ADR 0087).
- `LUCIDOS_EVAL_FULL_CAPTURE`: makes the engine persist WHOLE `ContextCaptured` section bodies, instead of truncating each head and tail at 8,000 chars. Off unless set to `1`/`true`/`yes`/`on`, read once per process, and a typo lifts nothing rather than failing the boot. **Set by the context-handling benchmark on every arm it boots** (`crates/lucidos-eval/src/workspace.rs` § `arm_engine_env`), and by nothing else: it is engine-read like `LUCIDOS_FORCE_QUERY_CLASSIFICATION`, and permanent harness infrastructure rather than a diagnostic, so it carries no `docs/temporary-measures.md` row. A section's two sizes stay the true assembled lengths either way, so no size figure moves. What changes is disk, since a body-bearing capture runs near 130 kB. Three consumer paths would ship hundreds of megabytes if a normal workspace did this (`crates/lucidos-engine/src/engine/eval_capture.rs`, ADR 0110).
- `LUCIDOS_CODEX_PROTOCOL` — which protocol drives Codex sessions: `app-server` (default — persistent JSON-RPC child; permission cards, streaming, graceful interrupt) or `exec` (per-turn `codex exec` escape hatch, sandbox-only guard). See ADR 0005.
- `LUCIDOS_CACHE_PROBE`: **temporary diagnostic**, off unless set to `1`/`true`/`yes`/`on`. Logs one `[CacheProbe] req` line per Claude request and one `[CacheProbe] resp` line per response, on both the Vertex and direct-Anthropic paths. The request line hashes each prompt-cache prefix segment (tools, system, messages) on its serialized JSON bytes, and censuses every `cache_control` marker. Joined on `thread`/`turn`/`round`, the pair says whether a zero-read call sent different bytes than the call before it. Read once at first use, so it cannot be flipped under a running engine. Registered in `docs/temporary-measures.md`; see `crates/lucidos-engine/src/llm/cache_probe.rs`.
- **Git clone credentials read NO environment variable.** One helper (`crates/lucidos-engine/src/core/git_auth.rs`) authenticates every engine clone: the marketplace scan, the plugin install fetch, and both `git_clone` routes. An HTTPS secret comes from the **credential store** alone, matched on the credential's own Base URL. `GITHUB_TOKEN`, `GH_TOKEN`, `GIT_TOKEN` and the `GH_HOST` allowlist are gone: the environment store shows its values in plain text in Settings. An SSH URL still presents an ssh-agent key, and `git credential` is still consulted, since neither carries a secret through Lucidos. Setup: `system-knowhow/plugins.md` § Private and internal repos.
- **Network bind** (security: defaults to loopback-only everywhere; a malformed value fails safe to loopback, never to all). Resolution precedence, highest first: `LUCIDOS_BIND_LOOPBACK` (engine only, the behind-gateway floor; a fronted packaged engine never faces the network) → `LUCIDOS_BIND_ADDR` / `LUCIDOS_GATEWAY_BIND_ADDR` (a literal IP, e.g. a Tailscale `100.x` address) → `LUCIDOS_BIND_ALL` / `LUCIDOS_GATEWAY_BIND_ALL` (`1` = all interfaces, `[::]` dual-stack) → the machine-global `~/.lucidos/network.toml` → loopback. The engine + gateway resolvers live in `crates/lucidos-{engine,gateway}/src/net_config.rs` (duplicated per ADR 0014 §1). `~/.lucidos/network.toml` (`[gateway] bind = "loopback" | "all" | "<IP>"`, `[engine] inherit = true|false`) is the durable, UI-editable config both binaries read at boot: the gateway binds `[gateway].bind`; an engine binds the gateway's bind when `inherit` (default) or its own per-workspace `network_bind` preference when not. Env vars override the file so launch scripts / e2e are unaffected. **A specific `<IP>` bind ALSO binds `127.0.0.1` (loopback retention, `net_config::bind_socket_addrs`).** A single specific-IP socket excludes loopback, but every co-located caller reaches these processes over loopback: the gateway proxies + health-probes its engines at `127.0.0.1:<port>`, the dev scripts POST the gateway control API over `localhost`, and the engine's Apply-restart callback hits `127.0.0.1:<gateway_port>`. So binding ONLY the tailnet IP wedged the gateway↔engine hop ("Opening your workspace" forever); binding the IP **and** loopback fixes it without widening external exposure (loopback is host-only; `loopback`/`all` already cover it, so only the specific-IP case adds a socket). Edited from the picker (machine-global, `/~/api/v1/control/network-config`) and per-workspace Settings → Access → Network access (`/api/v1/network-config`). A change takes effect only after a gateway/engine **restart** (a live socket cannot be re-bound). If an engine can never be reached past a budget (`BOOT_ESCAPE_BUDGET`, gateway `server.rs`) the boot splash escapes to a manual "Back to workspaces" link rather than refreshing forever.
- `LUCIDOS_GATEWAY_ENGINE_LOOPBACK` (gateway only). Whether the engines this gateway spawns bind loopback. Default yes, packaged and dev alike, since ADR 0096: the gateway authenticates every network caller (ADR 0094), so a network-bound engine port is a way straight past pairing. Nothing in the tree sets it now, and `0` / `false` / `no` / `off` restores the old all-interfaces dev topology along with that bypass. It also decides the engine's scheme, since a loopback engine gets its TLS cert stripped and the gateway then proxies and probes over http.
- `LUCIDOS_HOOK_PORT` (set by the gateway, read by the gateway and the engine). The port the *hook socket* binds, the listener that answers webhook deliveries and nothing else (ADR 0097). Unset, it is the gateway's own port plus ten, so 5261 in dev and 5262 packaged, which keeps the two coexisting as their gateways do. The gateway resolves it once and passes it to every engine it spawns, so `scheduler/webhook_ingress` never re-derives the port it probes. `0` switches the socket off, so the probe has nothing to probe, and an unparseable value does the same with a log line: a listener on a port nobody meant to open is worse than none. Always bound to `127.0.0.1`: `tailscale funnel` proxies from this machine, so loopback is what it reaches.
- `LUCIDOS_TAILSCALE_BIN` (absolute path to the Tailscale CLI) overrides the built-in candidate probe in `lucidos_tailscale::resolve_tailscale_binary` (one copy, shared by the engine, the gateway and the desktop app). Unset (the norm) probes `/usr/local/bin/tailscale`, `/opt/homebrew/bin/tailscale`, `/usr/bin/tailscale`, then falls back to bare `tailscale` on `PATH`. The macOS `Tailscale.app` GUI executable is deliberately excluded: it is not a CLI, headless it exits **0** while printing `Tailscale.CLIError error 3`, and since the probe stops at the first EXISTING candidate it would shadow the working CLI on every Mac that has the app. Absolute-path probing exists because a **packaged app's `PATH` holds none of the places a CLI is actually installed** (Finder/launchd give it the bare `/usr/bin:/bin:/usr/sbin:/sbin`), so a bare-name spawn silently failed there. Still true with the login-shell hydration described at the top of this file: hydration is best-effort, only the SERVICE role does it, and the CLIENT role, which is where the Access buttons run, does not. **Scope: actions only.** Since 2026-08-02 the Network access "Detected Tailscale" hint and the Mobile Access tailnet state are read from the machine's interface list with no CLI, so this variable affects only **Settings → Access**'s Sign in and Expose buttons (`tailscale up` / `tailscale serve`). Neither detection nor this override can change what a process binds to.
