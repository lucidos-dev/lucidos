# Database Schema Reference

Lucidos uses **event sourcing** — the `events` table is the central source of truth. Thread metadata cached in `thread_summaries` (projection maintained by EventBus).

## Key tables

| Table | Purpose |
|---|---|
| `events` | Event store. Columns: `id` (uuid), `event_type` (text), `payload` (jsonb), `created` (timestamptz), `thread_id` (uuid), `sequence` (bigserial), `aggregate` (text), `aggregate_id` (text). |
| `changes` | CC proposed changes. Columns: `id`, `request_id`, `branch_name`, `repo_root`, `description`, `file_count`, `files` (text[]), `requires_restart`, `status` (`pending`/`applied`/`discarded`), `created_at`, `resolved_at`, `thread_id`. `repo_root` legitimately holds a workspace root path (not just a registered repo root) for *app coding-agent thread* changes — apply routes by `thread_summaries.coding_agent_kind`, not by `repo_root` shape. |
| `thread_summaries` | Projection — cached thread metadata (title, source, last_activity, message_count, is_saved, has_response). Maintained by EventBus. Carries `last_user_action` and `last_agent_action` (both TIMESTAMPTZ NOT NULL DEFAULT NOW(), added by `20260615093955_add_last_user_and_agent_action_to_thread_summaries.sql`) — `last_activity` is split into two attributed signals: `last_user_action` bumps only on user-initiated events (human `MessageReceived`, `CodingAgentUserMessageSent`, `UserPromptInjected`, `UserQuestionAnswered`, `*PermissionResolved`, `ChangeApplied`, `ChangeDiscarded`), `last_agent_action` only on agent/trigger events (streaming, terminal responses, `CodingAgentIdled`, trigger fire/complete, the agent ASKING, non-human `MessageReceived`); `last_activity` stays the max-of-both. The **`get_saved_threads` query ORDERs BY `last_user_action DESC`** (the Saved section sorts by the family's freshest user action; indexes `idx_thread_summaries_last_user_action` + `..._source_user_action`) so background agent churn no longer reshuffles it. The **Archive pile orders AND paginates by `created_at DESC`** instead — `get_older_threads` (cursor filter + ORDER BY), the **global** archive `ROW_NUMBER` window in `get_recent_threads` (`PARTITION BY (archive_state='archived')` — the newest `archive_limit` archived rows across ALL sources, NOT per-source: a per-source window is a union of per-source `created_at` prefixes that a single global cursor cannot page gap-free, so it surfaced sparse coding-agent/trigger threads above their real date, skipped intervening chats, and halted scroll early — fixed 2026-06-27, plan `docs/plans/2026-06-27-archive-pile-chronological-ordering.md`. The outer `WHERE` then still had two out-of-window bypasses — `status IN (failed, waiting_for_user_answer)` and `coding_agent_proposed=TRUE` — that injected archived rows ahead of their `created_at` position (months-old failed threads jammed under the newest window); both were REMOVED (`docs/plans/2026-06-27-archive-actionable-bypass-gap.md`). The outer `WHERE` is now ONLY `archive_state='inbox'` (unbounded) OR the contiguous archived window (`rn <= archive_limit`): an archived `failed`/`waiting_for_user_answer` thread reaches the drawer purely via `created_at` pagination at its true date (gap-free), and archived-`coding_agent_proposed` needs no bypass because it is an impossible state — a pending in-workspace change has no Archive action (`is_blocking`) and external-repo archiving applies the change before `ThreadArchived`. The INNER candidate filter keeps `... OR coding_agent_proposed = TRUE` (scopes which rows are candidates, so an inbox proposed/active row with no response still surfaces; mirrors `get_older_threads`' `has_response` gate). `loadOlderThreads` correspondingly dropped its actionable/proposed cursor-skips), the `/threads/older` cursor (the frontend sends the oldest loaded thread's `created_at`), and the frontend `byCreated` display sort (`sortDrawerSections`) all key on `created_at` (indexes `idx_thread_summaries_created_at` + `..._source_created_at`, added by `20260624063232_add_thread_summaries_created_at_indexes.sql`) so the visible order matches the `created_at` date each row displays and pagination stays gap-free. The Current section also sorts client-side by `byCreated`. Attention bubbling (REVIEW sectioning) is unchanged. `last_agent_action` drives the thread-row tooltip's "Agent ·" line. Facets, the family-extension cap, and the LLM/script `list_thread_summaries` surface deliberately keep ORDER BY `last_activity`. `archive_state` column defaults to `'inbox'` (since `20260518132821_blocking_count_running_overrides_archived.sql`) — fresh rows are not silently archived. Also carries `blocking_descendant_count` (INT, default 0) — rolled-up count of transitive descendants currently in a state that prevents this thread's archive (Running, WaitingForUserAnswer, or has_pending_changes on a non-external-repo CodingAgent thread — see `is_blocking` in `thread_lifecycle.rs`; Running / WaitingForUserAnswer block regardless of `archive_state`). Consumed by `available_thread_actions(..., descendants_block_archive: bool)` via `count > 0`; maintained by `propagate_blocking_change` in `event_bus_projection.rs`. AND `attention_descendant_count` (INT, default 0, added by `20260522091904_add_attention_descendant_count.sql`) — strict subset of `blocking_descendant_count` that DROPS the `Running` case. Counts transitive descendants in WaitingForUserAnswer OR with pending changes (CC && !external_repo) — the user-attention subset, per `is_attention_needing` in `thread_lifecycle.rs`. Consumed by `display_section(..., has_attention_descendants: bool)` via `count > 0` to bubble the ancestor chain to REVIEW. Relationship: `is_blocking = is_attention_needing OR status == Running`. Maintained by the same `propagate_blocking_change` walk in lockstep with `blocking_descendant_count`. ALSO carries `coding_agent_kind` (TEXT, nullable, added by `20260527131839_add_coding_agent_kind_and_folder_to_thread_summaries.sql`) — `'lucidos' \| 'app' \| 'external'` — and `coding_agent_folder` (TEXT, nullable) — the canonical folder the spawn targets (`<ws>/data/apps/<id>/` for App, repo root otherwise). AND `coding_agent` (TEXT, nullable, added by `20260612154421_add_coding_agent_to_thread_summaries.sql`) — `'claude-code' \| 'codex'` — which backend drives the thread. NULL = legacy Claude Code row; consumers default via `CodingAgent::parse`. Written by the SessionStarted projection arm with COALESCE-keeps-existing, so the backend is locked at the thread's first session (a flip would resume nothing — the other backend has no session). Read by `run_direct_agent`'s backend resolution (stored value beats the request), `validate_thread_continuity` (mismatched follow-up → 409), `thread_coding_agent` (event stamping on engine-internal flows), and the `/api/v1/claude-code/commands` handler (backend-specific control menus). **Not backfilled** — the engine writes a non-NULL `cc_repo_id` for both Lucidos-source and external threads (Lucidos-source threads get the registered Lucidos repo UUID), so the naive `cc_repo_id IS NOT NULL → external` rule would mislabel every legacy Lucidos thread. Legacy rows stay NULL; consumers default NULL to `'lucidos'` via `CodingAgentKind::parse`. New rows are filled by the SessionStarted projection arm via COALESCE-keeps-existing. Consumed by `apply_change`'s `load_apply_kind_context` to dispatch (skip `/harden` + restart + emit `AppUiRefreshRequested` for `'app'`) and by the WIP-preview app-UI route to locate the worktree's app folder. The `coding_agent_bg_bash_pending` column was DROPPED (`20260529155954_drop_coding_agent_bg_bash_pending.sql`). It backed the removed bg-bash propose-gate: the engine used to refuse `ChangeProposed` at idle while a CC background bash task was (thought to be) pending, surfacing this column → a "CC waiting on background tasks" banner with no Apply button until a 5-minute `BgBashWakeRequested` nudge fired. That gate (plus its tracker, timer, event, and `display_section`/`resolve_actions` `bg_bash_pending` params) was removed — changes now propose the instant CC idles, and correctness is covered by harden-at-apply. The `CodingAgentIdled.bg_bash_pending` event field is kept as recorded history but no longer projected. Threads wedged by the old gate auto-recover at boot via `propose_held_back_changes_on_startup` (re-proposes any idle CC thread with a committed diff but no proposal). The same `CodingAgentIdled` projection arm also writes `coding_agent_has_diff = payload.has_changes` (git-truth, drives the WaitingBanner Diff button independently of the proposal lifecycle — the prior bug was a "No changes on this branch" tooltip on a worktree with five commits because `coding_agent_has_diff` was only set by `ChangeProposed`). **Compose-draft columns** (written directly by `PUT /threads/:id/compose`, not via an event projection — the row IS the authoritative draft store): `compose_text` / `compose_images` (JSONB) / `compose_mode`, plus `compose_selection` (JSONB, nullable, added by `20260701163714_add_compose_selection_to_thread_summaries.sql`) — the per-draft dropdown selections (target/scope, coding agent, Lucidos model + reasoning, coding-agent model + reasoning) as a partial `ComposeSelectionOverride`-shaped object; NULL = no per-draft picks (client resolves each unset field to its account default). All four use `COALESCE($n, col)` in the compose UPDATE so a text-only keystroke PUT preserves the stored value, and are read back into the emitted `ThreadComposeChanged` for cross-device sync + rehydrated on reload (`stageDraftFromApi`). See `docs/plans/2026-07-01-compose-selection-db-persistence.md`. |
| `notifications` | Projection — from `NotificationCreated` events. Columns include `tap` (jsonb, default `'{"kind":"modal"}'`) — discriminated union controlling what happens on tap. Kinds: `{"kind":"modal"}` (opens the inbox detail — the default, and the only kind for info-only notifications), `{"kind":"navigate","to":{"target":"...","app_id":"...","id":"...","event_id":"...","file_path":"...","url":"...","prompt":"...","settings_view":"..."}}` (delegates to the `navigate_ui` router). CHECK constraint enforces `tap ? 'kind' AND tap->>'kind' IN ('modal','navigate')`. The passive `{"kind":"none"}` kind is RETIRED (`20260702162723_drop_notification_tap_none.sql` rewrote existing `none` rows to `modal` and dropped `none` from the CHECK; `docs/plans/2026-07-02-remove-notification-tap-none.md`) — every notification is openable. Historical `NotificationCreated` events keep `{"kind":"none"}` forever (immutable), but the engine's custom `Tap` deserialize (`scheduler/notifications.rs`) coerces `none` → `Modal` on any replay, so a projection rebuild never re-emits a `none` row. The column was JSONB-migrated from the old four-string text form by `20260522152123_notification_tap_jsonb.sql` (rewriting `'open_app'` → `{kind:navigate,to:{target:app,app_id:<row.app_id>}}` and `'open_thread'` → `{kind:navigate,to:{target:thread,id:<row.thread_id>,event_id:<row.event_id>}}`). `event_id` (uuid, nullable) — specific event inside `thread_id` that raised this notification; the §4 in-app matrix uses it for the "user looking at source event" auto-read check (distinct from `tap.to.event_id` which controls the scroll-and-pulse target when the tap navigates). (`push_dispatched` was added by `20260518173257_add_push_dispatched_to_notifications.sql` to gate a cross-device read-marker push fan-out; both the column and the fan-out were dropped in `20260518204120_drop_push_dispatched_from_notifications.sql` — see work-tracker `pwa-read-on-another-device-noise`.) |
| `thread_queue` | Projection — the *Thread Queue* (admission control). Holds **background** entries only: `status = 'queued'` (waiting for capacity) or `'admitted'` (the persisted active-session record). Columns: `id` (uuid PK = entry id), `kind` (`event-trigger`\|`cron`\|`sub-thread`\|`coding-agent`), `trigger_id`/`trigger_name` (trigger kinds), `thread_id` (bound thread for spawn kinds), `summary`, `request` (jsonb — full re-executable `ThreadQueueRequest`), `queued_at`, `admitted_at`, `sequence` (FIFO). Maintained in-tx from `ThreadQueued`/`ThreadQueueAdmitted` (upsert/flip) and `ThreadQueueDropped`/`ThreadQueueCompleted` (delete) — rows exist only while the entry is live; the events table keeps the audit trail. Rebuilt into the manager's memory at boot (`recover_persisted_entries`): admitted rows whose work died with the old process re-queue (`requeued: true`), spawn rows whose thread already materialized hand off to thread-level recovery, and **duplicate cron rows for one trigger collapse to one** (oldest kept + re-queued, the rest emit `ThreadQueueDropped` reason "coalesced on recovery") so a restart storm can't re-stack a cron backlog. **Cron holds at most one entry per trigger** (active + queued ≤ 1): a cron fire carries no distinct payload, so `submit` *coalesces* a redundant cron fire (drops it, no `ThreadQueued`) instead of queueing — `max_queued_per_trigger`/`overflow` apply only to event triggers. **User-initiated work shares the same pool but is NOT a row here** (ADR 0008): `acquire_user_slot` tracks it in-memory only (ephemeral runtime — a dead response is gone on restart, never re-fired) and the panel API merges it in as `kind: "user-chat"`; the transient `ThreadQueueChanged` event refreshes the panel when only user-slot state moves. |
| `apply_all_batches` | Projection — durable **membership** mirror of the in-memory Apply-All registry (`engine::apply_all_batches::ApplyAllRegistry`; added by `20260619124120_create_apply_all_batches_projection.sql`). Columns: `batch_id` (uuid PK), `change_ids` (uuid[] — members in pending-list order), `actor` (jsonb, nullable — who clicked Apply All), `created_at`. Membership ONLY — per-member resolution is NOT stored; recovery reconstructs it from the authoritative `changes.status`. The driver (`engine::apply_all_driver`) is the single live authority: it INSERTs the row in `start_apply_all_batch` and DELETEs it (`persist_batch_removed`) wherever it removes the batch from the in-memory registry (completion, cancel, recovery). Rows exist only while a batch is live — a clean boot finds zero; the `events` table (`ApplyAllBatchStarted`/`Completed`) keeps the audit trail. Rebuilt at boot by `LucidosEngine::recover_apply_all_batches` (called from `main.rs` after agent/CC recovery): each member is classified `applied` → applied, `discarded`/missing → terminal, `pending` → re-driven through the idempotent `apply_change` (skipped if its thread has a running session). A fully-resolved batch emits the missing `ApplyAllBatchCompleted` so the frontend's "Applying changes…" toast clears. Without this the batch was lost on restart and the toast stuck forever. |
| `preferences` | Key-value store with optional `device_id` scoping. |
| `memory_entries` | Vector memory with pgvector embeddings (384-dim). |
| `credentials` | Service credentials. `env_var_name` (TEXT, nullable, added by `20260618124350_add_env_var_name_to_credentials.sql`): an optional custom env var name for the injected secret; when set, `credential_env_vars()` ALSO injects the secret under that exact name (e.g. `GITHUB_TOKEN`) IN ADDITION to the canonical `CRED_<NAME>` (an extra alias, not a replacement; single-value types only; `password` keeps the `_USERNAME`/`_PASSWORD` split). Validated at the API boundary via `environment_variables::validate_name`. **`auth_type` is the discriminator, and `service_name` carries no namespace prefix.** Until 2026-08-05 an `oauth_client` row was named `oauth:<provider>` and an `email_password` row `email:<account>`, which spelled a second time, into an untyped field, what `auth_type` already recorded. The two could drift, and did: a correctly-typed row under a bare name was unreachable by every read path. `20260805134838_drop_credential_name_prefixes_use_auth_type.sql` strips both prefixes and replaces the single `UNIQUE (service_name)` with **two** constraints: `UNIQUE (service_name, auth_type)` (the new identity) and a PARTIAL `UNIQUE (service_name) WHERE auth_type <> 'oauth_client'`. The asymmetry is load-bearing. A name stays GLOBALLY unique for every type that is injected as `CRED_<NAME>` or resolved by bare name, and `oauth_client` alone may shadow a name (a Google API key beside the Google app registration). So `CredentialStore::get` adds `AND auth_type <> 'oauth_client'` and keeps returning one row, which is what leaves the five bare-name readers correct without changing: the provider keys in `llm/provider_build.rs` (`anthropic`, `openai`, `openrouter`, `xai`, `local`) and the `apis.json` resolvers in `api/proxy.rs` / `api/proxy_builtin.rs`. Typed reads go through `get_oauth_client` / `get_email_password` / `get_typed`. `upsert_row` picks its `ON CONFLICT` target by type to match (composite for `oauth_client`, the partial index otherwise, so saving an existing name under a new type still REPLACES rather than raising a bare 23505). **An `oauth_client` row is never injected as `CRED_*`** (`credential_env_vars` skips it): its value is a client blob only the OAuth flow reads, from the DB, so injecting it broadcast a `client_secret` for no reader, and excluding it is also what keeps `CRED_<NAME>` unambiguous. The migration renames only where the target is free and moves at most one row per target, `RAISE NOTICE`ing whatever it skipped; a stranded `email:` row is still resolved by `get_email_password` (a registered temporary measure). The superseded `20260805085054_normalize_oauth_client_credential_names.sql` stays on disk as applied history, because sqlx refuses to run when a previously-applied version is missing from the resolved set. **The credential HTTP verbs that act on an existing row take `id`, not a name** (`PUT`/`DELETE /api/v1/credentials`, `GET /api/v1/credential-value`), since a name identifies at most a pair and the edit form can change `auth_type`; `POST` stays name-keyed because it is an upsert. Every other auth type keeps its name verbatim, because that name is what `CRED_<NAME>` injection and `apis.json` service lookups resolve. **`auth_value` for an `oauth_client` row is a plaintext JSON blob** (`{client_id, client_secret?, auth_url, token_url, userinfo_url?, userinfo_method?, authorize_params?, scopes?, redirect_uri?}`) and is the per-credential source of truth for the OAuth flow's endpoints. `authorize_params` (`key=value&key=value`, absent means `access_type=offline&prompt=consent`) carries the provider's own spelling of "issue a refresh token"; `20260805104126_backfill_dropbox_offline_authorize_params.sql` adds Dropbox's `token_access_type=offline` to clients connected before the key existed, keyed on the stored `auth_url` (the name is a user-chosen alias), skipping any row that already sets it and any whose value is not `IS JSON OBJECT`. |
| `environment_variables` | User-managed **non-secret** env vars (Settings → System → Environment variables; added by `20260618121152_create_environment_variables_table.sql`). Columns: `id` (uuid PK), `name` (TEXT UNIQUE NOT NULL — `^[A-Z_][A-Z0-9_]*$`, not engine-reserved), `value` (TEXT, plaintext — deliberately non-secret), `created_at`, `updated_at`. `EnvironmentVariableStore` (`core/environment_variables.rs`) does CRUD + `env_pairs()` (reserved-filtered `(NAME,value)` for injection). Injected per-spawn (fresh, no cache → no restart) into every subprocess via `build_script_env_vars` + `apply_lucidos_env`, BEFORE engine-owned vars so the engine always wins. ALSO applied to the engine's OWN process env at startup (`apply_to_process_env`) so engine-internal shell-outs that inherit it — the engine's own `git push`/`fetch`/`clone`, stdio MCP servers, `open` — see them too (these pick up a CHANGE only on the next restart, like the old `data/.env`). The legacy per-workspace `data/.env` was retired into this table (`migrate_env_file_to_db` at startup). CRUD emits `EnvironmentVariable{Set,Deleted}`. |
| `devices` / `push_subscriptions` | Push notification targets. |
| `device_presence` | Presence projection (transient — no `events` rows). `device_presence(device_id PK, visible_at)` tracks devices with any visible top-level Lucidos tab. `DevicePresenceStore::candidates` returns the device_ids that pinged visible in the last 2 minutes (`PRESENCE_STALE_AFTER`). It is now the **secondary** input to the PresenceCheck gate: `send_push_to_all_with_app` runs the protocol when `max(engine.sse_connections.count(), candidates.len()) > 0` (`expected_pong_count` in `scheduler/push.rs`) and skips it (→ `push_allowed=true` directly) only when BOTH are zero. The live SSE-connection count is the primary signal — it doesn't go stale when iOS suspends the 30s heartbeat on a foregrounded PWA, which is why a heartbeat-only gate fired pushes on active pages. Maintained from transient `DeviceVisible` / `DeviceHidden` SystemEvents. Per-thread focus is no longer persisted — every page reports `focused_thread_id` live in its PresenceCheck pong (see `system-knowhow/notifications.md` §3). |
| `mcp_servers` | MCP server configs. Carries a **cached tool manifest** since `20260814122644_add_tools_cache_to_mcp_servers.sql`: `tools` (JSONB NOT NULL DEFAULT `'[]'`, the `McpTool` array verbatim as `{name, description, inputSchema}`), `tools_observed_at` (TIMESTAMPTZ NULL) and `disabled_tools` (TEXT[] NOT NULL DEFAULT `'{}'`). Only a RUNNING server advertises tools, so before this a stopped one reported zero tools and zero cost, indistinguishable from one that genuinely costs nothing. `McpServerStore::set_tools` writes the manifest from `start_server_internal` **after** `McpClient::connect` succeeds, so a failed start leaves the previous manifest intact; it is the table's one **silent** writer (a registered `ExemptWriter`, because a cache refresh is an observation and the only candidate event describes an auto-approve change). `tools_observed_at` is the freshness signal instead: **NULL means never observed**, which every pre-migration row reads as, and `GET /api/v1/mcp/servers` reports that as `tools_source: "never-observed"` rather than a zero-cost server. `disabled_tools` holds **wire names** (`mcp__<server>__<tool>`), the same spelling the permission allowlist and dispatch key on; `get_tool_definitions` filters them out of every request, and `call_tool` refuses one at dispatch. Dispatch is the half that enforces it: a call already in flight, or a resumed turn carrying the old definitions, would otherwise still run. `McpServerStore::set_disabled_tools` announces via `McpServerDisabledToolsChanged`. |
| `models` | Chat-model registry (Settings → Models). Plain config table (authoritative, like `mcp_servers`/`credentials`), seeded with builtins by `20260610152555_create_models_registry.sql`; user rows added via the HTTP API. Columns: `id` (PK, the request value, e.g. `claude-fable-5`, `claude-opus-4-8@default[1m]`; `[1m]` variants are separate rows), `label`, `provider` (`vertex`\|`anthropic`\|`openai`\|`openrouter`\|`xai`\|`opencode-free`\|`local`: `openai`/`openrouter`/`xai`/`opencode-free`/`local` all speak the OpenAI Chat Completions wire format but are distinct backends; e.g. `z-ai/glm-5.2` is a seeded `openrouter` builtin and `grok-4.6` a seeded `xai` one; `opencode-free` alone carries no credential and is gated on the `opencode_free_enabled` preference), `sort_order`, `source` (`builtin` disable-only \| `user` deletable), `enabled`, `context_window` (INTEGER, nullable, added by `20260725200708_add_context_window_to_models.sql`), `created_at`, `updated_at`. `context_window` is the model's window in tokens; **NULL = not declared**, so `llm::model_registry::context_window_from_prefix` guesses from the id shape (`[1m]`→1M, `claude-`→200k, `gpt-5`→400k, else 200k). Two migrations declare it where the guess is wrong: `20260725200708_add_context_window_to_models.sql` (adds the column; 1048576 for `z-ai/glm-5.2` + the three Gemini rows, which the map has no rule for at all) and `20260725211150_declare_context_window_for_all_builtin_models.sql` (1050000 for `gpt-5.5`/`gpt-5.5-pro`/`gpt-5.6-{sol,terra,luna}`, which the map understates at 400k; plus the six Claude `[1m]` rows at 1000000, matching what the suffix already infers). `20260814161515_seed_xai_grok_models.sql` declares its four rows inline as it seeds them, since the map has no `grok-` rule either: `grok-4.6` / `grok-4.5` at 500000, `grok-4.20` at 2000000, `grok-4.3` at 1000000. `20260822195315_seed_opencode_free_models.sql` does the same for the six keyless free models, whose ids share no shape at all: `laguna-s-2.1-free` at 256000, `nemotron-3.5-lightning-free` at 262144, `x-preview-f-free` / `nemotron-3-ultra-free` at 1000000, `muse-spark-1.2-contributor-free` at 1048576, `hy3-free` at 190000. Seeding them does not switch the tier on, and `big-pickle` is excluded because the relay serves it only to the OpenCode CLI's own User-Agent. **Bare `claude-*` rows stay NULL on purpose**: 1M mode is gated on Lucidos's own `[1m]` suffix (`parse_context_suffix` → `is_1m` → the `context-1m-2025-08-07` beta in `build_claude_request`), so a bare id sends no beta and 200k really is its request window; declaring 1M there would let the packer exceed the API mode selected. Five older rows are also NULL because their windows are unverified (`claude-opus-4-5@20251101`, `gpt-5.4`, `gpt-5.3-codex`, `gpt-5.3-codex-spark`, `gpt-5.2-codex`). Every guess errs low deliberately, since under-declaring only trims early while over-declaring makes the provider reject the request. `llm::model_registry::declared_window` drops a non-positive stored value. Drives the Lucidos Agent model picker, `RoutingProvider`'s provider selection, and the context trim budget. That budget reads the in-memory `ModelRegistry`, a `HashMap<String, ModelRouting>` of provider plus optional window, reloaded on `Model*` events. The Claude Code `/model` picker stays separate in `runtime/cc_menu_options.json`. CRUD emits `Model{Created,Updated,Deleted}`. |
| `oauth_accounts` / `email_accounts` | External account configs. `oauth_accounts` records **two** scope sets: `scopes` is what the provider GRANTED (`core::oauth` prefers the token response's `scope`, falling back to the requested set only when the provider reports none), and `desired_scopes` (TEXT, nullable, added by `20260807072717_add_desired_scopes_to_oauth_accounts.sql`) is what the account was ASKED for. `prepare_oauth_flow` writes the latter from the set it already computes as `merged_scopes` = `granted ∪ previous_desired ∪ requested`, so it accumulates monotonically and a scope once asked for is asked for again whether or not it was granted. The *Reconnect* button re-requests `desired_scopes`; re-requesting `scopes` made the same merge compute `granted ∪ granted`, a no-op, so an account a provider had narrowed could never recover the difference, which is exactly what `core/backup/dropbox.rs`'s permission error sends the user there to do. **No backfill**: NULL means never recorded, and both the merge and the frontend's `reconnectScopes` treat it as nothing extra, so a legacy account is never narrowed. |
| `repositories` | Registry of registered git repos (the default Lucidos source + any user-added external repos). | `webhooks` | Inbound *webhook* config (ADR 0097). A CHECK constraint (`webhooks_needs_a_verifier`) refuses a row with neither `token_hash` nor `hmac`, so a publicly reachable endpoint with nothing to verify is not a storable state. Written only by `WebhookStore` (`core/webhooks.rs`), which emits from inside its own write paths, so every mutation surface announces by construction. |
| `webhook_deliveries` | *Delivery ledger* for webhook idempotency (ADR 0122). Columns: `webhook_id` (uuid, FK to `webhooks` `ON DELETE CASCADE`), `delivery_key` (text), `event_id` (uuid, nullable), `created` (timestamptz), PK `(webhook_id, delivery_key)`. **A nonce ledger, not a delivery log**: no payload, no list surface, and its only reader is the next delivery. The PK IS the concurrency control. `DeliveryLedger::claim` runs one `INSERT ... ON CONFLICT DO UPDATE ... WHERE created < NOW() - make_interval(secs => $n) RETURNING`, so a returned row means "you own this delivery" (fresh key, or a claim past its window) and no row means a live claim holds it. Two concurrent copies of one delivery serialize on the index and exactly one emits. `delivery_key` is always a SHA-256 digest, of `header:<value>` when the hook names a dedupe header and of `body:<body>` otherwise, so a public caller's header value is never stored raw and the two sources cannot key the same claim. `claim_id` is re-minted on every claim and takeover, and `record_event` / `release` both require it. So an owner whose emit outran the window cannot stamp its event onto the claim that replaced it, nor delete it. `event_id` is written after the emit, and stays NULL while the holder is in flight. A resend arriving then answers **503**, not 200: that holder can still fail, and a 2xx would stop the sender retrying a delivery nobody emitted. A failed emit DELETEs the claim, so the sender's retry is a real retry. A claim read back as absent is re-attempted (`CLAIM_ATTEMPTS`), never reported as a duplicate. Written only by `DeliveryLedger` (`core/webhook_deliveries.rs`); classified `Silent` in `announced_surfaces.rs`. Swept daily at 03:10 UTC by `prune_webhook_delivery_claims`, whose horizon is `MAX_WINDOW_SECS` (7 days), the SAME constant that caps a configurable window, so the sweep can never drop a claim still deciding a duplicate. |

## Querying threads

No `threads` table. Use:
```sql
SELECT DISTINCT aggregate_id FROM events WHERE event_type = 'CodingAgentIdled';
SELECT payload->>'title' FROM events WHERE aggregate_id = '<id>' AND event_type = 'ThreadTitleGenerated' ORDER BY created DESC LIMIT 1;
SELECT thread_id, branch_name, description, status FROM changes WHERE status = 'pending';
```

## Key event types

**Persisted means subscribable** (`docs/adr/0113-persisted-system-events-are-subscribable.md`). Every `SystemEvent` marked persisted below is a valid `await_event` name and a valid trigger `on:` entry. Every frame marked transient is refused at registration, because it writes no row for either matcher to see. One predicate decides it for both fan-outs: `core::event_subscription::is_subscribable_system_event`, keyed on `SystemEvent::is_persisted()`. So a new variant needs no separate list, just the persistence decision it already makes.

- **Thread lifecycle:** `SessionStarted`, `SessionEnded`, `ThreadTitleGenerated`, `ThreadSaved`/`ThreadUnsaved`/`ThreadArchived`
- **Chat / triggers (Lucidos Agent):** `MessageReceived`, `ResponseGenerated`, `ResponseCanceled`, `ResponseAborted`, `TextStreamed`, `ThoughtStreamed` (serde alias `Thinking` for pre-T7 rows), `TodoListWritten` (chat-agent only — replace-whole-list snapshot of the thread's *todo list*; payload = `{ items: [{ content, active_form, status }] }`). These exist on chat AND CC threads — `MessageReceived` is the user typing, regardless of which agent answers. To filter chat-only, join `thread_summaries` and gate on `source = 'chat' AND is_coding_agent = false` (or `source IN ('chat','trigger')` to include triggers).
- **Coding Agent (CC):** `CodingAgentUserMessageSent` (user-typed), `CodingAgentPromptSent` (engine-synthesized: hardening, conflict recovery), `CodingAgentTextStreamed`, `CodingAgentToolCalled`, `CodingAgentToolResult`, `CodingAgentIdled`, `CodingAgentSettingsChanged`, `CodingAgentPermissionRequest`/`CodingAgentPermissionResolved` (the coding-agent permission card — raised by CC's MCP permission prompt and by the Codex app-server approval bridge). A `CodingAgentIdled` (session/turn end) clears any still-pending `CodingAgentPermissionRequest` on the thread via `resolve_pending_permissions_as_session_ended` (reason `"Coding agent session ended before answering — request expired"`), so a finished session leaves no dangling card; and a `CodingAgentPermissionResolved` flips status to `running` ONLY from `waiting_for_user_answer` (a stale click on an already-idle thread no longer resurrects it into a dead `running` — see `.claude/rules/db.md` § Command guard for the shared projection arm). Old `ClaudeCode*` names are serde aliases — write new code against `CodingAgent*`.
- **Command guard (chat, ADR 0002):** `CommandPermissionRequested`/`CommandPermissionResolved` — the chat mirror of the `CodingAgentPermission*` pair. Emitted when a bash/python command hits the `IrreversibleDanger` lane on a chat channel; renders a `PermissionCard`. Request flips status to `waiting_for_user_answer`; resolution flips back to `running` ONLY from `waiting_for_user_answer` (the shared projection arm in `event_bus_projection_thread.rs` — `CodingAgentPermissionResolved` / `McpPermissionResolved` behave identically; a stale resolution on an idle/terminal thread leaves the status unchanged so it can't zombie a finished thread). `UserQuestionAnswered` deliberately stays on its own UNCONDITIONAL `→ running` branch — a question answer can resume an already-idled thread via `--resume`, which a permission resolution never does. `Resolved` carries `allowed`, optional `reason`, optional `persist_scope` (`narrow`/`broad`/`session`). Both persisted; chat-channel only. Resolved via `POST /api/v1/command-permission/consent`.
- **Chat MCP permission (`engine::mcp_permission`):** `McpPermissionRequested`/`McpPermissionResolved`: the chat mirror of the command-guard pair for **MCP server tool calls** (`mcp__<server>__<tool>`). `Requested` carries `request_id`, `tool_use_id`, `server_id`, `server_name`, `tool_name`, `arguments_summary`; renders a `PermissionCard`, flips status to `waiting_for_user_answer`. `Resolved` carries `allowed`, optional `reason`, optional `persist_scope` (`narrow` → `Mcp(server:tool)`, `broad` → `Mcp(server:*)` persisted to the workspace's `mcp-allowed-tools`; `session` → in-memory). Both persisted; chat-channel only, resolved via `POST /api/v1/mcp-permission/consent`. **No card** (auto-approved) in a non-interactive trigger thread or when the server's `auto_approve` flag is set. Replaces the removed transient `McpConsentPromptRequested` modal.
- **Command checkpoint / undo (ADR 0002, Phase 4, amended 2026-08-06):** `CommandCheckpointed`/`CommandCheckpointReverted`. Emitted when the command guard hits the `ReversibleDanger` lane (in-workspace deletion/overwrite). The engine snapshots the git-visible working tree **twice**, both as non-invasive `commit-tree`s via a throwaway `GIT_INDEX_FILE`: a **pre** image on `refs/lucidos/command-checkpoints/<checkpoint_id>` before the command, and a **post** image on `refs/lucidos/command-post-images/<checkpoint_id>` after it. Diffing the pair names exactly what the command created (`A`), overwrote (`M`) and deleted (`D`). `CommandCheckpointed {checkpoint_id, command, summary, restores, removes}` is emitted **after** the command returns, and **only when that diff is non-empty**: a command whose destruction landed entirely in a gitignored path (`.lucidos/`, `data/blobs/`) leaves the images identical, so both refs are dropped and no card is shown rather than one whose Undo can do nothing. `restores` / `removes` default to 0 on events written before the counts existed. The one-click Undo restores the working tree from the pre image, removes each created file git still calls unchanged against the post image, and emits `CommandCheckpointReverted {checkpoint_id}` (stamped with the checkpoint's `request_event_id` so it groups into the same exchange). The refs **survive** the undo, because they also back the card's diff viewer; `prune_expired_checkpoints` reclaims pairs older than 30 days. Neither event changes thread status. Undo via `POST /api/v1/command-checkpoint/undo`; the diff via `GET /api/v1/command-checkpoint/diff?checkpoint_id=...`. Both persisted.
- **Changes:** `ChangeProposed`, `ChangeApplied`, `ChangeDiscarded`. Every real merge path in `engine::change_ops::apply_change` (and `apply_now_success` in agent sessions) calls `emit_entity_events_for_change_apply` after `ChangeApplied` to derive per-entity events (`AppCreated`/`AppUpdated`/`AppDeleted`, `ArtifactCreated`/`ArtifactUpdated`/`ArtifactDeleted`) by comparing pre-merge git state vs. post-merge disk state, so frontend caches that subscribe to entity events refresh after a coding-agent thread lands files in `data/apps/<id>/` or `data/artifacts/`. `ChangeApplied` is emitted **at most once per `change_id`**: `EventBus::emit` `FOR UPDATE`-claims the change row (`ChangesProjection::change_apply_dedup`) and suppresses the persist if the row is already `applied`, so concurrent double-fires, HTTP/Apply-All retries, conflict-recovery cleanup, and post-restart recovery re-applies can't produce two "Change applied" timeline entries for one change (rows still `pending` or with no aggregate row `Proceed` and emit once).
- **Tools:** `ToolCalled`, `ToolResult`, `HttpRequestSent`, `HttpResponseReceived`, `BackgroundBashStarted`, `BackgroundBashCompleted` (the latter two form the durable record for the `run_bash_background` / `bash_output` / `bash_kill` chat tools — `bash_output` falls back to `BackgroundBashCompleted` after the in-memory registry evicts the task on completion)
- **System:** `NotificationCreated`, `PreferencesChanged` (event-sourced, with projections)
- **Backup:** `BackupProgress` (transient — pure SSE progress, never persisted, one per tick), `BackupCompleted`, `BackupFailed` (**persisted** since the run-history change — they ARE the durable record of every backup run). Aggregate = `ops`, `aggregate_id` = `global`. `BackupCompleted`/`BackupFailed` payloads carry `started_at` + `finished_at` (RFC 3339; duration = the difference); `BackupCompleted` also `filename` + `size_bytes`, `BackupFailed` also `error`. Read newest-first by `core::backup::load_recent_runs` (`SELECT … FROM events WHERE event_type IN ('BackupCompleted','BackupFailed') ORDER BY created DESC LIMIT n`) — no projection table. Backup ALSO persists just the latest run's outcome (now incl. `started_at`) under the `backup_last_run` preference via `BackupLastRun` (read by `GET /api/v1/backup/status` and the `get_backup_status` tool). **Restore is NOT an engine concern.** It moved to the workspace picker (gateway control plane): the gateway provisions a new workspace, then shells out to the engine binary's one-shot `lucidos-engine restore-archive` subcommand (decrypt → unpack → `pg_restore` into the provisioned dir + DB; it does NOT restore the archive's `user_dir/` over `~/.lucidos`, which would clobber the gateway registry). Progress is the gateway's in-memory single-slot `RestoreStatus` (`idle`/`running`+phase/`completed`/`failed`), exposed at `GET /~/api/v1/control/restore-status` (DELETE clears a terminal result) and driven by the upload at `POST /~/api/v1/control/workspaces/restore` (multipart). The engine's old `Restore{Progress,Completed,Failed}` SystemEvents, `engine.restore_state`, and `/api/v1/backup/restore*` / `start-workspace` / `validate-workspace-name` routes were removed.
- **Presence (transient):** `DeviceVisible`, `DeviceHidden`, `PresenceCheck`. Aggregate `device_presence` (device-visibility events) or `presence` (PresenceCheck). Never persisted to `events`. `PresenceCheck` is the engine's fan-out **pong trigger** at `NotificationCreated` time — every connected page POSTs `/api/v1/presence-pong` with its live `is_active`, `focused_thread_id`, `event_in_viewport`, and the engine uses the pongs to decide whether to send the OS push (see `system-knowhow/notifications.md` §3). It carries no toast content (that moved to `NotificationToastRequested`). `ThreadFocused` / `ThreadUnfocused` and the `thread_presence` table they fed were retired in favour of the live pong.
- **In-app toast (transient):** `NotificationToastRequested`. Aggregate = `notification`, `aggregate_id` = notification_id. Never persisted to `events`. The engine emits it from the `NotificationCreated` fan-out **only on the push-suppressed branch** (`push_allowed = false` — an active device pong'd in), carrying the toast content (`title`/`body`/`thread_id`/`event_id`/`app_id`/`tap`/`sent_at_ms`). It drives the active-page in-app toast (`system-knowhow/notifications.md` §4). Mutually exclusive with the OS push by construction: the toast-request and the push hang off opposite branches of one `push_allowed` decision, so a device never gets both for one notification (the fix for the "toast AND iOS push at the same time" report).
- **Native desktop push (transient):** `NativePushRequested`. Aggregate = `notification`, `aggregate_id` = notification_id. Never persisted to `events`. Same payload shape as `NotificationToastRequested`. The engine emits it from the `NotificationCreated` fan-out **only on the push-ALLOWED branch** (`push_allowed = true` — no active device), the mutually-exclusive complement of `NotificationToastRequested`. A connected Tauri desktop app renders a NATIVE macOS notification from it via its `show_native_notification` command (Apple's `UserNotifications` framework / `UNUserNotificationCenter`, driven directly through `objc2` with a delegate that captures the tap; requires a packaged `.app` build, inert in `tauri dev`) — the embedded WKWebView can't receive Web Push, so this is the desktop counterpart of the web-push fan-out, delivered over the open SSE stream. A tap focuses the window and routes through the same `dispatchDeepLink` as the web-push tap. Browser / PWA pages ignore it (the frontend `handleNativePushRequested` gates on `isTauri()`); they get the real web push on the same branch. See `system-knowhow/notifications.md` §1, §4. Note: `send_push_to_all_with_app` no longer bails the instant `push_subscriptions` is empty — it now runs the PresenceCheck decision whenever any client is connected via SSE, so a desktop-only workspace with zero web-push subscriptions still gets toasts (suppressed branch) and native banners (allowed branch).
- **Native desktop dismiss (transient):** `NativePushDismissRequested`. Aggregate = `notification`, `aggregate_id` = the notification id, or `"all"` when `notification_id` is `None`. Never persisted to `events`. Payload: `{ notification_id: Option<Uuid>, sent_at_ms }`. The cross-device counterpart of a *read*: the engine emits it from the `mark_notification_read` (`Some(id)`) and `mark_all_notifications_read` (`None` = all) HTTP handlers — inside the same `success`/`count > 0` guards as `NotificationRead`/`NotificationsAllRead`, so a no-op (already-read) POST emits neither. A connected Tauri desktop app REMOVES the matching delivered native banner(s) via its `dismiss_native_notification` command (`UNUserNotificationCenter.removeDeliveredNotifications(withIdentifiers:)` / `removeAllDeliveredNotifications`, dropping the stashed deep link so a phantom tap can't route). macOS-desktop-only: browser / PWA pages ignore it (`handleNativePushDismiss` gates on `isTauri()`) because the open web can't silently remove a Web Push banner (Safari revokes a subscription after 3 silent pushes — see `docs/plans/2026-05-18-cross-device-notification-dismiss-design.md`). `sent_at_ms` drives the page-side freshness gate, which drops a late SSE-queue flush — bounding (not fully eliminating, since `removeAllDeliveredNotifications` is blunt) the window in which a delayed dismiss-all could clear a banner for a notification created after an all-read. See `system-knowhow/notifications.md` §4.
- **Thread Queue (admission control):** `ThreadQueued`, `ThreadQueueAdmitted`, `ThreadQueueDropped`, `ThreadQueueCompleted`. Aggregate = `thread_queue`, `aggregate_id` = entry id. All persisted; they drive the `thread_queue` projection (see table above) and the panel's SSE refresh. Emitted for EVERY background spawn — an immediately-admitted entry gets `ThreadQueued` + `ThreadQueueAdmitted` back-to-back, so the events double as the audit trail of background work. `ThreadQueued.requeued = true` marks the boot sweep re-queuing an admitted entry whose work died with the previous engine process. A **coalesced cron fire emits NO `ThreadQueued`** (it never enters the queue); on recovery, duplicate cron rows for one trigger emit `ThreadQueueDropped` with reason "coalesced on recovery". User actions (Run now / Drop) carry `actor`; engine drain decisions pass `None`. AND `ThreadQueueChanged` (fieldless) — aggregate = `thread_queue`, `aggregate_id` = `global`, **transient (NOT persisted, no projection)**: the panel-refresh signal for in-memory-only user-initiated slot moves (which carry no persisted `ThreadQueue*` event — see the `thread_queue` table note + ADR 0008); the frontend refetches the panel on it. AND `CapacityPolicyChanged` — aggregate = `capacity_policy`, `aggregate_id` = `global`, persisted; the LATEST event IS the stored *capacity policy* (no config table — `ThreadQueue::load_policy` reads it at boot). The policy gained a `reserved_background` field (ADR 0008 — background's reclaim floor under user priority); `#[serde(default)]` keeps old persisted payloads readable.
- **Scheduling:** `ScheduledTaskCreated`, `ScheduledTaskStarted`, `ScheduledTaskCompleted`, `ScheduledTaskDeleted`
- **Triggers (audit + firing):** `TriggerCreated`, `TriggerUpdated`, `TriggerDeleted`, `TriggerEnabled`, `TriggerDisabled` (the CRUD lifecycle, emitted by the `/api/v1/triggers*` handlers via `emit_user_system`) and `TriggerExecuted` (engine-driven, emitted when a trigger fires). Aggregate = `trigger`. The five CRUD variants carry `actor`, and that `actor` is merged into the persisted payload + SSE frame by `SystemEvent::to_payload` (`merge_actor`) — same contract as the `TriggerGroup*` events — so the audit timeline can attribute who created/updated/deleted/enabled/disabled a trigger. `TriggerExecuted` is engine-driven and carries no `actor` (its raw payload is the wire shape: `trigger_id`, `last_run`, and `status` — `"ok"`/`"failed"`, the firing's outcome, added so a threadless trigger's last-run status surfaces on its panel row; `replay.rs` rebuilds `TriggerConfig.last_run_status` from it, and a legacy status-less event degrades to `None`). `TriggerCreated`/`TriggerUpdated` payloads may carry an optional **`plugin_id`** (ADR 0019) — set on triggers a *plugin* auto-registered from a shipped `triggers/<slug>/trigger.toml`; `TriggerConfig::from_created_payload` reads it (absent → user-created, never plugin-managed). Plugin install emits these (`engine::tools::plugins::resync_plugin_triggers`); uninstall emits a `TriggerDeleted` for every trigger carrying the plugin's id (`delete_plugin_triggers`).
- **Plugins (audit):** `PluginInstalled`, `PluginUninstalled`, `PluginInstallCanceled`, `PluginUninstallCanceled`. Aggregate = `plugin`, `aggregate_id` = the plugin `id`. All persisted, and `PluginInstalled` is reused for updates and reinstalls (no separate `PluginUpdated`). Its nested payload map (`payload.data.manifest.*`) carries `summary`, the raw `manifest`, `files` (every shipped `data/`-relative path), `installed_at`, `source_type`, optional `setup_thread_id`, and **`commit`**. That `commit` is the workspace-repo sha of the "Install plugin: …" commit. **`id` is at the top level**, `payload.data.id`, which `aggregate_id()` reads; an older row carries it only inside the raw manifest.

  There is **no `PluginModified` event**. A plugin's locally-modified state (the Plugins-list "Modified" badge) is **derived on read**, by diffing current on-disk content against `commit` (`engine::tools::plugins::registry::plugin_modification_status`). It surfaces as `modified` + `modified_paths` on the installed summary and the `MarketplacePlugin` catalog row. Self-healing: reverting an edit clears it. Legacy rows with no `commit` never read as modified.

  An update MERGES a local edit rather than overwriting it (`plugins::merge`), so the badge stays on afterwards. That rests on `commit` naming a byte-exact copy of what the plugin shipped. A merged path is staged from upstream's bytes, not the working tree (`core::commit_data_paths_with_overrides`); a second commit records the merge. Record the merge in the install commit and the NEXT update drops the patch as upstream's own content.
- **Plugin local changes:** `PluginLocalChangesMerged`, aggregate = `plugin`, `aggregate_id` = the plugin `id`, emitted right after its `PluginInstalled` when the install met a locally-edited file. Payload: `merged` / `conflicted` / `replaced` / `restored` (paths per outcome), `saved_paths`, and `commit` (the keep-local-changes commit). Everything in `conflicted` and `replaced` has a copy in `saved_paths`, under `data/artifacts/plugin-local-changes/` with a `.patch` sibling. Nothing in `restored` does, since a deletion has no content to keep. Persisted deliberately, even though the Modified badge beside it is derived: the badge recomputes from git + disk, where a merge cannot, since nothing on disk records which files merged. Each saved copy also gets an `ArtifactCreated` (`source: "plugin_update"`), which refreshes the Files list.
- **Plugin marketplaces (audit + list refresh):** `PluginMarketplaceRegistered` (payload `{marketplace_id, name, source, actor}`) and `PluginMarketplaceRemoved` (`{marketplace_id, actor}`). Aggregate = `plugin_marketplace` (its own, not `plugin`: a marketplace is the source a plugin can be installed *from*, and registering one installs nothing), `aggregate_id` = the `marketplace_id`. Both persisted. `Registered` is an **upsert** event: the id hashes the *canonical* source, so re-registering the same source rewrites the existing entry's `name` (and its raw `source` string, which can differ by a `.git` suffix or owner/repo casing while hashing the same) rather than adding a second one. So one variant covers a first registration and a rename alike, the same shape as `RepositoryAdded` and `McpServerRegistered`; a `Renamed` variant would misdescribe the source-only case, and the payload carries the resulting `name` + `source` so a reader sees what the marketplace is now. It fires on **every** registration call, not only ones that changed something, matching `McpServerRegistered` (a caller re-registering is asserting a state, not a delta). `RepositoryAdded` does suppress its no-op, but only because the engine re-registers the Lucidos source repo on every boot; nothing re-registers a marketplace automatically, so there is no per-restart row to suppress here. Emitted from inside `engine::tools::plugins::marketplaces`, the single write path for `data/config/plugin-marketplaces.json`, so both mutation surfaces announce by construction: the `/api/v1/plugins/marketplaces` HTTP CRUD (device `actor`) and the `plugins` tool's `register_marketplace` action (acting thread, `mode: Agent`). Removal is HTTP-only today; there is no remove tool. The registry commit ALSO emits its usual `DataFileWritten` audit (that is what carries the commit sha), the same audit-plus-entity pairing the `Artifact*` events have. These are what refresh the Plugins panel + Settings → Marketplaces live; before they existed only `DataFileWritten` fired, and the frontend ignores it outside `artifacts/`, so a registration or rename was invisible until a page reload.

## Column notes

**`thread_summaries.parent_callback_pending`** (BOOLEAN NOT NULL DEFAULT FALSE,
added as `parent_callback_sent` by
`20260402030859_add_parent_callback_sent.sql`, renamed and inverted by
`20260805123727_rename_parent_callback_sent_to_pending.sql`) is the child-side
fan-in marker. TRUE means the parent callback for this child's *current* run has
not been delivered yet. It is written TRUE by the spawn upsert and by the
revive/start helper, in both cases only for a row that has a parent; it is
cleared in-tx by the `ChildThreadCompleted` projection arm. Its job is to
collapse a coding-agent child's terminal storm (`CodingAgentIdled`, then
possibly `SessionEnded` / `ResponseFailed` / `ResponseCanceled`) into exactly
one completion card, which is why every read of it is `is_coding_agent`-gated. A
row with `parent_thread_id IS NULL` is always FALSE: a top-level thread owes no
parent a card. See ADR 0011.

**`thread_summaries.live_event_waits`** and **`live_event_wait_count`** are the
*event waits* the thread itself holds unresolved: which ones, and how many. The
list is JSONB NOT NULL DEFAULT `'[]'`
(`20260814142434_add_live_event_waits.sql`); the count is INT NOT NULL DEFAULT 0
(`20260806183944_add_live_event_wait_count.sql`). Each array entry is
`{wait_id, on, reason, expires_at}`, copied from the wait's `EventWaitStarted`,
mirroring the `EventWaitSummary` type in Rust and TS.

**One statement per projection arm writes both, and the count is DERIVED from
`jsonb_array_length` rather than incremented** (`event_wait_sql` in
`event_bus_projection_thread.rs`). The `EventWaitStarted` arm filters the array
by `wait_id` and then appends, so a replay converges rather than duplicating.
The three resolution arms are that filter alone.

Deriving is what makes the pair unable to disagree, and it retired the old
`GREATEST(0, ...)` floor: an array length cannot go negative. A resolution
naming a `wait_id` the array never held now moves neither column. It used to
decrement the count on its own, and such a resolution is emittable (a
hand-emitted row, a wait predating the backfill).

Unlike `blocking_descendant_count` neither is a roll-up: a subscription belongs
to the thread that registered it and nothing bubbles, so there is no ancestor
walk and no `propagate_*` counterpart. The list has one reader, the waiting
indicator's subscriptions section. The count has two: `count > 0` in
`resolveVisualStatus`, painting the same pulsing Waiting dot
`active_children_count` produces, and **`available_thread_actions`**, which
withholds Apply and Discard while it is non-zero (ADR 0106). A parked thread's
change is not final, so resolving it races the work still to come.

`is_blocking`, `is_attention_needing` and `display_section` still read neither,
so a subscribed thread stays non-blocking, non-attention-needing and archivable
(ADR 0049). Relaxing `is_blocking` is specifically unsafe: it is what stops an
ancestor cascade-archiving the thread, and that cascade emits `ChangeApplied`
per pending change.

Both are carried on `ThreadSummary` and on `ThreadAggregate`, and both exist
because the client cannot derive them. Its own `meta.liveEventWaits` fold covers
only a thread's LOADED events. So it was empty on a drawer row nobody opened and
empty again after a reload. Worse, nothing reconciled it, so a single missed
`EventWaitDelivered` left a resolved wait on screen with a live countdown until
the tab was closed. Each migration backfills from the unresolved
`EventWaitStarted` rows on a thread, and the later one re-derives the count so
the two agree from the start.

**`thread_summaries.compose_epoch`** (BIGINT NOT NULL DEFAULT 0, added by
`20260806003932_add_compose_epoch_to_thread_summaries.sql`) is the *compose
epoch* (`docs/glossary.md`): how many times a **submission** has consumed the
thread's compose slot. It is the write fence for `PUT /api/v1/threads/:id/compose`,
which takes the client's last-heard value and adds `AND compose_epoch = $n`, so a
write composed before a submission is refused with `412` (the body carries the
current epoch) instead of resurrecting the draft that submission consumed. An
absent value skips the precondition, permanent back-compat for a cached client
that predates the column.

It counts submissions, NOT writes, and that is what keeps the keystroke path
clear of it: every compose PUT between two submissions carries the same value, so
only a write straddling a submission can fail the check. The compose UPDATE never
moves it. Three projection arms do: `MessageReceived` (on its conflict arm, so a
message that CREATES the row leaves the epoch at 0), the coding-agent
`SessionStarted`, and the `UserQuestionAnswered` content match. `ThreadDiscarded`
deliberately does not, since its state guard already refuses every later write.
Carried on `ThreadSummary` and on the `ThreadComposeChanged` broadcast so every
device holds a value its next write can be fenced against. See
`docs/plans/2026-08-06-compose-write-ordering-after-send.md`.

**`thread_summaries.parent_thread_id`** is also the `parent` filter on
`GET /api/v1/threads/list` and `/threads/count`, matched with the usual
optional-filter idiom (`$n::uuid IS NULL OR t.parent_thread_id = $n`). Direct
children only, never the recursive ancestor CTE.

Timestamp is `created` (not `created_at`). `aggregate_id` is `text` (not uuid) — cast when joining: `aggregate_id = c.thread_id::text`. `thread_id` column is legacy; prefer `aggregate_id`. `payload` is `jsonb`.
