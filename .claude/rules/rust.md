# Rust Conventions

- **Error handling:** `Box<dyn std::error::Error + Send + Sync>` — no custom error types. **One blessed exception**: `LifecycleViolation` in `engine/thread_lifecycle.rs` carries structured fields (`event_type`, `thread_type`, `current_section`, `reason`) so the EventBus rejection path can fail-fast on a typed payload instead of parsing a string. New custom error types need the same kind of structural justification — generic "I want a typed error for this layer" is not enough; if the caller only ever formats the error into a string, use the boxed trait object. `api::error::ApiError` is NOT an error type in this sense — it's the HTTP response shape (`status` + `{"error": msg}` body) for `/api/v1` handlers, consumed structurally by its `IntoResponse` impl; axum handlers return `Result<_, ApiError>` instead of hand-rolling the `(StatusCode, Json)` tuple per file. Internal fallible code keeps using the boxed trait object and converts at the handler boundary.
- **Shared state:** `Arc<Mutex<T>>` for exclusive access, `Arc<RwLock<T>>` for read-heavy
- **Logging:** Always use `log!(...)` from `crate::lib` instead of raw `println!`/`eprintln!`. Format: `log!("[Module] message", args)` with `[Module]` prefix. Raw `println!`/`eprintln!` are reserved for: (1) inside the `log!` macro definition itself, and (2) user-facing CLI output that external tooling parses — `--version`/`-V` and `--help` are the canonical cases, where `log!`'s timestamp/pid/label prefix would break parsers reading stdout. Carve out a new exception only with the same justification (machine-readable stdout that callers depend on), and document the rationale at the call site.
- **Commit messages:** Conventional commits — `feat:`, `fix:`, `docs:`, `refactor:`, `chore:`
- **Path validation:** Always check for `..`, leading `/`, leading `\` before accepting user-provided paths
- **Serialization:** `#[derive(Serialize, Deserialize)]` on all API/event types, `#[derive(sqlx::FromRow)]` for DB types
- **Tests:** `#[cfg(test)]` modules colocated with source. Inline `mod tests { ... }` is the default; for large modules where tests dominate the file, lift them into a sibling file via `#[cfg(test)] #[path = "foo_tests.rs"] mod tests;` (or a sibling directory `foo_tests/` with one file per `mod` when there are multiple top-level test modules). Examples in tree: event_bus_tests.rs, context_tests/, thread_lifecycle_tests/.
- **`.ok()` / `let _ =` only for truly unrecoverable cleanup** (e.g. removing temp dirs). Never for operations whose failure the user should know about.
- **A probe that could not run is UNKNOWN, never a "no".** `git_cmd` returns `Err` for a spawn failure AND for its 30s timeout, and on a saturated host (an e2e run, a big rebuild) ordinary `rev-parse` calls really do take tens of seconds. So `git_cmd(...).map(|o| o.status.success()).unwrap_or(false)` is not a predicate, it is a coin flip that lands on "gone" exactly when the machine is busiest. Ask yes/no questions through **`git_answer` / `git_answer_with`** (exit status is the answer) or **`git_answer_when_ok`** (a non-zero exit is a failure, not an answer: `git status` is the canonical case), and collapse the resulting `GitAnswer` with **`or_unknown(true|false)`**, which forces you to name the fallback where a reviewer can see it. **Pick that side by asking which direction destroys something.** An unknown must never authorize deleting a worktree, deleting a branch, discarding a tree, force-checking-out over a working tree, moving a ref with no old-value guard, or resolving a change as an already-applied no-op. Prefer the direction that keeps the user's work and fails loudly later: a spawn that errors and says "resend to retry" costs a retry, a deleted working copy costs the work. The same rule applies to any string a git call yields (`unwrap_or_default()` turns an unresolved sha into `""`, and two empty shas compare equal). Every current site and its chosen default are tabulated in `docs/plans/2026-08-03-unknown-git-state-must-not-delete-worktrees.md`; this class emptied a live coding-agent worktree on 2026-08-03.
- **Failure-path cleanup deletes only what the failed attempt created.** A destructive git/filesystem op (`git worktree remove --force`, `git branch -D`, `remove_dir_all`) on an error/cleanup path must never run unconditionally — on a resume/recovery path the "cleanup target" is pre-existing state holding the user's committed work. Track what THIS attempt created (see `SpawnWorktreeContext::{worktree_created, branch_created}` + `git_ops::cleanup_failed_spawn`) and log every outcome; for "start fresh" retries, prefer `remove_worktree_and_optionally_delete_branch` (keeps any branch with unique commits). Three separate sites had this bug (2026-06-12); when fixing one instance of a pattern, grep for its siblings.
- **A session teardown never reclaims a worktree (ADR 0035).** Stronger than the rule above, and it is about *reclamation* rather than cleanup: reclaiming spent disk has exactly ONE owner, the background `WorktreeCleanup` worker, which weighs retention when nothing is racing it. A teardown must not do it even with a perfect gate, because a teardown frequently runs *because* something just went wrong, and it can be unwinding while the safety net relaunches a session into the very tree it would delete (that race destroyed a live worktree on 2026-08-03, hours after a timed-out probe destroyed another one through the same line). Two removals remain on the session path, and both delete something this attempt owns rather than reclaiming: an explicit user **Discard** (`discarded_worktree_removal`, still branch-checked, since Claude Code can `git checkout` inside its own worktree), and the Tier-3 **temp** merge tree behind `conflict_abort_deletes_temp_state`. Adding a third fails `the_completion_path_removes_only_the_two_worktrees_it_is_allowed_to`. Do not re-add one to reclaim disk: the deleted call never ran on the clean path anyway (a clean turn returns earlier, at the idle exit in `run_session/run.rs`), and Tier 0 reclaims the same bytes within the hour.
- **Never slice strings by byte index.** `&s[..n]` panics on multi-byte chars. Always use `s.floor_char_boundary(n)`.
- **API returns raw markdown, frontend converts to HTML.** No `markdown_to_html` on backend. Error responses use `[ERROR]` prefix.
- **A state change ANNOUNCES by default; not announcing needs a reason.** When you add a write to a table `core/announced_surfaces.rs` classifies as `Announced`, the write emits. "There is no variant for this yet" is a reason to ADD one, not to skip the event: a new `SystemEvent` is five match arms plus a `.claude/rules/db.md` row, while an unannounced change is invisible to the timeline, SSE and every trigger, permanently. `ExemptWriter` is the narrow exit, covering three shapes only: downstream of an emit, a cascade the parent event covers, or an observation rather than a decision. Its required `why` records that judgment. The MCP disabled-tools change took the event; the manifest-cache refresh beside it took the exemption.
- **ALL events go through EventBus.** `EventBus.emit()` is the sole entry point for event persistence. `EventStore::append()` and `append_thread_event()` have been deleted. Thread events use `BusEvent::Thread { .. }`, system events use `BusEvent::System(SystemEvent::...)`, and domain events (from `emit_event`) use `SystemEvent::DomainEvent { .. }` (persisted with the inner event_type, not "DomainEvent"). Never bypass EventBus to write directly to the events table.
- **Response termination uses the typed helpers.** Never construct `ThreadEvent::ResponseCanceled { .. }` or `ThreadEvent::ResponseAborted { .. }` directly — call `thread_events::emit_response_canceled` (cancel = user-driven, takes a `CancelCause`) or `thread_events::emit_response_aborted` (abort = system-driven, takes an `AbortCause`). The helpers force every site to declare *why* the response ended via the typed enum, and route the construction through one place so the cancel-vs-abort split stays honest. Exceptions stay direct and document why with a comment: (1) sites that need to observe the emit `Err` for per-thread logging — chat/recovery sweep, mod.rs shutdown sweep, settle_stuck_running_thread; (2) `runtime_helpers::make_terminal_event` — the lower-level factory the helpers themselves depend on.
- **Mutating endpoints stamp the actor.** Use `state.engine.event_bus.emit_user_system(&headers, &state.pool, "[Module] EventName", |actor| SystemEvent::X { …, actor }).await` from any axum handler that mutates state and emits a `SystemEvent`. The helper resolves the actor via `api::actor::user_actor_resolved`, wraps in `BusEvent::System`, and emits through `emit_or_log` so failures land in `[EventBus] [Module] EventName emit failed: …`. Use the lower-level `user_actor_resolved` + `emit_or_log` directly only for the cases the helper deliberately excludes: per-device handlers (body-supplied device id), cross-workspace handlers (use `build_message_origin` with a `CallerOrigin`), `BusEvent::Thread` emits, and handlers that need the `EmitResult` back. Engine-internal emits (state-machine side effects, scheduler tick, recovery) pass `None` and call `emit_or_log` directly. The lower-level `user_actor(&headers, device_id, device_label)` exists for callers that already have the label in hand. For new `ThreadEvent` variants prefer `EventMeta::with_actor(actor)`. The four change events carry per-variant `actor` (predates EventMeta path); leave as-is. For `SystemEvent` add `actor: Option<MessageOrigin>` as a `#[serde(default, skip_serializing_if = "Option::is_none")]` field on the variant. The actor flows into the event payload as a stable `actor` field — frontend reads it without translation.
- **What the AGENT wrote names which agent.** The bullet above says engine-internal emits leave the actor unset. An agent's own output is the exception: it stamps `EventMeta::authored_by(AgentParticipant::…)`, so two agents sharing a thread stay distinguishable (ADR 0150). `history.rs` reads it to give a *guest* its own speaker label. Get it wrong and the reasoner obeys a turn nobody sent, or agrees with itself. Stamp the AUTHORED event only, never the turn's shared request meta: `meta_with_cancel_actor` fills its slot only when empty, so a pre-filled one attributes the user's Stop click to the agent.
- **Dependencies: committed lockfile is authoritative; builds are `--locked` (ADR 0020).** Keep idiomatic caret/range versions in `Cargo.toml` (`serde = "1"`), NOT exact `=` pins — `Cargo.lock` pins the exact full tree. All build/test scripts pass `--locked`, so a build ERRORS on `Cargo.toml`↔`Cargo.lock` drift instead of silently rewriting the lock; commit both together. Change a version only via a deliberate `cargo update` you commit. (npm side: `npm ci`. See `.claude/rules/build-release.md` § Lockfile determinism.)
- **Database schema changes must be migrations.** Always create with `./scripts/new-migration.sh <description>` — it stamps the file with the real wall-clock second and bumps if the slot is taken. Never hand-pick the timestamp (placeholders like `120000` collide across parallel CC branches and crash the engine on startup with a `_sqlx_migrations_pkey` duplicate). Format: `YYYYMMDDHHMMSS_description.sql` in `crates/lucidos-engine/migrations/`. `build.rs` panics if two files share a version prefix. Never put ALTER TABLE in `init_schema`.

## Database

Lucidos uses **event sourcing** — the `events` table is the source of truth, with cached projections (`thread_summaries`, `notifications`) maintained by EventBus. Schema reference (tables, event types, column notes, query patterns) lives in `.claude/rules/db.md` — auto-loaded when editing `*.sql` or `migrations/**`.

- **"The last N seconds" over a DB timestamp is resolved in SQL, never from `Utc::now()` (ADR 0053).** `events.created` is stamped by Postgres, so `WHERE created >= $cutoff` with a cutoff the engine computed puts the host clock and the database clock on opposite sides of one `>=`. In dev both the workspace PG and `lucidos-pg-test` run in a Docker VM whose clock drifts, and once it drifts past the window EVERY row falls outside it: the query returns nothing and the caller reads that as "nothing happened". Pass a **duration** (`window_secs: i64`) and write `created >= now() - make_interval(secs => $n)`, so there is no timestamp parameter to fill in from the wrong clock. Same for anything derived for the caller to read: an age is `EXTRACT(EPOCH FROM now() - created)::bigint`, not `Utc::now() - row.created`. This has bitten twice (`pg_now` in `changes_projection_tests/helpers.rs`, then seven event-wait tests reporting "0 matches" on 2026-08-07); the ADR names the two sites deliberately left alone.

## Timezone Handling

UTC in database, user timezone in UI. Cron: 6 fields — `second minute hour day-of-month month day-of-week` (e.g., `0 0 8 * * *` = 8am daily). Stored with user timezone for DST. IANA format (e.g., `Europe/Oslo`). Convert: `utc_time.with_timezone(&user_tz)`.

## HTTP Usage Rule

Only conversational data goes through HTTP API. DB access, vector search, embeddings, file ops stay in-process.

## Intra-host scheme — never hardcode `http`/`https`

An HTTP call between co-located Lucidos processes (engine → gateway control API, gateway ↔ engine, any `127.0.0.1` hop) MUST resolve its scheme through **`net_config::tls_scheme` / `tls_scheme_from` / `peer_scheme_order`** (the constants `SCHEME_HTTP` / `SCHEME_HTTPS`) — never a hardcoded `http://` or `https://` in the URL. A process serves TLS iff **both** `LUCIDOS_TLS_CERT` and `LUCIDOS_TLS_KEY` point at non-empty paths: **dev keeps the certs → `https`**; the **packaged gateway strips them → `http`** (see `crates/lucidos-gateway/src/stack.rs` + `crates/lucidos-app/src/desktop.rs`, and the dev-vs-packaged table in ADR 0014). For a call to a peer whose scheme *should* match ours but might not, use `peer_scheme_order()` — it puts the resolved scheme first and the other protocol second, so a mismatch still connects (supports both). A self-signed dev cert on a loopback hop is accepted with `reqwest`'s `danger_accept_invalid_certs(true)` + `no_proxy()`, matching the gateway's `build_health_client` and the dev scripts' `curl -sk`.

A hardcoded `http://` to the `https` dev gateway is exactly the recurring bug this rule prevents — it surfaced as `gateway restart request failed: error sending request for url` on *Switch to new version* (`restart_via_gateway`). The scheme decision lives in **one place** (`net_config`); resolve it there, don't re-derive from `LUCIDOS_TLS_*` inline.

## API URL Conventions

**Every HTTP route lives under `/api/v1/`.** No exceptions — no `/api/foo` shortcuts, no unversioned routes. The engine mounts a single router at `/api/v1` (see `create_router` in `crates/lucidos-engine/src/api/mod.rs`); a request to `/api/foo` returns 404. When you add a new endpoint, define it relative to that mount (`/health`, `/threads/list`, `/foo/bar`) — the `/api/v1/` prefix is stamped on once by the nest, not repeated per `.route()`.

Frontend callers in `crates/lucidos-app/src/api/client.ts` build URLs from a single `const API = ${API_BASE}/api/v1` so the version cannot drift per-function. SDK callers (`packages/lucidos-sdk/src/`) pass *suffix-only* paths (`request('/threads/list')`); the `/api/v1` prefix is stamped inside `_fetch.ts` (`API_V1` constant + `apiUrl()` helper). When you need a full URL for `EventSource`, `<script src>`, or anchor hrefs, use `apiUrl('/events')` rather than concatenating manually. Engine-internal callers (e.g. `crates/lucidos-engine/src/engine/http/workspace_client.rs` reaching across workspaces) hit the target's `/api/v1/...` directly — no engine code should ever emit a `/api/` URL without the version.

Docs (`system-knowhow/**`, `docs/**`, comments in code) reference routes by their full path including `/api/v1/`. A doc that says "POST /api/foo" is wrong — the route either is `/api/v1/foo` (fix the doc) or doesn't exist.

Prefer query params: `/apps?commit=abc123`, `/app?id=habit-tracker`.

## Apps — Event APIs

When changing event system, update all 5 surfaces:
1. LLM tool definitions: `llm/tools/`
2. LLM tool handlers: `engine/tools/mod.rs`
3. App UI JS API: `api/app_ui.rs`
4. HTTP API handlers: `api/history.rs`
5. System prompt: `engine/chat/process/system_prompt.rs`

LLM event tools: `emit_event(event_type, payload)`: PascalCase past tense, payload must include `summary`. `query_events(event_id?, event_type?, thread_id?, since?, until?, limit?, byte_limit?)`: newest first, `limit` default 50 and max 200, `byte_limit` default 128 KB and max 512 KB. `event_id` resolves ONE event by primary key, accepting the `evt-<32 hex>` address every tool result states. It errors rather than returning an empty window when nothing matches. `thread_id` takes a uuid, or `current` / `this` for the calling thread. The alias resolves from the tool-execution context, so it exists on the LLM tool only: the HTTP and SDK surfaces have no ambient caller.
