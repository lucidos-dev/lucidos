# Glossary (dev)

Internal terms used in the Lucidos codebase, PRs, design docs, and CC sessions. Extends [`system-knowhow/glossary.md`](../system-knowhow/glossary.md) — read that first for user-facing terms (app, artifact, intent, knowhow, plugin, trigger, thread, event, …) and the user-facing advanced-coding-agent terms (Apply, change, Claude Code, coding agent, coding-agent thread, external-repo coding-agent thread, hardening). This file only adds dev-internal concepts the workspace LLM doesn't need.

One term, one definition. When prose anywhere in the repo names a term below, it uses *this* meaning — never a synonym. If you're tempted to write *child thread* for the transitive *sub-thread* concept, *coding agent session* for *agent session*, or *cmd thread* for *coding-agent thread*, use the canonical word.

If a needed concept genuinely isn't in either glossary, add it here (if dev-only) or to `system-knowhow/glossary.md` (if user-facing) in the same change.

## Terms

### Account pin
The `CLAUDE_CONFIG_DIR` (provider/account) a *coding-agent thread* is permanently bound to — the config dir its **first** session was created under. Resolved by `lookup_pinned_cc_config_dir` (the earliest recorded `claude_config_dir` across the thread's `CodingAgentSettingsChanged` / `CodingAgentIdled` events) and re-injected on *every* later spawn (resume, fresh, post-stale-resume retry, recovery), so a live `CLAUDE_CONFIG_DIR` toggle change never moves an existing thread to another provider — only a thread's very first turn adopts the live toggle (and thereby establishes the pin). The auto-detected resume session id is likewise scoped to the pinned account (`lookup_latest_cc_session_id_for_config_dir`), so a thread that a mid-thread flip mis-recorded onto another account still resumes the session belonging to its original account. Claude-Code-specific (Codex records no config dir → no pin). See `crates/lucidos-engine/src/engine/agent_session/resume.rs` + `run_session/run.rs`.

### Actor
The originator of an event — who or what caused it. Captured on persisted events as `actor: Option<MessageOrigin>`. Set by the mutating HTTP handler via `api::actor::user_actor_resolved(&headers, &state.pool, device_id_override).await`; engine-internal emits pass `None`. The frontend reads it raw to render the actor-chip popover; *ActorMode* derived from `MessageOrigin` drives the UI label (Lucidos Agent / Lucidos Engine / device name).
See also: `.claude/rules/rust.md` § "Mutating endpoints stamp the actor".

### ActorMode
The request-initiation mode — `Human` / `Agent` / `Engine`. Drives the UI actor-chip label via `mcp_client_name(ActorMode)`: `Human` → device label, `Agent` → `"Lucidos Agent"`, `Engine` → `"Lucidos Engine"`. Carried on the `Api { mode }` and `Workspace { mode }` `MessageOrigin` variants so SDK callers and cross-workspace requests can declare themselves explicitly; defaults to `Human` for back-compat. Distinct from *MessageOrigin* itself: ActorMode is the live-request classification; MessageOrigin is the persisted origin record.

### Agent session
The subprocess + worktree pairing managed under `crates/lucidos-engine/src/engine/agent_session/`. Generic across *CodingAgent* variants (the runtime map in `engine_impl.rs:655` is keyed by `CodingAgent`). When the subprocess is *Claude Code* specifically, call it a *Claude Code session* (see entry; or just *CC session* in conversation). Auto-resumes on engine restart unless the branch is already merged. Replaces the older "CC session" term, which baked the product name into the concept.

### Phantom session
An `agent_sessions` entry with no run loop behind it. `run_session` inserts the entry and removes it on every *completion* path, but a run future that is **dropped** rather than polled to completion (a cancelled caller, an aborted task) runs none of those removals — so the entry survives with `process_exited == false`, which only the loop ever sets. Membership in the map is therefore not liveness; **`AgentSession::is_live()`** is (`!process_exited && !msg_tx.is_closed()` — the receiver is owned by the run future, so the channel closes the moment the loop is gone, with no cleanup required). Every liveness reader goes through it. A phantom is also *transient*: `SessionEntryGuard` (`run_session/entry_guard.rs`) reaps the entry on drop — identifying its own by `msg_tx.same_channel`, so a recovery hand-off's replacement survives — and settles the thread with `ResponseAborted{cause: SessionDropped}` unless the engine is shutting down. Named for the 2026-07-28 incident where one fooled three readers at once (worktree cleanup, the chat follow-up fast path, and the resume guard), wedging a thread on "A coding agent is already running for this thread" with no subprocess anywhere on the box.

### Always-on engine service
In a packaged macOS desktop build, the *Workspace gateway* runs as a persistent launchd **LaunchAgent** (`~/Library/LaunchAgents/com.lucidos.engine.plist`, `RunAtLoad` + `KeepAlive`), independent of any window — so triggers, scheduled tasks, *agent sessions*, and mobile push keep running headless in **every** registered workspace after the UI is closed. The desktop **service** role (`Lucidos --service`, run by launchd — `run_service` in `crates/lucidos-app/src/desktop.rs`) spawns + supervises the standalone **`lucidos-gateway`** binary on the *stable gateway port*; the gateway in turn owns one shared Postgres cluster, provisions one database per workspace, and spawns one `lucidos-engine` per workspace (by path via `LUCIDOS_ENGINE_BIN`). The **client** role (the GUI app — `launch`) installs/bootstraps the agent, waits for `/~/api/v1/health`, then points the window at a workspace (`/<slug>/`) or the picker (`/~/`). Closing the window (red X / Cmd+W / Cmd+Q) leaves the service running — the client uses a **menu-bar (tray) model** and stays resident in the menu bar; only the explicit **Quit and Stop Background Service** action (menu-bar tray + app menu, `launchctl bootout`) stops it (tearing down the gateway *and* its spawned engines). Mobile devices reach the gateway over Tailscale (`serve`, tailnet-private — see **Settings → Mobile Access**, `crates/lucidos-app/src/mobile.rs`). Supersedes the single-engine-on-the-stable-port model (ADR 0014 refines 0013 refines 0012). Dev runs the same gateway (`scripts/web-dev.sh`), Docker-backed shared Postgres; `LUCIDOS_NO_GATEWAY=1` falls back to the legacy single-engine launcher.

### Stable gateway port
The fixed TCP port the **packaged gateway** binds (default `5252`) so the mobile connect URL is constant across restarts — as opposed to the random free port the legacy single-engine launcher used. The gateway binds all interfaces (`Ipv6Addr::UNSPECIFIED`), so it's network-reachable once the port is stable; in the packaged build the per-workspace engines it fronts bind **loopback only** (the engine's default since the loopback-bind security fix; `LUCIDOS_BIND_LOOPBACK=1` is also set as its `behind_gateway` signal) and Postgres stays loopback-only too — the gateway is the sole network-facing surface. (Dev differs — see *Workspace gateway* and ADR 0014 "Dev runtime topology": the engine binds its own user-facing port directly and the **one shared dev gateway** binds **`5251`** by default (override `LUCIDOS_DEV_GATEWAY_PORT`) — one below the packaged `5252`, so a dev gateway and an installed `Lucidos.app` coexist out of the box. Loopback-only is packaged-only.) Consumed by the gateway as `LUCIDOS_API_PORT`.

### Workspace gateway
The standalone headless reverse-proxy + control plane — the **`lucidos-gateway`** binary (`crates/lucidos-gateway/`, ADR 0014), with **no dependency on `lucidos-engine`** so the only network-facing process links proxy + supervise + registry code, not the engine's heavy core. Runs as the *Always-on engine service* (launchd on the *stable gateway port*; also used in dev). Owns the workspace registry (`<app-data>/config/workspaces.json`: stable slug → {display name, dir, engine port, optional legacy `database_url`, **auto-start flag**}; **membership is durable** — a workspace stays registered, and thus listed in the picker, until explicitly deleted), provisions one database per workspace in a shared Postgres cluster (`lucidos_<slug>`) and supervises that workspace's engine (spawned by path via `LUCIDOS_ENGINE_BIN`). A legacy `database_url` is a migration source only: if the shared database is missing, the gateway/dev launcher dumps/restores the old per-workspace `lucidos` database, verifies the shared database, re-points the engine to it, and leaves the old cluster intact until the explicit decommission script removes it.

On boot the gateway **re-adopts** already-running engines, **spawns** the *auto-start* workspaces, and leaves the rest **stopped** (listed but not running; **lazy-started** on the first proxy hit / explicit open). It reverse-proxies `/<slug>/*` to that workspace's engine as a **pure streaming forward**: it strips `/<slug>`, adds an `X-Forwarded-Prefix: /<slug>/` request header, and forwards the response **untouched** (body streamed, compression + SSE intact, no HTML rewrite — the engine stamps `<base href>` / re-scopes app refs from the forwarded prefix instead). The PWA manifest is the deliberate exception: gateway-served picker and workspace manifests use `scope: "/"` so a PWA installed from the stable port (`5252` packaged, `5251` dev) can switch between `/<slug>/` workspaces without opening a separate browser context. All gateway-owned surface lives behind the reserved *sigil namespace* `/~/`: the workspace **picker** (served from `LUCIDOS_STATIC_DIR` with `<base href="/~/">`), the control API (`/~/api/v1/control/*`), and health (`/~/api/v1/health`). `/` is **smart**: a sole workspace → redirect into it; otherwise the picker. A single client (Tauri window or web/PWA over one Tailscale `serve` mapping) addresses multiple workspaces concurrently by path prefix.

Postgres backends are shared-cluster backends: **Docker** (dev, one `lucidos-pg-shared` container/volume) or **Embedded** (packaged, one bundled cluster under `<app-data>/pgdata`). Workspace delete drops that workspace's database and leaves the shared cluster running for peers. Failure-isolated: a stack that fails to boot or crash-loops shows as `unhealthy` in the picker (start / stop / retry / delete, plus the per-workspace *auto-start* toggle) without taking down the gateway or peers; supervision is health-probe based with a boot grace, crash backoff, restart cap, and re-adoption of already-running engines across a gateway restart (engine-statelessness). The frontend is base-path-aware (`crates/lucidos-app/src/utils/basePath.ts`, reading the stamped `<base href>`) so one bundle serves under `/`, `/<slug>/`, and `/~/`; the service worker scopes per prefix. **Engine bind differs by build (ADR 0014 "Dev runtime topology", normative):** *packaged* engines bind **loopback-only** (the engine's default; `LUCIDOS_BIND_LOOPBACK=1` is also set as the `behind_gateway` signal) so the gateway on the stable port is the sole network-facing surface; *dev* engines (`web-dev.sh`, `LUCIDOS_GATEWAY_ENGINE_LOOPBACK=0`, `LUCIDOS_BIND_ALL=1`) bind **all interfaces on the user-facing port** (5173+offset) so `https://localhost:5173/` reaches the workspace app DIRECTLY (base `/`) *in addition* to `/<slug>/` through the ONE shared dev gateway on its fixed port (default **5251**; override `LUCIDOS_DEV_GATEWAY_PORT` — one below the packaged 5252 so both coexist) — the gateway then proxies/probes the dev engine over https. Loopback-only is packaged-only; do not apply it to dev. (Dev's gateway data — registry, pidfile, log — is machine-global under `$HOME/.lucidos/gateway`, NOT per-workspace, so one gateway fronts every workspace launched from any `web-dev.sh`.)

### Sigil namespace
The single reserved path prefix — `~` — under which **all** *Workspace gateway*-owned surface lives: `/~/api/v1/health`, `/~/api/v1/control/*`, and the picker + its bundled assets (`/~/assets/*`, `/~/sw.js`, …). Introduced by ADR 0014 to make the first path segment unambiguous between a workspace and the gateway's own root files **without a growing reserved-word list**: the only rule is that a workspace slug can never start with the sigil — and slugs are `[a-z0-9-]`, so that's automatic (`gateway::registry::slugify`/`is_valid_id`). Replaces 0013's `/ws/<id>/` prefix (which kept workspaces in their own namespace) by flipping it: workspaces get the bare `/<slug>/` and the gateway retreats behind `/~/`.

### Boot splash
The brand cover shown while a workspace comes up: the gradient wash, the white Lucidos mark, and one status line under it. **One splash, rendered by two documents.** The *Workspace gateway* serves it as a 503 page while the engine starts (`proxy.rs::splash_page_html`, labelled with the current *boot phase* or a *boot failure*); the app document then serves it inline in `crates/lucidos-app/index.html`, painted on the first frame before the bundle loads. Both live at the SAME url, so a cold launch crosses from one to the other mid-boot and any difference between them reads as the brand jumping.

They cannot differ, because there is only one definition: index.html holds the stylesheet and the mark markup (between its `lucidos-boot-splash-css` / `lucidos-boot-splash-mark` markers), and the gateway `include_str!`s that file and lifts both out at compile time, overriding only what is genuinely its own (a wrapping status line, no breathe under its meta-refresh, a tappable escape link, its own label). Two rules follow from the shared-across-documents shape. Every length in it is **px, never rem**: the app's root font-size is `var(--user-ui-scale)` and the gateway's is the browser default, so one rem value paints at two sizes (the 2026-07-31 seam bug, where the mark grew from 240px to 330px at 137.5% scale). And the built mark is **handed over** rather than rebuilt: a per-tab `sessionStorage` flag tells the next document the mark is already standing on screen, so it is revealed once per boot instead of re-revealing on every gateway refresh and again on the swap (`boot-splash-formed`; the app document consumes the flag as it reads it). Not to be confused with the iOS `apple-touch-startup-image` PNGs, which are solid-color launch images the OS draws before any document exists.

### Boot phase
A named step of a workspace's cold boot, rendered as the label on the *Workspace gateway*'s "Workspace starting…" 503 boot splash (`crates/lucidos-gateway/src/proxy.rs::splash_page_html`) so the wait is legible instead of opaque (ADR 0014 §11). The `BootPhase` enum (`crates/lucidos-gateway/src/boot_phase.rs`) maps each phase to a human label; the gateway holds the current phase per workspace in an in-memory `boot_phases` map (cleared when the workspace goes healthy or is stopped, so a later cold open starts clean). Two producers feed it: **gateway-observed** phases the gateway sets directly (`provisioning-database`, `starting-engine`), and **engine-reported** phases the engine POSTs to `/~/api/v1/control/workspaces/:id/boot-phase` during its own startup — before its HTTP server is up — via best-effort, fire-and-forget telemetry (`crates/lucidos-engine/src/boot_report.rs`: `migrating` and `recovering`). The embedding model (which powers vector memory) is deliberately NOT a boot phase — it loads in the background and never blocks boot (see `memory::EmbedderSlot`). The kebab-case wire values are the cross-layer name root (`BootPhase::from_wire`); an unknown value is tolerated and ignored (so a retired phase like the former `downloading-memory-model` degrades to keeping the previous label). Not persisted, not an *event* — pure boot-window UI state. A boot that *dies* rather than progresses is a **boot failure**, not a phase.

### Boot failure
A **terminal** startup failure an *engine* reports to the *Workspace gateway* on its way out, because no retry can fix it — the canonical case being a database migrated by a NEWER Lucidos than the running binary, which is what an app downgrade produces (sqlx `MigrateError::VersionMissing`). Distinct from a *boot phase* in three ways: it describes death rather than progress, it is **awaited** rather than fire-and-forget (`crates/lucidos-engine/src/boot_failure.rs` — the process exits immediately after, so `boot_report`'s detached task would never run), and it **changes gateway behavior** rather than being pure telemetry. The engine classifies the failure and builds the user-facing sentence itself (only it knows which migrations it carries), naming the size of the version gap but never a target version to install — migrations carry no app-version tag, so the newest unknown migration id cannot be mapped back to a release. Posted to `/~/api/v1/control/workspaces/:id/boot-failure`; the gateway stores it per workspace, renders it on the boot splash with **no auto-refresh** plus the escape link (`proxy.rs::failed_page`), sets it as the stack's `last_error` (so it doubles as the picker's health-dot tooltip), and **stops auto-respawning** — five pointless cold boots only delayed the message by ~30s in the 2026-07-29 downgrade incident. First report of a boot episode wins, so the migration site's specific message is never overwritten by `main`'s generic backstop. Cleared when the workspace next boots healthy or is stopped, never when it is marked `Unhealthy` — that is the state the message exists to explain. Not persisted, not an *event*.

### Aggregate
The grouping a persisted event belongs to — a `text` column on the `events` table. Determines how the EventBus routes the event and which projection (if any) materializes from it. Today's values: `"thread"`, `"app"`, `"trigger"`, `"artifact"`, `"plugin"`, `"change"`, `"notification"`, `"preference"`, `"presence"`, `"device_presence"`, `"device"`, `"repository"`, `"credential"`, `"model"`, `"oauth_account"`, `"data_file"`, `"pinned_app"`, `"ops"`, `"domain"`. **Not** a per-event-type discriminator — multiple variants share the same aggregate. Set by `SystemEvent::aggregate(&self)` in `event_bus_system_event.rs`.

### Aggregate_id
The `text` column on `events` that ties events together inside an aggregate. For threads, this is the thread UUID as text. **Always cast when joining**: `aggregate_id = c.thread_id::text`. The older `thread_id` column on `events` is legacy; prefer `aggregate_id`.
See also: `.claude/rules/db.md`.

### Blocking descendant
Internal name for the predicate in `is_blocking` (`engine/thread_lifecycle.rs`): a thread whose state currently makes it unsafe to cascade-archive its ancestor. Materialized as `thread_summaries.blocking_descendant_count` and maintained by `propagate_blocking_change` (`engine/event_bus_projection.rs`). User-facing definition lives under *Blocking descendant* in `system-knowhow/glossary.md`.

### blocking_descendant_count
`thread_summaries` column (`INT`, default `0`) holding the rolled-up count of a thread's *blocking descendants* (transitive). Maintained by EventBus; consumed by `available_thread_actions(..., descendants_block_archive: bool)` via `count > 0`.

### Attention-needing descendant
Internal name for the predicate in `is_attention_needing` (`engine/thread_lifecycle.rs`): a thread whose state requires user attention to progress — `WaitingForUserAnswer`, or an in-workspace *coding-agent thread* with pending *changes*. Strict subset of *blocking descendants* — drops the `Running` arm. Running threads are delegated work; attention-needing threads are pending user action — both render in the merged *Current* section, distinguished by the per-row status icon (running) vs. the attention badge / filter (your turn). Materialized as `thread_summaries.attention_descendant_count`, maintained by the same `propagate_blocking_change` walk that maintains the blocking count. Relationship: `is_blocking = is_attention_needing OR status == Running`.

### attention_descendant_count
`thread_summaries` column (`INT`, default `0`) holding the rolled-up count of a thread's *attention-needing descendants* (transitive). Maintained by EventBus alongside `blocking_descendant_count`; consumed by `display_section(..., has_attention_descendants: bool)` via `count > 0` to bubble the ancestor chain to the *Current* section when any descendant needs user attention, even if sibling descendants are still running.

### available_thread_actions
The DB-derivable per-thread action-availability core in `engine/thread_lifecycle.rs` (renamed from `resolve_actions`). Pure function over `thread_summaries` facts — `thread_type`, `status`, `stored_section`, `has_pending_changes`, `descendants_block_archive`, `has_unsent_draft`, `is_saved` — returning the available `Action`s in cascade order: `[DiscardDraft?, Discard?, Apply?, Archive?, Unsave|Save]`. Single source of truth on BOTH sides: codegen'd to TS (`generated/thread-lifecycle.ts`, contract-tested) so the frontend buttons derive from it, AND called server-side via `api::threads::available_thread_actions_for` to guard the mutating HTTP handlers (archive / apply / discard / save / unsave) — a stale frontend or raw API caller can't invoke an action the user couldn't currently take. Verb seam: `available_*` reads only DB-derivable facts; the frontend's *resolveThreadActions* layers in client/UI state.

### Bg-bash wait (retired)
A retired concept. The engine used to refuse `ChangeProposed` at idle while a CC background bash task was still running (`may_touch_change_state_at_idle`'s bg-bash gate), surfacing a `thread_summaries.coding_agent_bg_bash_pending` column → a "CC waiting on background tasks" banner with no Apply button until a ~5-minute `BgBashWakeRequested` nudge fired. **Removed** (2026-05-29): the wait was worse than the rare wasted re-harden it prevented, and it wedged permanently when CC verified bash completion via a shell `ps` check instead of `TaskOutput` (the in-memory tracker never saw the drain). The change now proposes the instant CC idles regardless of background bash; correctness is covered by *harden-at-apply* (an un-hardened change re-runs `/harden`, tests included, before it can merge), and app/external changes accept the small risk. The gate, the `CCInternalBgBashTracker`, the timer, the `BgBashWakeRequested` event, the column, and the `display_section`/`available_thread_actions` (then `resolve_actions`) `bg_bash_pending` params are all gone. The `CodingAgentIdled.bg_bash_pending` event field is kept as recorded history but no longer projected. Threads wedged by the old gate auto-recover at boot via `propose_held_back_changes_on_startup` (re-proposes any idle CC thread with a committed diff but no proposal).

### BusEvent
The wrapper enum the EventBus routes. Two variants: `BusEvent::Thread { .. }` (per-thread, becomes a *ThreadEvent*) and `BusEvent::System(SystemEvent)` (workspace-wide). Every emit goes through one of these — never bypass to write directly to the `events` table.

### Capability parity manifest
The single source of truth (`crates/lucidos-engine/src/capability_manifest/`) for which **agent surfaces** expose each capability — the LLM tools, the `lucidos` CLI, and the JS SDK (UI/HTTP are the substrate). Each *domain* declares its operations once plus domain-level `llm`/`cli`/`sdk` flags; from that one declaration the grouped LLM `ToolDefinition` is built in-crate, the CLI subcommand module is generated into `crates/lucidos-cli/src/generated/`, and the SDK capability table into `packages/lucidos-sdk/src/generated/`. Drift is a build failure: staleness tests (mirroring `navigate_targets_codegen`) fail `cargo test` when a generated file falls behind, the grouped handler's recognised-action set is checked against the manifest, and a Vitest test checks the SDK facade. Introduced to stop the agent-facing surfaces silently lagging UI/SDK/HTTP — see `docs/adr/0018-capability-parity-manifest.md`. Models *declared parity* (per-capability target surfaces), deliberately not blanket N×N parity.

Each `Operation` carries the wire details (method, path, `args` with type/location) plus three knobs that let one declaration serve surfaces whose shapes diverge: **per-op surface overrides** (`llm`/`cli`/`sdk` as `Option<bool>`, `None` inherits the domain — e.g. trigger `pause`/`resume` are LLM-only, app `update`/`delete` are CLI-only); a raw **`llm_schema`** (a JSON properties object used verbatim for the grouped tool when the LLM-facing shape differs from the HTTP `args` — e.g. a trigger's `cron` string|array shorthand vs the HTTP `cron_expressions` array, or omitting a context-injected `device_id`); and **`llm_alias`** (the retired flat tool name an operation supersedes — the grouped handler maps `action` → legacy name and delegates to the existing per-verb handler, and the legacy name still resolves to the domain so cached prompts/threads keep working). `ArgType::Json` expresses complex args (objects/arrays) that scalar `Str`/`Int`/`Bool` can't — the CLI takes them as `--flag '<JSON-STRING>'` parsed onto the body.

### Tauri capability
An entry in `crates/lucidos-app/capabilities/*.json` (or built at runtime by `desktop::gateway_capability`) granting a set of **Tauri permissions** to named webviews on a named origin — the ACL that decides whether an `invoke` from the desktop app's page is allowed to reach a command at all. **Unrelated to the *capability parity manifest* above**, which is about which agent surfaces expose an engine operation; the two senses of "capability" collide only in the word. Three parts matter: `permissions` (plugin ones like `core:default`, plus the app's own, declared in `crates/lucidos-app/permissions/`), the origin (`local` for the Tauri app URL, `remote.urls` for URLPattern-matched HTTP origins), and the scope — always `webviews`, never `windows`, because a window entry enables the capability on *every* webview of that window including the `url-preview-*` previews of third-party sites. Since tauri 2.11 a page on a non-local origin is `Origin::Remote` and ACL-checked, which is why the packaged client — whose window is navigated to the gateway — needs an explicit remote capability pinned to its resolved port. See `docs/adr/0028-the-packaged-window-is-a-remote-origin.md`.

### Claude Code session
The *agent session* when its *coding agent* is *Claude Code*; the sibling term for `CodingAgent::Codex` is *Codex session* (see entry). Often shortened to *CC session* in conversation, comments, and commit messages. Prefer *agent session* when the discussion is agent-agnostic (the runtime map, the spawn dispatcher, recovery semantics that apply to any *CodingAgent*); reach for *Claude Code session* (or *CC session*) only when the behavior is CC-specific — `--resume` flag semantics, the `/harden` gate, the stop-reminder hook, the `cc_session_id` field on interception events. No extra mechanics beyond *agent session*; same subprocess + worktree pairing.

### Codex session
The *agent session* when its *coding agent* is *Codex* (`CodingAgent::Codex`, `CodexRuntime` in `crates/lucidos-engine/src/runtime/codex.rs`). Two drivers behind one runtime, selected by `LUCIDOS_CODEX_PROTOCOL` (ADR 0005): the default **app-server driver** (`runtime/codex_app_server.rs`) holds ONE persistent `codex app-server` child per session speaking line-delimited JSON-RPC over stdio — `thread/start` / `thread/resume`, `turn/start` per input, real per-token streaming via `item/agentMessage/delta`, graceful `turn/interrupt`, and approval requests bridged onto the engine's PermissionCard flow (`approvalPolicy: on-request`); the **exec escape hatch** (`LUCIDOS_CODEX_PROTOCOL=exec`, `runtime/codex.rs`) runs one `codex exec --json` child per turn, resuming via `codex exec resume <thread_id>`, non-interactive with the sandbox as the only guard. Both share the Codex thread id (rides the same `cc_session_id` plumbing CC's session id uses — the two protocols read the same on-disk rollout, so a thread can switch protocols between sessions), the `--sandbox workspace-write` profile (network on, plus `CodexConfig.sandbox_writable_roots` — the worktree's shared git dir and the workspace's `data/` tree, without which `lucidos data write` to the parent workspace fails with `EPERM`; ADR 0004 §4), and the `lucidos` MCP server exposing `ask_user_question` (QuestionCards work on both). No slash commands / skills. Tool activity surfaces as Codex item types (`command_execution`, `file_change`, `mcp_tool_call`, `web_search`, `todo_list`) on the same `CodingAgent*` events.

### Close cascade
The progressive-close behaviour: each invocation resolves EXACTLY ONE close *layer* for the focused thread — draft (confirm-discard the unsent compose draft) → change (Apply / Discard / Cancel choice) → archive — re-running *resolveThreadActions* each time so resolving one layer surfaces the next (stateless re-eval; no cursor, no "cascade in progress" flag). `nextCloseLayer` picks the front-most layer, `runCloseCascade` invokes it; in-flight apply/discard/archive gate it to a no-op (the async bridge that keeps stateless re-eval honest). Driven by the per-thread buttons (each click resolves its own layer) and the `closeThread` keybinding (default `Ctrl/Cmd+Shift+W`) — a *keybinding registry* entry dispatched generically via `matchShortcut` / `SHORTCUT_ACTIONS` in `useKeyboardShortcuts.ts` and rebindable in Settings → Keyboard Shortcuts. Shift-modified so plain `Cmd/Ctrl+W`, the browser's reserved tab-close, is left alone (sibling of the `Ctrl+Shift+O` new-thread chord). Distinct from *Escape*, which is non-destructive and never triggers it.

### CodingAgent (enum)
The Rust enum representing which *coding agent* (the user-facing role, see system-knowhow glossary) is driving a session. Two variants: `CodingAgent::ClaudeCode` (the `claude` CLI, `ClaudeCodeRuntime`) and `CodingAgent::Codex` (the OpenAI `codex` CLI, `CodexRuntime`). Wire/DB values are kebab-case (`"claude-code"` / `"codex"` — `as_str()` and serde share the root); `CodingAgent::parse` defaults unknown/NULL to `ClaudeCode` for legacy rows. Replaces the older `AgentKind` enum, whose name didn't make the scope explicit. The engine's `agent_runtimes` registry is keyed by this enum, so adding a coding agent is variant + runtime impl + registration. A thread's backend is chosen at first send, persisted on `SessionStarted.coding_agent` → `thread_summaries.coding_agent`, and locked (no mid-thread flips — the other backend has no session to resume).

### Command checkpoint
The `ReversibleDanger`-lane snapshot/undo (ADR 0002, Phase 4) in `engine/git_ops/checkpoint.rs`. Before an in-workspace destructive command runs, `create_command_checkpoint` snapshots the whole working tree (tracked + untracked, respecting `.gitignore`) onto `refs/lucidos/command-checkpoints/<id>` via a non-invasive `git add -A` + `write-tree` + `commit-tree` through a throwaway `GIT_INDEX_FILE` (the repo's real index/working tree are never touched). The guard then emits `CommandCheckpointed`. `LucidosEngine::undo_command_checkpoint` (HTTP `POST /api/v1/command-checkpoint/undo`) runs `restore_command_checkpoint` (`read-tree` + `checkout-index -a -f` through a throwaway index), deletes the ref, and emits `CommandCheckpointReverted`. Documented limit: undo restores deleted/overwritten files but does NOT remove files the command newly created. User-facing concept: *command checkpoint* in `system-knowhow/glossary.md`.

### Command classifier
The static, deterministic fast-path of the *command guard*: `static_classify(tool_name, &input)` in `engine/command_guard.rs`, which returns a `StaticVerdict` — either `Settled(RiskLane)` or `NeedsJudge(JudgeInput)`. It settles the two ends deterministically: the catastrophic deny-list (recursive root/home delete, fork bomb, disk format/overwrite) → `Settled(Catastrophic)`, and a positive read-only / in-workspace-write allowlist → `Settled(Safe)`. Everything else is the *ambiguous middle* (`NeedsJudge`), handed to the *judge* (or, when the judge is off/unavailable, to `fallback_lane`, the Phase-2 static "dangerous" list). It also computes the out-of-workspace risk marker carried on `JudgeInput`. Zero cost, runs on every command before any LLM call.

### Command guard
The pre-dispatch safety gate over the Lucidos Agent's bash/python tools (`run_bash`, `run_bash_background`, `run_python`, `run_python_background`), inserted in `agentic_loop/run.rs` before tool dispatch (`LucidosEngine::command_guard_decision`). Each command is classified into a *RiskLane* — the static *command classifier* settles the obvious cases, the LLM *judge* handles the ambiguous middle — and handled accordingly. Off by default; toggled under **Settings → Permissions → Command Safety** (the `command_guard` preference). Under that master toggle, two sub-settings (UI-disabled while the master is off): the `command_guard_judge` on/off switch and the `model_command_judge` model picker. Lanes: `Catastrophic` is refused without running (the reason fed back to the LLM); `IrreversibleDanger` on a `Chat` channel pauses and asks the user via the *command permission* lane (mirrors the coding agent); `ReversibleDanger` (in-workspace destruction) is snapshotted via a *command checkpoint* (ADR 0002, Phase 4) and then runs, leaving a one-click Undo; `Safe` runs. On a `Trigger` channel there's no one to ask, so `IrreversibleDanger` is gated by the trigger's *side-effect grant* (ADR 0002, Phase 5): the judge/static fallback tags the command's *SideEffectCategory*, and the command runs only if that category is in `TriggerConfig.side_effect_grant` — otherwise the guard returns `GuardDecision::FailTrigger`, which records the block and fails the whole trigger run (a scheduler failure notification surfaces it). Triggers therefore DO reach the judge now (they skipped it in Phase 3). Rationale and full design: ADR 0002 (`docs/adr/0002-lucidos-agent-command-safety.md`).

### Command permission
The interactive *ask* lane of the *command guard* (ADR 0002, Phase 2) — the chat mirror of the coding-agent permission model. When a command hits `IrreversibleDanger` on a chat channel, the engine emits a `CommandPermissionRequested` `ThreadEvent`, the agentic loop blocks in-process on a `PermissionEntry` broadcast (`Engine.pending_command_permission`, a `PermissionState` shared with the CC lane), and the user resolves it from the same `PermissionCard` UI via `POST /api/v1/command-permission/consent` → `CommandPermissionResolved`. Reuses *AllowScope* (Narrow / Broad / Session); `derive_command_allow_pattern` produces `Bash(<first-token>:*)` / `Bash` / coarse `Python` patterns, persisted to `~/.lucidos/agent-allowed-commands` (Narrow/Broad) or the per-thread `session_allows` (Session — see *session allow*; this lane's grants are still cache-only, so unlike the coding-agent lane they do not survive an engine restart). The persisted file is viewable/editable as a per-row list under **Settings → Permissions → Lucidos Agent permissions** via `GET`/`PUT /api/v1/agent-allowed-commands` (whole-file read/overwrite, mirroring `cc-allowed-tools`; the guard re-reads it per command so edits take effect with no restart). Code: `engine/command_permission.rs`, `api/command_permission.rs`, `api/settings.rs`.

### Conflict-resolution duty
(short form in code comments and prose: *merge duty*.) A thread's in-flight obligation to finish an apply's merge-conflict resolution. Event-sourced, not stored: a `status='pending'` change whose latest merge-lifecycle event is an **unpaired `MergeConflictDetected`** (no later `MergeResolutionCleared` / `ChangeApplyFailed` / `ChangeApplied` / `ChangeDiscarded` for that `change_id`) — derived by `ChangesProjection::pending_conflict_change_for_thread`. Two consumers: (1) a stray-killed or watchdog-recovered merge session's completion **hands off** instead of aborting (`ConflictResolutionCleanupAction::HandOff` — an auto-recovery `ContinuationRequested{auto_recovery_after_hang}` is in flight, signalled either by the in-loop safety net's own decision or by the external watchdog's `external_continuation_requested` flag on the session, so aborting would fail the apply and race destructive git cleanup against the continuation re-adopting the same worktree; the 2026-07-10 incident); (2) the spawn consumer's `Continue` arm re-attaches the duty to the resumed session (`conflict_change_id` + the merge worktree, wired like `run_merge_session_tier2`), so its completion finishes the apply (`ChangeApplied`) or aborts for real — but only for **recovery-shaped** continuations (`continue_should_open_resume_exchange`; an `answered_after_idle` follow-up never binds a merge duty), taking the **newest** open pairing when several exist, and closing a duty it cannot carry (worktree gone, resume failed before settling) with the deferred `MergeResolutionCleared` + `ChangeApplyFailed` pair so the apply never dangles. The hand-off deliberately skips the closing events so the pairing stays open — the gate and the derivation interlock. See `docs/plans/2026-07-10-conflict-resolution-survives-auto-recovery.md`.

### Continuation handoff
The moment the exchange fold moves a **running** turn from one exchange to a later one, recorded as `Exchange.continuationMoved` (`store/thread-events/exchange-grouping.ts`). It happens when a boundary takes over the turn's request-id redirect: a `ChildThreadCompleted` card raised by a spawned sub-thread finishing mid-response, or a question / permission divider. Everything the turn emits from then on groups in the new exchange, so a `Thinking` marker left pending in the old one can never be resolved by its own events — rendering finalizes exactly those markers (`resolvePendingSteps(steps, isThinking)` in `exchange-render.ts`) instead of shimmering an old step half a screen above the work. Deliberately narrow: a pending **tool** step is still owed a result that re-routes back by tool id (the `ask_user_question` spinner that must keep running while the card is on screen), so it is left alone. The mark lands on the exchange the redirect is moved OFF — usually the fold's `current`, but a queued uningested follow-up in front of the live turn makes those different exchanges — and is cleared if that exchange takes the turn back (its `UserPromptInjected` is absorbed; an answered divider is re-anchored to its resolution point).

### Navigation focus marker
The persistent highlight host navigation leaves on the specific inner element it lands on — the "focus stick". One shared mechanism (`components/shared/focusMarker.ts`: `applyNavFocus`/`clearNavFocus`/`hasNavFocus`, CSS `.nav-focus-stuck` + the transient `.nav-focus-fading` in `styles/global/host-components.css`) used by every navigation that scrolls to an element that would otherwise blend into a list/transcript: a chat event/change exchange (`scrollState.ts` deep-link), a settings item (`SettingsView.tsx` Search-Everywhere jump, anchor `data-search-anchor`), and a plugin row (`StoreTab.tsx` update deep-link, anchor `data-plugin-id`). Just a BORDER — no entrance animation, it appears instantly on landing. The border is an `outline` with `outline-offset`, so it sits at the element's OUTER edge with a uniform gap to content, follows border-radius, and never shifts layout (outline is outside the box model). It STAYS until the user takes ANY action, so a glancing-away / slow-iOS-load landing still leaves an unambiguous "this is the thing" indicator. It clears on: a new marker (supersede) or a plain focus / explicit scroll (e.g. chat's `clearPendingEventScroll`) — both remove it immediately via `clearNavFocus` — or the user's first action (scroll `wheel`/`touchmove`, click `pointerdown`, or any `keydown`), which fades the outline out (`.nav-focus-fading` transitions `outline-color` → transparent over `NAV_FOCUS_FADE_MS`, then both classes are removed; skipped under `prefers-reduced-motion`). The action-clear takes an optional `settleGuard` — chat passes `hasPendingEventScroll` so its own deep-link landing scroll can't self-clear the marker before the user engages; synchronous landings (settings, plugins) omit it. There is deliberately no timeout, and it is NOT applied to apps or whole-pane opens (trigger detail, file preview). Replaced three earlier one-off pulse mechanisms (chat `event-pulse`/`event-focus-stuck`, `settings-search-highlight`, `plugin-row-highlight`).
See also: `.claude/rules/frontend.md`; `docs/plans/2026-06-30-unified-navigation-focus-marker.md`.

### Deferred-DMG release
A release published while Apple's notarization verdict is still outstanding, with the signed-but-**unstapled** `.dmg` attached and labelled, then swapped for the stapled one when the ticket lands. Entered with `build-dmg.sh --defer-notarization` (via `release.sh --verify-build --defer-notarization`, which also works against an already in-flight submission and so rescues a Phase A stuck on a slow verdict); finished with `release.sh --attach-notarized <version>`. It exists because notarization gates exactly ONE artifact — the DMG a browser downloads. The headless tarball (`curl … | sh`) and the Tauri updater (`.app.tar.gz` + `.sig` + `latest.json`) are never quarantined, so Gatekeeper never assesses them, which is why existing users and terminal installs get the release immediately and unaffected. The state lives in the *staging manifest*'s `notarized` field, never in a flag, so the *notarization-pending banner*, the site link, and the deferred cleanup cannot disagree with the bytes; an **absent** key means notarized (the pre-2026-07-29 writer staged only after `Accepted`). A deferred publish deliberately does NOT clean up the Phase A worktree, staging, state file, notarize handle, or submitted-bytes pin — those are the attach step's only inputs, and a rebuild is exactly the cost being avoided. See ADR 0027 and `docs/plans/2026-07-29-deferred-dmg-release-mode.md`.

### Notarization-pending banner
The warning a *deferred-DMG release* carries on its GitHub Release body: the DMG is signed but has no Apple ticket yet, what to do to open it anyway (the five-step macOS Sequoia/Tahoe flow — the Control-click override was removed in Sequoia, so it is deliberately not offered), and the two paths that need nothing extra (the in-app update, the one-line installer). Composed by `release_notes_compose_pending` in `scripts/lib/release_notes.sh` from the staging manifest's `notarized` field, so it cannot be forgotten. It goes on the **Release body only** — never into `$NOTES_FILE`, which feeds `latest.json` and therefore the *in-app updater's* release notes, whose readers are unaffected by notarization; telling them to visit System Settings would be a lie. Removed by `release.sh --attach-notarized`, which rewrites the body with the plain changelog section produced by the same shared extractor (`release_notes_extract_section`), so the text it lands on is byte-identical to what the publish wrote.

### Deferred snap
The desktop pane-resize contract (`crates/lucidos-app/src/components/layout/splitHelpers.ts`): a divider drag lands wherever the pointer drops it; `SNAP_DELAY_MS` (~400ms) after release, a pane below its minimum width (`MIN_THREAD_PANE_PX` / `MIN_CONTENT_PANE_PX` for the split panes, `MIN_DRAWER_WIDTH` for the thread drawer) animates to the minimum — or to hidden when below half of it (`computeSnapRatio` / `computeDrawerSnap`). While the drag is live, `data-pane-resizing` on `:root` disables the header/drawer geometry transitions so the header regions track the panes 1:1. Collapse states (`data-thread-collapsed` / `data-content-collapsed` / `data-thread-drawer-open`) flip only at the snap, never mid-drag (the drag keeps the ratio off exactly 0/1 by 1px), so header icon groups can't dance between hosts — and they hide via opacity/visibility fades that ride the same transitions, never `display: none` or unmount (which would pop a header region out at the start of the pane animation; header regions stay mounted and clip their own overflow). A snap still pending when a new drag begins is flushed — applied, not discarded — by `beginPaneResize`; only explicit layout overrides (`setSplitRatio`) discard it. The deferred snap is a *drag* contract only: the keyboard pane-resize shortcuts (`computeStepRatio` / `computeDrawerStepWidth`, driven from `store/actions/pane.ts`) clamp to the minimums immediately on each press and never collapse a pane — a discrete keystroke has no mid-gesture state to defer around.
See also: `.claude/rules/frontend.md` § "Pane Resize".

### Deterministic repo id
A *repository*'s stable identity: `repositories.id = uuidv5(REPO_ID_NAMESPACE, git root-commit SHA)`, falling back to `uuidv5(namespace, canonical path)` for a repo registered with no commits yet (`core::repositories::deterministic_id`; the root-commit SHA is read from disk by `git_ops::root_commit_sha` and stored in the `repositories.root_commit_sha` column). Because it is derived from the repo's git history rather than minted randomly, re-registering, moving, renaming, re-cloning, or re-seeding the same checkout yields the *same* id — so `thread_summaries.cc_repo_id` bindings never orphan. Replaces the former random `gen_random_uuid()` surrogate PK, whose regeneration across a checkout's rename/move history (e.g. cognos→lucidos→Lucidos) was the source of "(deleted)"/missing-repo badges in the drawer's repo filter (`repoFilters.ts` keys live-vs-deleted on id). `RepositoryStore::add` upserts keyed on this id and atomically collapses stale rows (a legacy random-id row at the same path; the same history registered at a different path). A git remote URL is *not* part of the identity (remotes get rewritten ssh↔https; local-only repos have none). One-time historical cleanup of already-orphaned bindings is the marker-guarded `EventStore::backfill_cc_repo_id_to_deterministic` startup step — every `coding_agent_kind = 'lucidos'`/legacy-NULL thread targets the Lucidos source by definition, so it is re-pointed to the default repo's deterministic id.

### Repo-encoded preview path
The file-preview overlay path form that addresses a file inside a registered *repository* clone instead of the workspace data tree: `repo:<repoId>:<mode>:<repo-relative path>`, where `<mode>` is `file`, `diff`, or `diff#<changeId>` (the change id rides inside the mode segment so a diff preview survives nav-history persistence — the runtime-only `repoDiff` does not). `<repoId>` is the *deterministic repo id*. Built by `encodeRepoPath`, decoded by `parseRepoPath` (`crates/lucidos-app/src/store/store.ts`), which is the **single predicate** for "is this a repo path": `ContentPane` routes a parsing path to `RepoFilePreview` and everything else to `FilePreviewInline`; `normalizeDataPath` passes one through instead of prefixing `artifacts/`; `openEncodedRepoFilePreview` binds `repoSource` to it. Every segment must be non-empty, because the form reaches the parser from OUTSIDE the app — an app iframe's `lucidos.ui.navigate('file', { file_path })` (see `system-knowhow/js-sdk.md`) or an LLM `navigate_ui` — and a partial encoding like `repo::file:x` would otherwise yield an empty repoId (a repo selection that is neither null nor a real id) or an empty path, opening a preview that can only 404 rather than falling back to the data-path preview.

### Drawer view selector
The **View** section of the unified thread-drawer **Filter dropdown** (`crates/lucidos-app/src/components/layout/ThreadFilterDropdown.tsx`): it picks one of five mutually-exclusive views. A single funnel `FilterIcon` button in the threads header (desktop `AppHeader` + mobile `MobileAppHeader`) opens that dropdown, which has two sections: the **View** (single-select) on top, a divider, then **Show**, the *channel filter* (multi-select: chat / triggers / coding-agents → repos/apps). The Show section is disabled (greyed in place, a `<fieldset disabled>`) whenever a non-`all` view is active, since those views bypass the channel filter (replacing the former separate channel button that was disabled with a "filter unavailable in this view" tooltip). Merging the two former separate controls (the standalone view-selector menu + the channel dropdown) into one button also fixed a Chrome bug where the view-selector failed to open. Views (`DrawerView` in `store/store.ts`, persisted in `localStorage['lucidos-alt-view']` via `setDrawerView`; legacy `'attention'`/`'drafts'` still restore, retired `'none'`/unknown → `all`): **All**, the default sectioned list (Current/Saved/Archive); **Needs attention**, Current/Saved threads where the agent is stuck waiting on the user (`waiting_for_user_answer` OR `failed`; predicate `threadNeedsAttention`, list `attentionThreads`, count `attentionThreadCount`); **Review**, Current/Saved threads carrying a *change* ready to apply (`codingAgentProposed`, not mid-turn; predicate `threadInReview`, list `reviewThreads`, count `reviewThreadCount`); **Running**, Current/Saved threads actively working on a response (effective status `running`; predicate `threadIsRunning`, list `runningThreads`, count `runningThreadCount`); **Drafts**, threads with an unsent draft (`draftThreads`). Needs-attention and Review are independent surfaces: a thread that is both awaiting an answer and carrying a proposed change appears in both; Running is mutually exclusive with both (they exclude `running`). The Filter button shows a **needs-attention badge** (`attentionThreadCount`, the threads stuck waiting on the user) and the active-control highlight (`view-selector-active`) when a non-`all` view OR a channel filter is set. Review and Running are surfaced as per-row counts inside the View section only and never inflate the button badge (Review is a change merely ready to apply; Running is informational, "work in flight, nothing to do"). The same `attentionThreadCount` also badges the **thread-drawer toggle** (`ThreadToggleButton`, both of its desktop hosts plus the mobile *thread pane* header) whenever the thread list is HIDDEN: `!threadDrawerOpen` on desktop, `mobileView !== 'threads'` on mobile, via the pure `threadToggleBadgeCount` / `threadListVisible` rule. The two surfaces are mutually exclusive by construction, since the Filter button lives in the threads header, which is hidden with the list. The button glyph swaps to the **selected view's icon** (the funnel `FilterIcon` for the default `all` view, each view's own glyph otherwise; single source of truth `viewIcon` in `ThreadFilterDropdown.tsx`, shared with the dropdown rows); picking a View row does not close the dropdown, so the Show section's enable/disable updates in place. The Running view's icon is a **static ring spinner** (`RunningIcon`), the same visual family as the animated `.mini-spinner` on running thread rows (`modal-overlay.css`), so the app shows one spinner shape. ### Em-dash gate
The deterministic enforcement of `.claude/rules/no-em-dashes.md` (never write U+2014 EM DASH or U+2015 HORIZONTAL BAR; U+2013 EN DASH stays legal in numeric ranges). Two layers over one shared library, `scripts/lib/em_dash_scan.sh`, which owns the two characters (spelled as byte escapes, never literals, so the gate's own files stay clean under it) and the replacement advice. **Write time:** `.claude/hooks/no-em-dashes.sh`, a `PreToolUse` hook on Claude Code's `Edit`, `Write` and `Bash`, blocking with exit 2 and naming file, line and text. The `Bash` arm covers `git commit`, whose message reaches disk through neither `Edit` nor `Write`. It fails **open** on infrastructure trouble, so a hook bug cannot brick a session. **Review time:** `scripts/check-em-dashes.sh`, run by `/harden` Phase 4.5 on every diff including docs-only, which is what covers Codex (no hooks); it fails **closed**, since a scan that cannot run must not read as clean. Both are **diff-scoped, added lines only**: the rule is deliberately not retroactive, and the ~29,000 pre-existing lines decay as files are touched. Rewording a line that keeps its dash counts as adding one. No exemption list exists, by design. Tested by `scripts/lib/em_dash_scan_test.sh`.

### Empty completion
A chat agentic-loop turn that ends with no text and no tool calls. Classified by *why* it was empty — uniformly across providers and thread types — by `classify_empty_completion` (`crates/lucidos-engine/src/engine/agentic_loop/helpers.rs`), which first runs the raw provider finish reason through `normalize_finish_reason` → `FinishClass::{Clean, Truncated, Blocked, Unknown}` (case-insensitive, so Anthropic `end_turn`, Gemini `STOP`, OpenAI `completed` all collapse to `Clean`). A **benign empty completion** = a `Clean` stop with no dropped-output signal: the model ended its turn and simply produced no text. It emits an *empty* `ResponseGenerated` (thread completes Idle, no red dot; the UI renders a neutral "empty response" note — `ResponseEvent { type: 'empty' }`). The genuine-failure shapes — `Truncated`, `Blocked`, dropped output (`output_tokens > 16 && thinking_chars == 0`, or `unknown_sse_dropped > 0`; Anthropic-only signals), or `Unknown` (fail-safe) — emit `ResponseFailed`. See ADR 0009 and `system-knowhow/thread-events.md` (`ResponseGenerated` / `ResponseFailed` rows). Distinct from a *terminal* like `ResponseCanceled` (user) / `ResponseAborted` (system) — an empty completion is the model's own clean end-of-turn.

### ENGINE_BUILD_ID
Deterministic-per-source id baked into the engine binary by `crates/lucidos-engine/build.rs` (git short SHA + a hash of any uncommitted engine-source diff; a source-tree hash when git is unavailable). Mirrors the gateway's `GATEWAY_BUILD_ID`. Printable via `lucidos-engine --build-id`; a running engine reads the on-disk binary's `--build-id` (behind an mtime cache, `LucidosEngine::engine_disk_build_id`) and `version_status` compares it against this baked const to detect that a newer version has been built — the dev half of *New version available / Switch to new version* (see `system-knowhow/glossary.md`). Byte-identical source → identical id → no spurious "new version". Consumed by `GET /api/v1/engine/version-status`; the packaged half of the flow uses the release updater instead. See `crates/lucidos-engine/src/engine/engine_version.rs`.

**`update_available` means NEWER, not merely DIFFERENT** (`LucidosEngine::disk_binary_is_upgrade`). Co-located dev workspaces share one checkout and one *launch binary*, so the binary on disk is routinely written by something other than the workspace reading it — a peer's `--engine-build`, or a build whose `build.rs` ran before an Apply moved HEAD. A bare `disk != running` therefore announced an OLDER binary as an update, and *Switch* **downgraded** onto it; the downgraded engine was then genuinely behind HEAD, self-heal rebuilt, the switch re-surfaced, and the pair ping-ponged (the 2026-07-26 endless-toast loop). So direction is decided by git ancestry over the two ids' commit prefixes (`git merge-base --is-ancestor`, memoized per on-disk build id): a disk commit that is a **strict ancestor** of the running commit is provably older and vetoes the update, and the downgrade is logged once. Everything indeterminate — unrelated commits, a `src-…` id, git unavailable — keeps the difference test, because *missing* a real update strands the user on an old engine, the worse failure. The same method gates self-heal's "a fresh binary is already on disk" skip, so the two can't disagree, and `gateway_update_available` carries a hand-synced copy of it (`crates/lucidos-gateway/src/build_id.rs`) so the picker's reload can't re-exec the gateway backwards. See `docs/plans/2026-07-26-downgrade-switch-toast-loop.md`. The *cause* of a wrong binary being there at all — one uplift path shared by every cargo variant — is fixed separately by publishing a *launch binary* per build variant (ADR 0022); this guard remains the authority on direction.

Because that binary-diff signal is silent when the background rebuild **fails or never runs** (the on-disk binary stays == running, so `update_available` never flips), `version_status` ALSO reports **`source_behind_head`** — the engine SOURCE is behind HEAD by a restart-requiring change (the SAME `engine_source_matches_head` git classifier the frontend-only-Apply INV-A veto uses), so a new engine version is discoverable even before a fresh binary exists. A dev-only **self-heal** driver (`self_heal_engine_version_if_needed`, on the ~10s periodic loop) then (re)triggers a coordinated background rebuild — bounded per HEAD, and serialized across co-located workspaces by a checkout-shared advisory build lock (`<repo_root>/target/.lucidos-engine-build.lock`) so they never run concurrent cargo builds on the shared `target/`. So a *Switch* can't become a dead-end when a rebuild fails. See `docs/plans/2026-07-03-engine-version-switch-selfheal.md`. `source_behind_head` carries the same direction guard as `update_available`: its underlying two-dot `git diff` is symmetric, so an engine running a commit HEAD is an *ancestor* of is explicitly not "behind" — otherwise a workspace already ahead of its checkout would show a permanent pending-version toast and rebuild every 10s. And self-heal gives up for a HEAD the moment a rebuild it triggered **succeeds without advancing the binary**: that is a wedged build configuration, not a transient miss, so it logs once instead of retrying forever (a compile *failure* still keeps the retry budget).

### Cause-gated resume
The rule that a thread interrupted by an engine restart only **auto-resumes** when the restart was a **user-initiated switch**. The fingerprint is a teardown `ResponseAborted` that is BOTH `cause = engine_shutdown` AND device-attributed, with no newer start event — `switch_was_user_initiated` in `agent_recovery/recovery.rs`, the single definition, exposed to both resume gates as the `SWITCH_TEARDOWN_ABORT_SQL` + `THREAD_START_EVENTS_SQL` fragments. **Both halves of the fingerprint are load-bearing:** `AbortCause::StaleSettle` deliberately carries the actor of the user button that exposed a stuck row (Stop / Apply / Discard / Archive / Interrupt, via `settle_stuck_running_thread`), so an actor-only predicate reads a user *Stop* as a switch and re-runs work the user just abandoned.

Two halves consume it. **Coding-agent threads** queue a `ContinuationRequested{reason: auto_resume_after_switch}` (`enqueue_switch_resume`, emitted from `main.rs` after the spawn dispatcher subscribes) and re-enter via `--resume`. **Chat / trigger threads** are selected at boot by `chat::recovery::switch_resume_candidates` and driven through `continue_chat` — the same entry point the manual **Continue** button uses, so the resumed turn gets the identical `ContinuationStarted` boundary and side-effect engine note. That pass runs later in boot than the coding-agent one (after `thread_queue.spawn_settle_subscriber()`): a chat resume re-enters the agentic loop directly and immediately reads as `running`, so the settle subscriber must already be live to reconcile its queue slot, and it must follow `recover_orphan_tool_calls` or the re-entered turn rebuilds an unpaired `tool_use` block.

A **crash / OOM / panic / agent-killed** engine leaves no such boundary, so the thread keeps the manual **Continue** affordance (for coding agents, the Phase 5.3 `engine_restart_interrupt` idle) and is NOT auto-resumed — work that may have crashed the engine can't loop. The start set counts `ContinuationStarted`/`OrphanRecoveryStarted` so a consumed switch-abort can't re-fire (the loop-breaker) — and because `continue_chat` emits `ContinuationStarted`, chat inherits that loop-breaker unchanged. A thread parked on an unanswered `UserQuestionAsked` is preserved by recovery either way (`thread_has_unanswered_question`) and is structurally excluded from both resume gates (no abort was ever emitted for it) — answering resumes it instead.

### Chat resume anchor
Which `request_event_id` a re-entered chat/trigger turn is stamped with — and therefore which exchange the resumed work renders under (`ChatResumeAnchor` in `engine/chat/rerun.rs`, consumed by the single re-entry site `spawn_chat_resume`). Two forms. **New boundary** — the manual **Continue** after a genuine interruption: the previous turn really ended (a `ResponseAborted` sits in the timeline) and the user asked for a new attempt, so the resume opens its own boundary — `ContinuationStarted` ("Continued the response") plus the engine note as `UserPromptInjected` ("Reminded the model about N prior tool calls") — and anchors on that new event. **Existing turn** — the answer-driven resume of a thread parked on an unanswered `ask_user_question` that a restart *preserved* (no abort was emitted; see *cause-gated resume*): nothing was interrupted from the user's point of view and nothing needs their action, so the resume emits **no** boundary and anchors on the turn that asked, making the resumed reply group under the question card exactly as it would have without the restart — the chat parity of the coding agent's silent `--resume`.

### Engine supervisor
Bash wrapper (`scripts/lib/engine_supervisor.sh`, function `run_supervised`) that runs the engine binary in a restart loop. SIGKILL / OOM / panic exits trigger an exponential-backoff respawn (1–30 s) and rewrite `engine.pid`; clean exits (0 / 130 / 138, i.e. `graceful_shutdown` or SIGUSR1/SIGINT defaults) break the loop. Traps SIGTERM/SIGINT on itself so `web-dev.sh`'s `kill_stale_processes` (which `pkill -P`s the supervisor as a direct child) forwards SIGUSR1 to the engine and exits cleanly instead of respawning the engine that's about to be rebuilt. The pid the supervisor writes is always the *live* engine, so `stop.sh`, `is_protected_host_pid`, and `kill_stale_processes` keep working across restarts. Wired in from `start_engine` (`scripts/lib/workspace.sh`); exported as `ENGINE_SUPERVISOR_PID` for `web-dev.sh`'s wait branch. Call it the **engine supervisor**, never "watchdog" or "babysitter" — the canonical noun lines up with the file/function/variable names. The "never call it watchdog or babysitter" rule applies to *this* concept (engine-binary respawn) only. The *in-loop watchdog* and *external watchdog* inside *agent session* are canonically watchdogs — they watch for stuck Lucidos *agent sessions* and emit `ContinuationRequested`, never restart the engine.

### Engine startup lease
A per-database Postgres **session-scoped advisory lock** each *engine* holds on a dedicated connection for its entire process lifetime, so a freshly-spawned engine never runs its startup reset / recovery sweeps against a database the *previous* engine is still mutating. Acquired in `main.rs::run` (before any reset/recovery) via `crate::engine::startup_lease::acquire_startup_lease` and held as a `run()` local; released only when `run()` returns — i.e. after this engine's own graceful shutdown (`abort_in_flight_for_restart` + `shutdown_agent_sessions`) has persisted, or instantly when the connection dies on a crash. This exists because a respawn is **not** atomic: the *workspace gateway*'s `respawn_stack` spawns the new engine before the old one exits (it reaps the old child in a detached task), so without the lease the successor's `recover_orphaned_worktrees` read state before the predecessor's device-attributed switch-abort boundary landed (auto-resume misfired to manual Continue) and before its interrupted *agent session* subprocesses finished draining (their late no-actor activity events re-projected the thread to a phantom `running`). The key is a database-scoped constant (each workspace has its own database, so no cross-workspace collision). **Fail-open + bounded**: if the lock is still held after `DEFAULT_MAX_WAIT` (45 s, well inside the gateway's 120 s `BOOT_GRACE`), or the lease connection can't be opened, the engine logs and proceeds *without* serialization (degraded — a hung predecessor must never wedge boot). Distinct from the *engine supervisor* (restart loop) and the *gateway supervisor*: those manage the process lifecycle; the lease serializes what a booting engine does *inside* that lifecycle. See `docs/plans/2026-07-01-engine-startup-lease-recovery-race.md`.

### Launch binary
The copy of `lucidos-engine` / `lucidos-gateway` / the `lucidos` CLI that a workspace actually **launches** — published by `build_or_find_engine` (`scripts/lib/workspace.sh`) into `target/<profile>/launch/<variant>/`, where `<profile>` is `debug` | `release` and `<variant>` is `plain` for a default build or a slug of `ENGINE_BUILD_FEATURES` (`e2e-test-hooks`). `ENGINE_BIN` / `GATEWAY_BIN` / `LUCIDOS_ENGINE_BIN` and the engine's own `current_exe()` all resolve here. Distinct from **cargo's uplift path** (`target/<profile>/lucidos-engine`), which every cargo variant in the checkout writes to and which nothing launches from any more: a workspace-scope `cargo test`, an e2e feature build, and a build whose `build.rs` ran before an Apply moved HEAD all compete for that one path, so launching from it ran (and compared `ENGINE_BUILD_ID` against) a binary from another commit or another feature configuration — the cause half of the 2026-07-26 downgrade/toast loop. A launch dir is written **only by completed builds of the same profile AND variant**, published by temp-file + atomic rename (a failed publish leaves the previous binary intact — the launch path must never go missing), verified against HEAD with one bounded rebuild, and signed with the stable dev identity. Staying under `target/` is load-bearing: *repo root* resolution walks `current_exe()`'s ancestors for `scripts/web-dev.sh`, and ADR 0021's worktree refusal is a pure path test on `LUCIDOS_ENGINE_BIN`. See ADR 0022 and `docs/plans/2026-07-27-launch-binary-published-per-variant.md`.

### Gateway supervisor
Dev-only bash wrapper (`scripts/lib/gateway_supervisor.sh`, function `run_gateway_supervised`) that runs the **machine-global workspace gateway** binary in a restart loop. Same respawn shape as the *engine supervisor* (exponential-backoff respawn on SIGKILL/OOM/panic, rewrites `gateway.pid`, clean exits 0/130/138 break the loop, writes a `gateway.last-death.json` sidecar) but **deliberately decoupled from it**, with the opposite signal policy: it `trap '' SIGHUP SIGINT SIGTERM` — IGNORING terminal/launcher signals — so closing the launching terminal, Ctrl-C on `web-dev.sh`, or a stray SIGTERM can't orphan the shared gateway. The only legitimate stop is SIGUSR1 to the gateway *child* (the gateway ignores SIGTERM and exits 0 on SIGUSR1; `start_gateway`'s `-b` stop + port-reclaim do exactly that). Wired in from `start_gateway` (`scripts/lib/workspace.sh`) and launched `disown`ed with `ENGINE_SUPERVISOR_PID` left empty, so `web-dev.sh` never `wait`s on the daemon. This exists because the gateway is one shared daemon fronting every workspace, not a per-workspace process tied to a dev session. The **packaged** app needs no bash equivalent — there the Rust `--service` process (`crates/lucidos-app/src/desktop.rs::run_service`) supervises the gateway under launchd `KeepAlive`. Call it the **gateway supervisor**; keep it distinct from the *engine supervisor*.

### Host-pid kill guard
`is_protected_host_pid` (`scripts/lib/ports.sh`) — the check that decides whether a pid is a live Lucidos host process the dev scripts must never signal. Consulted by `kill_unprotected_pids`, by `_try_reclaim_stale_lucidos_on_port` (the only path that sends the engine's real stop signal, `kill -USR1` — it ignores SIGTERM), and as a backstop by `webkit_reaper.sh::reap_once`. **Four arms**, and the split between them is the point: `LUCIDOS_HOST_PID` / `LUCIDOS_FRONTEND_PID` and a pidfile scan of `<home>/workspaces/*/.lucidos/{engine,frontend}.pid` read state the **caller owns** and can switch off; the **ancestor** arm (this process and every pid it descends from, a cached `ps -o ppid=` walk from `$$`) and `pid <= 1` **cannot be defeated by the caller**, because a process cannot unset its own parentage. The pidfile scan also covers the **password-database home** (`dscl` / `getent`, never `eval`), so reassigning `HOME` doesn't hide sibling workspaces' engines either. The two undefeatable arms exist because both original arms failed open on 2026-07-28 and `ports_test.sh` — doing nothing worse than sandboxing `HOME` and unsetting env vars, as a good test should — killed the machine's live dev engine twice. Consequence worth knowing before writing a test: **sandboxing `HOME` isolates the port registry but deliberately does NOT disarm host protection**; a pid you need unprotected must be dead (the `kill -0` liveness gate) or synthetic. Distinct from `.claude/hooks/pre-kill.sh`, which blocks `kill`/`pkill`/`lsof | xargs kill` typed directly into a Bash tool call by inspecting the command string, and so cannot see a kill several frames deep inside a sourced shell library. See ADR 0025.

### Network bind config
The durable, user-configurable control over what address the *workspace gateway* and each *engine* listen on, with a loopback-first security default. Lives machine-globally in `~/.lucidos/network.toml`: `[gateway] bind = "loopback" | "all" | "<IP>"` (the gateway's own bind — machine-wide, since it binds before any workspace is chosen) and `[engine] inherit = true | false` (true: every engine binds the gateway's bind; false: each engine reads its own per-workspace **`network_bind`** preference — so e.g. `dev` can be on the tailnet while `personal` stays loopback). Resolved at process start by `crates/lucidos-{engine,gateway}/src/net_config.rs` — two **deliberately duplicated** modules, since the gateway has no dependency on the engine (ADR 0014 §1). Precedence (highest first): the engine's `LUCIDOS_BIND_LOOPBACK` floor (a packaged behind-gateway engine never faces the network) → the `LUCIDOS_BIND_ADDR` / `LUCIDOS_GATEWAY_BIND_ADDR` env (a literal IP, e.g. a Tailscale `100.x`) → the `LUCIDOS_BIND_ALL` / `LUCIDOS_GATEWAY_BIND_ALL` env → the file / per-workspace pref → loopback. A malformed value fails safe to loopback, **never** to all-interfaces. Edited from the **workspace picker** (the gateway bind + inherit toggle, via `/~/api/v1/control/network-config`) and per-workspace **Settings → System → Network access** (the engine bind, via `/api/v1/network-config`). A change takes effect only after a gateway / engine **restart** — a live socket cannot be re-bound. Env vars override the file so launch scripts / e2e are unaffected.

### Event store
The persistence layer for events — the `events` table plus the append semantics that write to it. Today the *write* path is inlined inside *EventBus* (raw `INSERT INTO events` at `event_bus.rs:218, 276`) — `EventBus::emit` is the only API that appends. The `EventStore` struct (`core/store/mod.rs`) still exists, but only as a **read-only query facade** (`query_events`, `count_events`, `get_event_by_id`, …); its historical `append` / `append_thread_event` write methods were removed when persistence moved to *EventBus*. The term remains valid for the concept.

### EventBus
The in-process emit/subscribe mechanism. `EventBus::emit(BusEvent)` is the **sole** entry point for event persistence — it owns the *event store* directly. Consumers (SSE, projections, scheduler matcher, side-effects) subscribe to the bus, never poll the table.

### EventChannel
Also called **channel**. The source-channel tag merged into every persisted event's payload via `EventMeta::channel`, distinguishing which thread surface emitted the event. The Rust enum `EventChannel` lives in `engine/thread_events.rs`; today's variants are `Chat`, `ClaudeCode`, and `Trigger`, serialized to the wire strings `"chat"`, `"claude_code"`, and `"trigger"` respectively. The `"claude_code"` wire string is the persisted historical coding-agent channel for every *coding-agent thread*; it is backend-agnostic, while the `coding_agent` column / event field records the product (`"claude-code"` or `"codex"`). Public source filters call the bucket `coding-agent` and accept `"claude_code"` as the legacy persisted alias. `Trigger` is the umbrella for all trigger-driven runs (scheduled, event, hybrid); the precise invocation that fired a given run is recorded separately on `TriggerStarted.invocation`.

### EventMeta
Cross-cutting fields the EventBus merges into a persisted event's payload at write time: `request_event_id`, `channel`, `actor`, etc. Built per-variant by the helpers in `engine/thread_events.rs`. New variants take `EventMeta::with_actor(actor)` rather than reading the device header themselves.

### External watchdog
The 12-minute backstop that ticks from its own `tokio::spawn` outside every per-thread loop (`agent_session/external_watchdog.rs`, `EXTERNAL_WATCHDOG_LIMIT_MS`, tick interval `EXTERNAL_WATCHDOG_TICK_SECS = 30 s`). Scans `agent_sessions`; for any session past the limit where the gate (`is_waiting` / `tools_in_flight`) says we'd otherwise have fired, drops the entry from `agent_sessions` and emits a `ContinuationRequested { reason: AUTO_RECOVERY_AFTER_HANG_REASON }` which the spawn dispatcher consumes to issue a fresh `--resume`. Same outcome as the *in-loop watchdog*'s auto-recovery path, but reachable from outside a wedged `select!`. The 12 > 10 min gap gives the in-loop watchdog first crack; the external tick is a no-op when the in-loop succeeded. It honours the same **hung-tool ceiling** (`WATCHDOG_HUNG_TOOL_CEILING_MS`, 45 min) as the in-loop watchdog — a tool stuck in flight past the ceiling recovers (`ResumeIfRunning`, gated on a `thread_is_running` re-check) instead of skipping forever — and additionally recovers a `process_exited` session still stale past the limit, where the in-loop cleanup is wedged. Distinct from *Engine supervisor*.

### Family
A root thread plus every transitive descendant reachable through `parentThreadId` — the unit the thread drawer renders together. Distinct from *sub-thread* (any single descendant): a family is the whole set. The drawer routes families as one (highest-priority section wins: current > saved > archive — any live or attention-needing member keeps the whole family in Current, with the CTA rendered inline on the responsible child row). *Saved* and Archive sort families by the freshest user action anywhere in the subtree, so a parent automatically rises with its descendants; *Current* sorts by *thread* creation time (newest first) instead, so it doesn't reshuffle as agents work. Either way `nestByParent` puts each child directly under its parent. The **family root** is the topmost ancestor present in the currently-rendered list; an orphan child (parent paginated out / filtered) is its own root. Implemented in `crates/lucidos-app/src/components/drawer/family-graph.ts` as the `FamilyGraph` (`{ byId, rootByThread }`) and `FamilyKeys` (`{ recentKey }`) types, built by `computeFamilyGraph` and `computeFamilyKeys`.

### Family extension
The ancestor + descendant threads of a paginated set that get loaded eagerly so the drawer can render them under their parent, even when their own `last_activity` falls below the loaded window. Backend helper `EventStore::fetch_family_extension` (recursive CTE over `thread_summaries.parent_thread_id`); HTTP layer returns them in a separate `family_threads` field on `GET /threads` and `GET /threads/older`. The frontend upserts them into `threadMap` like any other thread but tracks their ids in `familyExtensionIds` (in `store/actions/thread-loading.ts`) so they're **excluded from the `loadOlderThreads` pagination cursor** — without that exclusion, a single old child would advance the cursor past every intervening thread. An id is removed from the set when natural pagination later returns it as a base thread.

### Focused pane
Desktop-only signal (`focusedPane`, `FocusedPane = 'drawer' | 'thread' | 'content'` in `crates/lucidos-app/src/store/store.ts`) tracking which of the three desktop panes the user is working in. All three are user-facing terms defined in `system-knowhow/glossary.md`: `drawer` → *thread drawer* (`.thread-drawer`), `thread` → *thread pane* (`.pane-thread`), `content` → *content pane* (`.pane-content`) — so a UI string may name any of them directly. The *Conversation* / *Canvas* pair sits one level up and names the two **sides**, not panes; use it only when the subject is a whole side (see *Pane group*). Set on pointer-down inside a pane (`focusPane`) and by the thread-pane / content-pane keyboard toggles (`toggleThreadPane` / `toggleContentPane` via `focusPaneAndControl`, which also moves real DOM focus via `focusPaneMainControl`). The drawer splits pointer vs keyboard the same way: the drawer **icon** (`toggleThreads`) is a pure show/hide that never *sets* `focusedPane` — it only drops a hidden-but-focused drawer's focus back to the thread pane so the focus wash never strands on an invisible region — while the `toggleThreadDrawer` **shortcut** (⌘⇧1, `focusOrToggleThreadDrawer`) IS focus-aware: a three-stage open+focus / focus / close that moves real DOM focus into the drawer (re-expanding the Conversation side first if it was collapsed) so the drawer's existing ↑/↓/Enter list-nav is reachable from the keyboard. **Navigation also activates the matching pane group**, signal-only (no DOM focus moved — the first Tab pulls focus in via `handlePaneTab`): `revealContentPane` sets `content` for any content navigation (menu switch, settings subview, app / file / URL / trigger / change — Search Everywhere included), and `focusThread` re-activates `thread` when arriving from the Content group (`focusedPane === 'content'`, so drawer browsing is left undisturbed). Without this the view lands but Tab stays stuck on the previously-focused pane. See *Pane group*. **Desktop-only** — mobile has no focused pane: panes there are *navigated, not focused* (via the header / swipe, tracked by `mobileView`, the *visible pane*), and the pane keyboard shortcuts don't exist on mobile. Pane-scoped keyboard actions target the focused pane: resize (`stepThreadPaneWidth` / `stepThreadDrawerWidth` in `store/actions/pane.ts`) and history navigation. The Back / Forward shortcuts (`historyBack` / `historyForward`, ⌘⌥↓ / ⌘⌥↑) route through `store/actions/focused-pane-history.ts` to the focused pane's OWN history stack: the content pane walks the panel nav stack (`navigation.ts`, `navBack` / `navForward`), while the thread and drawer panes share the thread nav stack (`thread-navigation.ts`, `threadNavBack` / `threadNavForward`). Each pane header's dedicated Back / Forward buttons drive their own stack directly regardless of focus; only the keyboard shortcut is focus-routed. Canonical term — don't say "panel" or "view"; *view* is already taken by `MobileView` (the mobile swipe position).

### Pane group
Desktop-only partition of the three *Focused pane* values into two maximizable groups: the **Threads pane group** (`drawer` + `thread` — the user-facing *Conversation* side) and the **Content pane group** (`content` — the user-facing *Canvas* side). The maximize shortcut (⌘⇧↵, `maximizePaneGroup` → `toggleMaximizeFocusedPaneGroup` in `store/actions/pane.ts`; labelled "Maximize focused side (Conversation or Canvas)" in Settings → Keyboard shortcuts, since *pane group* is dev-only) collapses the opposite group so the focused group fills the content row — `splitRatio → 1` (Threads; the drawer rides `splitRatio > 0`, so it stays open) or `splitRatio → 0` (Content) — and a second press restores the remembered pre-maximize ratio (falling back to `DEFAULT_SPLIT_RATIO`, since the remembered ratio is in-memory and doesn't survive reload). Structural code/keyboard names for the two user-facing sides (*Conversation* / *Canvas* in `system-knowhow/glossary.md`).

### Split
The desktop side-by-side layout (`SplitLayout`, `splitRatio` in `crates/lucidos-app/src/store/store.ts`, `splitHelpers.ts`) — the integrated back-and-forth between the user-facing *Conversation* and *Canvas*. `splitRatio` ∈ [0, 1] is the thread pane's fraction, persisted to `localStorage` (`lucidos-split-ratio`, default `0.4`): `0` collapses the *Threads pane group* (Canvas full), `1` collapses the *Content pane group* (Conversation full), in between is a live two-up split. Mutated only via `setSplitRatio` (animates + persists + cancels any pending *deferred snap*). The surface of *live co-creation* (user-facing): both sides stay live at once so a single conversation reshapes data and presentation together.

### In-loop watchdog
The 10-minute inactivity timer inside `run_session`'s `select!` (`WATCHDOG_INACTIVITY_LIMIT_MS` in `crates/lucidos-engine/src/engine/agent_session/lifecycle.rs`). When an *agent session* has been silent past the limit while the watchdog gate (`is_waiting` / `tools_in_flight`) says it should have fired, the in-loop watchdog cancels the agent token and the loop emits a `ContinuationRequested` so the spawn dispatcher issues a fresh `--resume`. The `tools_in_flight` skip is bounded by a **hung-tool ceiling** (`WATCHDOG_HUNG_TOOL_CEILING_MS`, 45 min): a tool call that never returns (e.g. a hung `/harden` sub-agent — the thread-72120ca6 incident) can't disarm the watchdog forever — past the ceiling the gate returns `FirePastCeiling` and the watchdog fires anyway, but only after re-confirming the thread is still `running` (a pending question/permission card sits at `waiting_for_user_answer` and is also counted in `tools_in_flight`, so it is never euthanized). First line of defense against a hung subprocess — useless when the `select!` itself is wedged (e.g. an event-handler await waiting on a slow subscriber). See *External watchdog* for the floor that catches that case. Distinct from *Engine supervisor*, which operates at the engine-binary level.

### Implementation plan
The pre-edit planning artifact for complex implementation work: ADR-backed or design-thread-backed work, cross-layer changes, routing/topology/storage/security/migration/process changes, or any non-local implementation. Created via the repo-owned `implementation-plan` skill before code edits and always written to a checked-in file at `docs/plans/YYYY-MM-DD-<slug>.md` (the committed file is the source of truth; a short summary may also appear in the conversation). It consumes the user prompt, any `grill` or design thread, ADRs/plans, and code reconnaissance, then records settled decisions, non-goals/deferred work, phase order, load-bearing implementation invariants, and verification for each invariant. It is an execution contract, not a retrospective `/harden` audit: unresolved load-bearing questions block edits, and implementation phases re-read the invariants before changing behavior.

### Judge (command guard)
The fallible LLM half of the *command guard* (ADR 0002, Phase 3) — `engine/command_judge.rs`. A cheap, fast model (Haiku by default; configurable via the `model_command_judge` preference) classifies the *ambiguous middle* — the commands the static *command classifier* returns as `NeedsJudge` — into a *RiskLane* (`Safe` / `ReversibleDanger` / `IrreversibleDanger`, never `Catastrophic`) and produces the one-line `summary` the permission card shows. For the `IrreversibleDanger` lane it also tags a *SideEffectCategory* (`email` / `external_api` / `cloud_cli` / `out_of_workspace_destruction` / `other`), which the trigger *side-effect grant* check keys on. It errs toward *ask*: an unrecognized or unparseable verdict resolves to `IrreversibleDanger` with category `Other`. Returns `Err` only on infra failure (no provider, a failed/empty call), in which case the guard falls back to the static list (`fallback_lane` + `static_side_effect_category`). Gated by `command_guard_judge` (default on when the guard is on); verdicts are cached per response by command hash so a re-emit doesn't re-pay. Triggers DO reach the judge now (Phase 5) — the lane + category are needed to enforce the side-effect grant. `judge_with_provider` is the provider-agnostic core, exercised offline with a stubbed `LlmProvider` in tests.

### Keybinding registry
The customizable keyboard-shortcut subsystem. Pure registry + binding math in
`utils/shortcuts.ts` (`SHORTCUT_DEFS`, `Binding`, `eventToBinding`,
`matchesEvent`, `formatBinding`, `serialize`/`parseBinding`, `bindingSearchText`).
The override-aware layer is `store/actions/keybindings.ts`: it merges per-user
overrides — persisted as the workspace `keybindings` preference (a JSON map of
`shortcutId → "mod+shift+o"`, synced across devices via `PreferencesChanged`) —
over the registry defaults, exposing `bindingFor` / `setBinding` / `resetBinding`
/ `matchShortcut` / `recordChord` and the override-aware `tooltipWithShortcut`.
`useKeyboardShortcuts` dispatches by the current binding (so rebinds take effect
with no code change), Settings → Keyboard Shortcuts renders the cheat sheet +
recorder, and SearchEverywhere indexes each shortcut by its combo aliases. The
`mod` modifier matches either Cmd or Ctrl (both fire); the single-key `c`/`t`
shortcuts were dropped in favor of modifier chords only.

### last_agent_action
`thread_summaries` column (`TIMESTAMPTZ NOT NULL`) holding when the AGENT (or trigger) last did something on a thread — streaming, a terminal response, a `CodingAgentIdled`, a trigger fire/complete, the agent asking the user, or a non-human `MessageReceived`. The counterpart to *last_user_action*. Not a sort key; it drives the thread-row tooltip's "Agent ·" line (frontend `meta.lastAgentAction`), kept distinct from `last_user_action` so the tooltip is accurate even right after the user acts. Bumped per-arm in `event_bus_projection_thread.rs` (co-located in the existing `last_activity` UPDATEs — no extra hot-path queries).

### last_user_action
`thread_summaries` column (`TIMESTAMPTZ NOT NULL`) holding when the USER last drove a thread forward: a human `MessageReceived`, `CodingAgentUserMessageSent`, `UserPromptInjected`, `UserQuestionAnswered`, a `*PermissionResolved`, or a `ChangeApplied`/`ChangeDiscarded`. The drawer's recency sort key — `get_saved_threads`/`get_recent_threads`/`get_older_threads` and the `/threads/older` cursor ORDER BY it, so background agent churn (streaming, idle) no longer reshuffles the list. Frontend `meta.lastUserAction` (the `recencyKey` / `byRecent` comparator + the pagination cursor). Distinct from `last_activity` (max-of-both, still used for facets, the family-extension cap, and the LLM/script list surface) and *last_agent_action*. Attention bubbling (REVIEW sectioning) is unchanged — it never keyed off recency.

### Lifted family
A *family* whose root's own natural display section is lower-priority than the section the family was routed to — i.e. a descendant earned the lift. Surfaces in the drawer as two coordinated cues: the parent row renders with demoted styling (muted opacity) so it reads as "I'm here because of one of my children", and any non-root descendant whose own natural section equals the routed section ("responsible child") gets a brighter accent rail in place of the default gray. When every family member naturally belongs to the routed section, the family isn't lifted and neither cue fires. Computed by `computeFamilyDecorations` (in `crates/lucidos-app/src/components/drawer/ThreadDrawer.tsx`) as `{ routedByThread, liftedRoots }`; routed section comes from the same priority pass `categorizeThreads` uses (current > saved > archive).

### Loadable<T>
The four-state TypeScript type for every async-fetched value: `{ status: 'not-loaded' }` / `'loading'` / `'loaded'; data: T` / `'failed'; error: string`. Store signals **must** wrap async data in `Loadable<T>` — bare arrays are a bug because they mask loading as empty.
See also: `.claude/rules/frontend.md` § "Async Data Loading".

### Notable state
A UI state worth marking that is **not** a caution — waiting, canceled, trimmed, changed, non-default provenance. Painted with `--accent-notable` (cool grey-blue), as distinct from `--accent-yellow` (muted sand), which means *caution* and nothing else. The two were one token until 2026-07-26, so every neutral marker in the app rendered in a warning hue; splitting them is what lets "the agent is waiting" stop looking like "something is wrong". `--accent-notable` is **host-only** — deliberately absent from the engine's `api/sdk_iframe.css`, so it must never be referenced from `styles/global/shared-components.css` (that file is served to app iframes, where the variable would not resolve). Two deliberate exceptions keep a warm hue despite marking non-caution states, each commented at its site: the memory-importance `high` step is part of an **ordered escalation ramp** (grey → blue → orange → red) where a cool hue would flatten the sequence, and the disk-usage `c2` slot is a **categorical chart palette** entry whose only job is differing from the other five. See `docs/plans/2026-07-26-accent-yellow-sand-retheme.md`.

### Staging manifest
`manifest.json` in a release staging dir (`.lucidos/release-staging/<version>/`) — the description of what was built, written by `build-dmg.sh` and verified before anything goes public. Carries `version`, the `source_commit` the artifacts were built from, an optional pair of build/recipe fingerprints (the compiled-input re-fold gate), an optional `notarized` boolean (see *deferred-DMG release*), and an `artifacts` list of `{name, sha256}`. Three separate guards read it: `release_staging_verify` (every listed artifact present, every checksum still matching), `release_staging_assert_commit` (the identity half — the verified tree has not moved under the artifacts), and `release_staging_is_notarized`. It is the pipeline's answer to "are these the bytes that were verified, from the tree that was gated, and do they carry an Apple ticket?" — which is why the deferred mode records its state HERE rather than in a flag: a manifest travels with the artifacts, a flag does not. Owned by `scripts/lib/release_staging.sh`.

### Notarize resume handle
The JSON breadcrumb that makes the release pipeline's notarization stage resumable: `<repo-root>/.lucidos/release-state/notarize-<version>.json`, recording the notary `submission_id`, the absolute `dmg_path`, the DMG's `dmg_sha256` at submit time, the `source_commit` it was built from, and `submitted_at`. `build-dmg.sh` submits with `--no-wait` and writes this handle **before** it starts polling, precisely so the process can die at any moment afterwards — Apple routinely takes longer than the waiter lives, and the orchestration layer caps background tasks at 3600 s, so a foreground `--wait` can never complete for a slow submission. Losing the waiter then costs a poll, not a rebuild. Owned by `scripts/lib/release_notarize.sh` (written atomically); consumed by `--resume-notarize` / `--adopt-submission` and by `release.sh`'s auto-promote of `--verify-build`. The resume gate refuses unless the DMG still hashes to `dmg_sha256` **and** the tree is still on `source_commit` — the latter because the resuming run stamps the *staging manifest*'s `source_commit` from its own HEAD, so resuming on a moved tree would let `--publish-verified`'s identity guard pass on a lie. The handle is deleted once staging succeeds, so a later run can't resume a finished release. See `.claude/rules/build-release.md` § "Notarization is resumable" and `docs/plans/2026-07-28-resumable-notarization.md`.

### Overlay (component)
The one shared component every overlay renders through (`components/shared/Overlay.tsx`) — modal, popover, dropdown, command palette, anchored panel, bottom sheet. It centralizes the click-outside-dismiss contract so no individual overlay can drop or mis-wire it: outside-`pointerdown` dismiss + paired-event swallow (the `click` on mouse, or the `touchend` on touch — a touch button that runs its action on `onTouchEnd` and `preventDefault()`s the synthetic click never dispatches a `click`, so the `touchend` is swallowed in the capture phase instead) + anchor exemption (via `useDismissOnOutside`) and Escape (via the *overlay stack*). While open it also makes the UI behind it **inert** — `data-overlay-open` on `<html>` (ref-counted) drives CSS that sets `.app-shell > * { pointer-events: none }` so behind-elements don't hover-highlight or activate (the panels carry `data-overlay-panel` and the opening toggle carries `data-overlay-anchor` — both re-enabled to `pointer-events: auto`, so the panel works and re-activating the anchor closes via its own handler); this is the hover analog of the swallow and applies even to backdrop-less popovers (a dropdown, the control panel). The inert targets `.app-shell`'s children, not `.app-shell` itself, so `.app-shell` stays a real hit target for the outside click that dismisses a backdrop-less popover. Positioning stays with the caller (CSS for modals, `panelStyle` + `backdrop={false}` for anchored popovers); only the contract is centralized. Replaced the older `ModalOverlay` (now deleted), which dismissed but did not swallow and couldn't serve click-through overlays — every overlay renders through `<Overlay>`, so `useDismissOnOutside` + the *overlay stack* have no other callers. See `.claude/rules/frontend.md` § "Modals & Popovers".

### Overlay stack
The central LIFO registry of dismissable overlays (`store/overlayStack.ts`) — every overlay *panel* registers through the `<Overlay>` component (the sole panel registrant since `ModalOverlay` was deleted); the panel-less pseudo-fullscreen mode also pushes an Escape-dismiss entry directly. Each entry registers its `dismiss` on mount and removes it on unmount. Replaces the per-instance `document` Escape listeners that used to race each other and any global key handler; the one capture-phase Escape dispatcher in `useKeyboardShortcuts` (`dispatchEscape`) pops the top entry. Escape policy is non-destructive, in order: dismiss the top overlay → else, if the focused text input opts out via `data-escape-self`, leave it for the element's own Escape handler (used where a blur commits work, e.g. the thread-title editor whose blur saves a rename — blurring on Escape there would save instead of cancel) → else blur a focused text input → else no-op (it never touches the focused thread or discards work). The *close cascade* lives on a separate trigger, not Escape — so a double-Escape on a cascade confirm cancels the dialog, it can't skip a layer.

### Sent receipt
The read-only state the **email confirmation panel** enters after a successful send (`EmailSentReceipt` in `components/email/EmailConfirmModal.tsx`) — the same content-pane panel, showing the recipients, subject, body and attachments that actually went out, a "Sent" chip with the timestamp, and Close as the only action. It is not a separate destination: `markEmailSent` (`store/actions/email-confirm.ts`) rewrites the open `email-confirm` *inline form* in place, stamping `sentAt` and folding the user's edited subject/body into `request`, then `replaceNavState()`s so one send keeps the one nav-history row it already owned (relabelled "Email Sent" by `getFormTitle`). Two consequences follow from `sentAt` living on the form rather than in component state: an already-sent email can never render a Send button again after a remount (a Back/Forward walk, or a reload), and the receipt is the one `email-confirm` overlay `isTransientForm` does NOT drop on reload — a *pending* confirmation is backed by an engine-staged draft that dies with the page, while a receipt has nothing left to resolve and is a real history destination. The panel deliberately does not switch the active menu item (see `openEmailConfirmRequest`); confirming a send used to teleport the user to Settings → Accounts and strand them there.

### Per-thread events bump
The frontend reactivity primitive in `crates/lucidos-app/src/store/threadActivity.ts` that splits SSE fan-out into two channels so a long-running streaming thread doesn't fire every wide `threadMap` subscriber on every token. `bumpThreadEvents(threadId)` increments a lazy-created `Signal<number>` for that thread only (RAF-coalesced); `getThreadEventsBump(threadId)` subscribes to just that thread. Streaming events (`TextStreamed`, `CodingAgentTextStreamed`, `CodingAgentToolCalled`, `ContextCaptured`, …) bump the per-thread signal and do **not** flip `threadMap`. Meta-shape changes (status, title, channel, codingAgent flags, child counts, …) flip `threadMap` and fire the wide subscribers (`attentionThreadCount`, `ThreadDrawer.ThreadList`, every `PromptInput` effect). Focused-thread views (`activeExchanges`, `activeStreamingBuffer`, `ThreadView`'s exchanges memo) subscribe to the per-thread bump and read `threadMap.peek()`. **Contract**: every code path that mutates `thread.events`, `thread.streamingBuffer`, or `thread.pendingUserMessages` MUST pair the mutation with `bumpThreadEvents(threadId)` — the SSE handler at the bottom of `handleThreadEvent` bumps unconditionally; the optimistic-message paths in `chat.ts` (`addPendingMessage`, `removePendingMessage`, `clearStalePendingMessages`, the unreachable-engine fallback) and the `CodingAgentThreadSpawned` branch in `handleGlobalEvent` bump explicitly. Wires same pattern as `composeDrafts` / `draftPresentThreadIds` for compose state.

### MessageOrigin
The Rust enum for *actor*, defined in `crates/lucidos-engine/src/engine/thread_events.rs`. Variants:

- `Device { device_id: String, label: String }` — human at a known device. `device_id` is the TEXT primary key from the `devices` table.
- `Api { user_agent: Option<String>, mode: ActorMode }` — HTTP request without a device id or cross-workspace caller. `mode` defaults to `Human`.
- `Workspace { workspace, thread_id, event_id, user_agent, mode }` — HTTP request from another Lucidos workspace, identified by the `caller_workspace` body field. `mode` carries upstream intent (defaults to `Human`).
- `ThreadLink { thread_id, title, spawning_event_id, mode, direction }` — bidirectional link to another thread in the same workspace. `direction = Parent` means the linked thread spawned the receiving thread; `direction = Child` means a child posting a callback. (Carries `#[serde(alias = "parent_thread")]` so historical rows from the old unidirectional `ParentThread` variant still deserialize; `direction` defaults to `Parent` when missing.)
- `System` — internal projection / housekeeping origin (e.g. `MessageOrigin::system()`).
- `Engine { reason: EngineReason }` — engine-internal action (e.g. `MessageOrigin::engine(EngineReason::HardenRetrigger)`).

Optional on `SystemEvent` variants (`actor: Option<MessageOrigin>`); the four legacy change-event variants carry per-variant `actor` instead. `MessageOrigin::mode()` derives the *ActorMode* used for UI labelling.

### PreEmittedOrigin
The Rust enum in `crates/lucidos-engine/src/engine/chat/process/mod.rs` telling `process_message_with_steps` that the turn's exchange-starter event is ALREADY persisted, so it must not emit its own `MessageReceived`. Two variants, and the distinction is load-bearing rather than cosmetic: `Message(Uuid)` is a message a person or an agent actually sent (the chat API boundary's *emit-before-ack*, the Thread Queue executor's eager child `MessageReceived`) and routes exactly like one the turn emitted itself, so on a live thread it injects as `UserText`, is acknowledged with a `UserPromptInjected`, and arms the Codex redirect interrupt; `EngineReentry(Uuid)` is an engine-internal re-entry anchored to an event the UI already renders (a child-completion wake, a continuation rerun's note, an orphaned injection being replayed) and stays silent, injecting as `WakeFromChild`. It replaced a bare `Option<Uuid>` whose readers inferred "engine re-entry" from "already persisted", an inference that only held while no caller could pre-emit a follow-up on a live thread. `ThreadQueueRequest::SubThread` keeps the plain `Option<Uuid>` on the wire (it is persisted in a `ThreadQueued` payload) and converts at the call.

### Emit-before-ack
The rule that `POST /api/v1/chat/stream` persists a chat follow-up's `MessageReceived` **before** it returns 200, so the ack means "recorded, with its sequence assigned" rather than merely "accepted". Implemented by `LucidosEngine::pre_emit_chat_message_received`, which runs after every validation gate and hands the event id to the spawned turn as a *PreEmittedOrigin*. It is what makes the frontend's *send chain* a real ordering guarantee: the handler otherwise spawns the turn and acks immediately, with the emit sitting behind a Thread Queue slot wait, so a client that waited for the ack could still have the next request's task take the lower sequence. Deliberately self-gating: a brand-new thread, a coding-agent dispatch, a non-human mode, a thread with an open question (the reply becomes `UserQuestionAnswered` and never a `MessageReceived`), and a failed emit all fall back to the turn emitting it. See `docs/plans/2026-07-30-serialize-chat-sends-per-thread.md`.

### Send chain
The per-thread promise chain in `crates/lucidos-app/src/store/actions/chat.ts` that keeps at most one `POST /chat/stream` in flight per thread, so a device's messages reach the engine in the order the user pressed send. The slot is claimed **synchronously** in `enterSendChain` at `sendMessage` call time, not when the POST is issued, because `sendMessage` can await before it gets there (`getWebviewContent()` on the Tauri panel path) and two of those resolve in either order. Links settle rather than resolve-on-success, so one failed send cannot poison the chain, and the wait for the predecessor is bounded by `SEND_CHAIN_MAX_WAIT_MS` because `mutatingFetch` has no client timeout and a hung POST would otherwise swallow every later message on the thread. Its engine counterpart is *emit-before-ack*; without that, the chain narrows the race but does not close it.

### ModelRegistry
The in-memory model→provider routing map, `Arc<RwLock<HashMap<String, ProviderKind>>>` in `crates/lucidos-engine/src/llm/model_registry.rs`. Projected from the `models` config table (`load_from_db`), cloned into `RoutingProvider`, and hot-swapped by the engine's `spawn_models_registry_subscriber` on any `Model{Created,Updated,Deleted}` event — so adding or re-providering a model in Settings → Models takes effect without a restart. `provider_kind_for` resolves a model id with an exact hit, falling back to a prefix heuristic (`gpt-`→OpenAi, `claude-fable`→Anthropic, else Vertex) for ids not in the table (legacy saved prefs). Distinct from the user-facing *model registry* (the `models` table + Settings UI) — this is the runtime cache.

### Per-thread model memory
A Lucidos Agent (chat) thread reuses the *model* and *reasoning effort* it last ran with, instead of snapping back to the account default on each new message. The durable record is the `model` / `reasoning_effort` the backend already stamps on every `MessageReceived`; resolution is `explicit per-request override → the thread's last recorded value → the account preference (chat_model / chat_reasoning_effort) → provider default`, per field, in `PreferenceStore::resolve_chat_overrides_for_thread` (via `last_thread_chat_settings`, excluding the in-flight turn). It is **backend-authoritative** — a follow-up with no override reuses the thread's value for any caller (chat UI, triggers, API). On the frontend the in-thread control menu resolves the same chain (`resolveActiveThreadModel` / `resolveActiveThreadReasoningEffort` in `store/threadModelSelections.ts`) and a pick writes only THIS thread's ephemeral pending override — never the account preference (which stays a Settings → Models default, and the fallback for a brand-new thread). Distinct from the coding agent's per-thread model, which is session-bound via `CodingAgentSettingsChanged`. See `docs/plans/2026-07-03-per-thread-model-memory.md`.

### model-tolerance measure
A change made *only* to compensate for current LLMs making a predictable, recurring mistake — a deliberate, temporary crutch (a forgiving alias, a tolerated wrong name, a fallback that fires on a model error), not something the design needs. Removable by intent — but the bar is the *weakest* model in the *model registry*, not the newest: the measure becomes dead weight only once every routed model has stopped making the mistake, so shipping a stronger default does not by itself retire it. It is one typed category of *temporary measure*, tracked in the umbrella [`docs/temporary-measures.md`](temporary-measures.md) (§ Model-tolerance measures) with a removal condition. Distinct from genuine ergonomics / backward-compat / external-robustness, which stay regardless of model quality. The test: *would we still want this if the model were perfect?* No → it's a tolerance measure. See `.claude/rules/temporary-measures.md`.

### open investigation
A parent entry in the *temporary-measures registry* representing the *reason* one or more measures exist — an unresolved question (e.g. the `ios-pwa-blackout` iOS-PWA black-screen hunt), not a measure itself, so it has no "Lives in" site. Each measure references its parent investigation by a short kebab-case id; closing the investigation surfaces every measure now eligible for removal (search the registry for the id). See `docs/temporary-measures.md` § Open investigations.

### temporary measure
Anything in the codebase that is *meant to end* and carries a *concrete condition for when* — the umbrella concept that generalizes the old model-tolerance crutch. Four typed kinds: temporary measures & workarounds (diagnostics, scaffolding, "workaround until upstream fixes X"); *model-tolerance measures*; feature flags & sunset deprecations (flags/kill-switches awaiting cleanup + back-compat shims with a concrete removal trigger); and *open investigations* (parents — the reason a measure exists). The inclusion test: *is this meant to go away, and is there a concrete condition for when?* Yes → it's a temporary measure, tracked in the *temporary-measures registry* with a removal condition, in the same change it lands. Distinct from permanent back-compat, site-local suppressions (`#[allow]` / `@ts-expect-error` / `eslint-disable`), accepted design decisions (→ `docs/adr/`, `docs/code-review-priors.md`), and open-ended tech debt (→ `docs/plans/`), which are explicitly OUT. See `.claude/rules/temporary-measures.md`.

### temporary-measures registry
The single file [`docs/temporary-measures.md`](temporary-measures.md) that tracks every *temporary measure* and *open investigation*, one row each, under a shared per-entry schema (what · where it lives · why impermanent · removal/resolution condition + how to verify · status-with-history · parent-investigation id for measures). Generalizes the retired `model-tolerance-measures.md`. `/harden` requires a new impermanent thing in a diff (a "remove after X" / "diagnostic-only" / "temporary" comment, a feature flag/kill-switch, a sunset shim, or a `TODO`/`FIXME`/`HACK`/`XXX` marker) to have a row here; `/harden-project` flags rows whose removal condition looks already met and impermanent-looking code missing a row. Removing a measure flips its status to `removed` (kept as history), never deletes the row.

### ProviderKind
The Rust enum (`crates/lucidos-engine/src/llm/model_registry.rs`) naming which backend serves a model: `Vertex` | `Anthropic` | `OpenAi`. Parsed from the `models.provider` column (`ProviderKind::parse`, unknown → `Vertex`). `RoutingProvider` dispatches to the matching `Option<Arc<…Provider>>`; the direct `AnthropicProvider` (api.anthropic.com) is the `Anthropic` arm, added alongside the existing Vertex path.

### Persisted event
A subset of *Event* (see user-facing glossary): past-tense, written to the `events` table by `EventBus::emit`, replayable, visible to projections, matched by triggers. The default flavor.

### Preference catalog
The single source of truth (`crates/lucidos-engine/src/core/preference_catalog.rs`) for the agent-settable *preferences* (user-facing term). A static `CATALOG: &[PrefSpec]` declares each key's scope (`PrefScope::Global` / `Device`), allowed values (`PrefValue`), default, description, and write side-effect (`PrefSideEffect::{None, Language, Timezone, Push}`); a separate `INTERNAL_KEYS` list names known-but-not-settable keys (command guard, backup last-run state, keybindings) with a hint. (The backup *schedule*/*provider*/*retention* ARE settable — they live in `CATALOG`; only `backup_last_run` stays internal.) The `set_preference` tool gates writes against it (reject unknown/internal/invalid); `get_preferences` renders it. NOT consulted for storage — the authoritative value still lives in the `preferences` table. Both write paths (the tool and HTTP `PUT /preferences`) funnel through `LucidosEngine::apply_preference_write` (`engine/preferences.rs`), which reads the catalog only to dispatch a key's side-effect; that chokepoint is permissive about the key (the HTTP/Settings path writes internal keys too), so the catalog *gate* lives in the tool handler, not the chokepoint. Kept in lockstep with `system-knowhow/preferences.md` by a sync test (`.claude/rules/system-knowhow.md`).

### Transient event
A subset of *Event*: past-tense, broadcast over SSE only, never persisted, never reaches projections or the trigger matcher. A trigger on a transient event can never fire — it isn't even allowlistable, because the scheduler's matcher only looks at persisted events. Routing is determined by `ThreadEvent::is_persisted()` / `SystemEvent::is_persisted()`.

### Private-data denylist
The enumerated half of the deterministic private-data guard: the exact tokens (contributor names, employer domain, MDM domain, internal repo/app/project names, personal-document words, family names) that may never appear in a shipping file. Lives **only** in two marker-fenced blocks in `WORKSPACES.md` — the one file the release stubs — because a tracked patterns file that spelled the tokens out would itself be the leak it exists to prevent. `private-data-denylist` holds tokens denied everywhere; `private-data-exceptions` holds the **exceptions list** (below). Its counterpart, the generalizable **shape heuristics** (real home paths under both roots — `/Users/<name>` and `/home/<name>` — and possessive device labels), stays tracked in `scripts/lib/private_data_patterns.sh` alongside the `private_data_load_denylist` loader that reads both blocks. The loader **fails closed** — a missing, marker-less, empty, malformed or uncompilable block makes `private_data_grep_tree` exit non-zero rather than report "clean", and `release-to-lucidos.sh` refuses the push on that status. Rule: `.claude/rules/no-private-data.md`.

### Private-data exceptions list
The `private-data-exceptions` block of the *private-data denylist*: `<ERE token> => <space-separated paths>`, meaning the token is legitimate **only** at those paths. It exists for project identity — a contributor's real name is legitimate as the copyright holder, governance owner, code-of-conduct contact, or credited contributor, and illegitimate everywhere else (fixtures, examples, device labels, home paths, incidental mentions). Each such name is denied outright and its attribution sites enumerated beside it, so the same name anywhere else is a release-blocking hit. Deliberately preferred over narrowing the token to a possessive/path form, which silently permits every other bare use. Each entry is scanned in its own `git grep` pass with its paths excluded.

### Plan marker
Durable enforcement record that the *implementation-plan* skill ran AND the human approved its plan (or that a local fix was acknowledged) before a *Lucidos-source* coding-agent branch's first edit. Modeled on the harden marker: a `planned_branches(repo_root, branch_name, state, plan_path, reason, head_sha, planned_at)` row keyed on `(canonical repo_root, branch_name)`, with three states — **`proposed`** (a `docs/plans/<date>-<slug>.md` file was written and recorded by `lucidos planned mark --plan`, but the human has NOT approved it yet — does **not** satisfy the gate), **`planned`** (the human approved the proposed plan, flipped by `lucidos planned approve`; also any legacy row predating the approval step — satisfies), and **`acknowledged_simple`** (a local fix, recorded by `lucidos planned mark --simple "<reason>"`, no approval needed — satisfies). Only `planned` and `acknowledged_simple` satisfy the gate; `proposed` and an absent row both block. The **human approval step** is conversational: the skill records `proposed`, the coding agent presents the plan to the user, and once the user approves in chat the agent runs `lucidos planned approve` to flip it (a deliberately light-touch, prompt-level gate — the agent runs the flip itself). The gate is binary **satisfying/not** (no `Fresh`/`Stale` re-check like hardening — planning is a settled decision a follow-up commit doesn't invalidate; `head_sha` is diagnostic only). Three enforcement points: the `cc-plan-gate` PreToolUse hook blocks Claude Code's first source edit while the marker is Missing (deny: run the skill) or `proposed` (deny: get approval, then `planned approve`), exempting `docs/plans/` writes and repos without the skill; the shared system-prompt rule reaches *both* Claude Code and Codex (Codex has no PreToolUse hook); and the Apply-time floor in `change_ops/apply.rs` refuses a non-satisfying Lucidos-source change (the hard backstop, and the only hard enforcement for Codex). Engine helpers live in `git_ops/plan_marker.rs` (`PlanMarkerState`, `PlanMarkerState::satisfies_gate` / `PlanMarkerKind::satisfies_gate`, `record_planned`, `approve_plan`, `consume_plan_marker`); the CLI is `lucidos planned` (`mark --plan` / `mark --simple` / `approve` / `state`). App coding-agent threads and external repos are exempt. Consumed on in-session apply (`apply_now`) so a reused branch re-triggers the gate for new work.

### Presence (device_presence)
Transient projection that feeds the PresenceCheck protocol's candidate list. `device_presence(device_id PK, visible_at)` records devices with any visible top-level Lucidos tab; `DevicePresenceStore::candidates` returns the device_ids fresher than 2 minutes (`PRESENCE_STALE_AFTER`). An empty list short-circuits `send_push_to_all_with_app` to `push_allowed=true` without bothering to broadcast the PresenceCheck. The projection comes from transient `SystemEvent`s (`DeviceVisible` / `DeviceHidden`) — never persisted to the events table. Frontend reporter: `device-presence.ts`, heartbeating every 30s while visible. Per-thread focus used to live in a separate `thread_presence` table updated by `ThreadFocused` / `ThreadUnfocused` events; that path was retired once the PresenceCheck pong started reporting `focused_thread_id` live (see `system-knowhow/notifications.md` §3).

### PresenceTracker
The in-memory `Arc<Mutex<HashMap<Uuid, PendingSlot>>>` on `LucidosEngine` that owns in-flight PresenceCheck slots. `expect(notification_id, expected_pongs)` registers interest and returns an `Arc<Notify>`; `record(req)` appends a pong and signals via `notify_one()` once `expected_pongs` are in (so a pong that lands before the fan-out task awaits doesn't lose its wakeup); `collect(notification_id)` drains the slot. Each `expect()` also sweeps slots older than 5 s so a panicking fan-out task can't leak entries. Lives only in memory and is wiped on engine restart; transient by design. See `crates/lucidos-engine/src/api/presence_pong.rs` and `system-knowhow/notifications.md` §3.

### Prose field
A text `<input>`/`<textarea>` holding **natural language the user writes** — the chat prompt, a thread title, a trigger intent or name, an app description, an email subject/body, the free-text prompt dialog — as opposed to the config fields the app is mostly made of (paths, ids, env var names, model ids, API keys, cron expressions, JSON conditions). The distinction exists because `installNoAutofill` (`crates/lucidos-app/src/utils/noAutofill.ts`) stamps `autocomplete`/`autocorrect`/`autocapitalize` = `off` on *every* text field to suppress WebKit's saved-value dropdown; that default protects a config value from an iOS auto-capital but strips a prose field of autocorrection. A prose field spreads `PROSE_TEXT_ATTRS`, a **marker** (`data-prose`) rather than a value: the stamp skips `autocorrect`/`autocapitalize` for it and leaves the browser's own defaults, which already are autocorrect-on and sentence capitalization (`autocomplete="off"` is still stamped, so the dropdown stays suppressed). Marking beats asserting because it never touches Preact's property path — `autocorrect={x}` becomes `el.autocorrect = x`, and since the IDL attribute is a boolean the string `"off"` coerces to `true` and reflects back as `autocorrect="on"`, an inversion this codebase shipped for seven weeks. Turning autocorrect off is therefore the stamp's `setAttribute` alone, never JSX. Pinned by source-scan guards in `noAutofill.test.ts`. See `.claude/rules/frontend.md`.

### Projection
A cached materialized view maintained by EventBus inside `emit()`, in the same transaction as the source event INSERT — `thread_summaries` (from thread lifecycle events), `notifications` (from `NotificationCreated`), `pinned_apps` (from pinning events). The *event store* is the source of truth; projections are recomputable, and consistent with it under read-your-write. See the `EventBus` struct doc-comment in `crates/lucidos-engine/src/engine/event_bus.rs` for the full five-phase pipeline (Validate → Persist → **Project** → CaptureAggregate → PostCommit).

### Front door
The **deployed `lucidos.dev` origin** as a delivery surface in its own right: what the advertised `curl -fsSL https://lucidos.dev/install.sh | sh` actually reaches. It is more than `install.sh`. A piped install has no checkout, so `_source_libs` fetches the helper libs from `${LUCIDOS_INSTALL_URL%/install.sh}/scripts/lib` too, and the publisher rewrites the baked `LUCIDOS_INSTALL_URL` to this origin, which makes `/scripts/lib/*.sh` part of the front door rather than an implementation detail of the repo. **`/uninstall.sh` is part of it too**, and on a sharper edge: `install.sh --uninstall` fetches it from the same origin and runs `exec bash -c "$payload"` on what comes back, while `curl -fsSL <origin>/uninstall.sh | sh` pipes the same bytes straight into a shell, so a soft-404 there does not fail, it *executes the landing page*. Worth its own term because it **regresses independently of any commit**: the *stripped release tree* can be perfect and every install-smoke job green while the origin serves something else entirely. On 2026-07-29 the Cloudflare Pages deploy published `/install.sh` but not the helper libs, and because Pages soft-404s (landing-page HTML at status **200**) `curl -fsSL` succeeded and the installer sourced HTML as shell. Guarded in three independent places, deliberately not folded into one: the publisher uploads + post-deploy-verifies the libs, `install.sh` fails closed on an HTML payload, and `install-smoke.yml`'s **`front-door`** + **`front-door-macos` jobs** run the advertised command against the origin, daily on a cron and on a `workflow_dispatch` whose `origin` input says which front door to test. The post-publish run is that dispatch, fired by the site publisher after `SitePublished`, NOT the `release: published` webhook: the Pages deploy runs outside CI, so the webhook arrives mid-deploy and would verify the previous origin. The front door is **per-platform**, which is why there are two jobs: `install.sh` resolves a different tarball per host triple, so a green `ubuntu:22.04` run says nothing about `aarch64-apple-darwin` or `x86_64-apple-darwin` (the latter being where the landing page sends Intel Mac users, since the DMG is aarch64-only). The macOS job differs only in launch shape (with `launchctl` present `install.sh` registers a launchd job and exits 0 instead of holding the foreground), so it never treats an exited installer as a failure. Since 2026-07-30 those jobs also assert the **uninstall** half in full mode (rungs 5-8): `--list` through both the delegation and the direct piped front door, a data-safe removal that must keep the data dir (and, on macOS, boot out the launchd agent), and `--all --purge` that must really remove the instance data and the shared runtime. Distinct from every other install-smoke job, which tests a *tree* or an artifact built from one. Each of those jobs resolves ONE origin per run, so a fourth job, **`front-door-parity`**, exists solely to compare this front door's *publish route* set against the *RC front door*'s. See also *RC front door*, *publish route*.

### RC front door
The *front door* of a *release candidate*: `https://rc.lucidos.dev` (its own Cloudflare Pages project, behind Cloudflare Access; installer at `/install.sh`, helper libs at `/scripts/lib/`, uninstaller at `/uninstall.sh`), published by the site publisher during the release so the RC's own copy can be gated before anything reaches the real path. `install-smoke.yml`'s `front-door` and `front-door-macos` jobs run against it in **payload mode** on every push to `rc/**`: rung 1 only, meaning fetch the served installer, parse its helper-lib list and lib base out of it, fetch those plus the served uninstaller, assert every payload is shell rather than the soft-404 landing page, then stop green. The uninstaller is in that list so an RC is gated on both halves of the advertised experience. It deliberately does **not** install. An RC `install.sh` bakes `LUCIDOS_DEFAULT_VERSION=<rc version>` and resolves its tarball to `…/releases/download/v<ver>/…`, but during an RC that tag does not exist (Phase A publishes only the `rc-<ver>` prerelease with the DMG + updater `.sig`; headless tarballs live solely on real `v*` releases), so a full `curl … | sh` would 404 every run and the gate would be permanently red. Payload mode loses nothing: the soft-404 class the gate exists to catch is entirely a payload question. Three rules keep its green honest. The lib base derived from the served installer must equal exactly `<origin>/scripts/lib` (fatal here, since it is the only rung); the served uninstaller must pin its own `LUCIDOS_UNINSTALL_SELF_URL` and lib base at this origin too, or a piped uninstall silently runs GitHub main's copy; and the served installer's baked version must match the `rc/<version>` branch, so the previous RC's copy at the same URL cannot pass. Because it and the production front door are published by two separate route-discovery paths, their *publish route* sets can drift; `front-door-parity` is what catches that.

### Publish route
Any path a piped run would curl back **from its own origin** and execute, which is the whole test for whether something belongs on a *front door*. Six today: `/install.sh` (the dash re-exec re-fetches itself), `/uninstall.sh` (`install.sh --uninstall` execs it, and a direct pipe runs it), and the four `/scripts/lib/*.sh` helpers the two scripts source (`stage_runtime.sh`, `headless_tarball.sh`, `install_common.sh`, `service.sh`). A missing publish route is not a 404: Cloudflare Pages answers an unknown path with the landing page at status **200**, so `curl -fsSL` succeeds and the shell runs HTML. The set is **enforced in two places that can drift** (the site publisher discovers routes separately for production and for the *RC front door*), which is exactly how `/uninstall.sh` reached production on 2026-07-30 and not the RC, surfacing only on the next morning's `rc/0.18.0` push as three red payload legs. `install-smoke.yml`'s **`front-door-parity`** job is the repo-side guard: daily, it derives each origin's route set from that origin's OWN served scripts (`scripts/lib/front_door_parity.sh`) and fails when production serves a route the candidate does not, naming it. The reverse direction is a warning, since an in-flight candidate legitimately leads production until publish. The structural fix, one discovery path parameterised by destination, is workspace-side.

### Release candidate (rc)
The stripped orphan commit a release is gated on, and — after *promotion* — the exact commit that becomes the mirror's `main`. Phase A (`release.sh --verify-build`) builds it with `release_tree_build`, scans it, commits it with `release_tree_commit`, and force-pushes it to `refs/heads/rc/<version>` on the `lucidos` remote (which fires `install-smoke.yml`'s clean-machine source install); the staged DMG + updater `.sig` then go onto the `rc-<version>` **prerelease** at that branch (which fires `dmg-verify`). Its SHA is recorded as `RC_COMMIT` in the verify-build state and pinned locally at `refs/release-candidates/<version>`. Deterministic: identity + dates are inherited from the internal release commit, so re-deriving it yields the same object. Never a raw branch push of the internal tree — that shipped `docs/plans/` and the release scripts to the public mirror on 2026-07-28 (ADR 0024).

### Stripped release tree
The only tree Lucidos ever publishes: `HEAD` (or the release commit) minus every `RELEASE_TREE_EXCLUDE_PATHS` entry, with `WORKSPACES.md` replaced by the public stub, scanned by `release_tree_scan` (fail-closed on a hit AND on a denylist that won't load). Built by `release_tree_build` in a throwaway index, so the working tree and real index are untouched. `scripts/lib/release_tree.sh` is the single definition — the *release candidate* push and `release-to-lucidos.sh` both call it, because a duplicated exclusion list is how internal content leaks. The lib and its test exclude themselves.

### Promotion (release)
Phase B's publish step: force-pushing the **already-validated** *release candidate* commit object to the mirror's `main` and tagging it `v<version>` **by SHA** — as opposed to rebuilding an equivalent tree at publish time, which would ship an object CI never saw. Gated by `release_promote_preflight`, which refuses when no `RC_COMMIT` was recorded, when `rc/<version>` is absent from the mirror, when it **moved** (someone re-pushed ⇒ stale gate result), when the staging manifest's `source_commit` ≠ the worktree HEAD, or when a staged artifact's sha256 drifted. Driven by `release-to-lucidos.sh --promote-rc <sha>`; `release.sh --push-rc <version>` re-arms the gate without a rebuild. See ADR 0024. The source-side half that follows it is the *release landing*.

### Release commit
The **main-line** commit of a release: the one bumping `RELEASE`, `CHANGELOG.md` and `install.sh`, created on `release/<version>` in the Phase A worktree off `main`. Distinct from the *release candidate*, which is the parentless stripped commit built **from** it — same release, two objects, and the *release tag* names a different one on each remote. `RELEASE` is the load-bearing file: the site publisher reads the version from the local checkout's copy, so a release whose commit never reaches `main` leaves the site advertising the previous version (the v0.17.0 incident).

### Release landing
Getting the *release commit*'s bump onto the live checkout's `main` at publish time — **fast-forward** when `main` is still an ancestor, **cherry-pick** of that single commit when `main` moved during the (40+ minute) build, and a **hard failure** (after `cherry-pick --abort`, leaving nothing wedged) when that conflicts. Only operator state — the checkout is not on `main`, or is dirty — still skips, and then the recovery commands are reprinted in a `STILL OWED` block at the very *end* of the run. It replaced a fast-forward-or-warn-and-continue step whose warning nobody read. `release_main_land` in `scripts/lib/release_main_sync.sh`; called with the *release tag* creation and the `origin` push through one `settle_source_side` entry point shared by Phase B and the one-shot. See ADR 0029.

### Release tag (per-remote)
`v<version>` names a **different object on each remote, deliberately**. On the public mirror it names the *release candidate* orphan, because the GitHub Release and every download URL resolve through it — so it is pushed **by SHA** (`push --force <remote> <commit>:refs/tags/<tag>`), touching no local ref. Locally and on `origin` it names the *release commit* on `main`, which is what gives it ancestry. Creating the mirror's tag locally first is what left 26 of 27 `v*` tags outside main's history, made `git describe --tags main` report `v0.9.6-4946-gfb4b344cf`, and rendered every `PREV_TAG` guard in `release.sh` vacuous. The local tag is annotated, idempotent (an already-correct one is left byte-identical so the `origin` push stays a no-op), and only ever created at a settled commit — so "the tag exists" implies "it names a real main-line commit". See ADR 0029.

### LucidosReleased
The domain event the release spine emits once a release is public — `{version, commit, tag}`, plus `dmg_pending: true` on a *deferred-DMG release*. Emitted by `release-to-lucidos.sh` via `emit_lucidos_released` (`scripts/lib/release_events.sh`); it also marks every Release Cockpit step done. `dmg_pending` is written **only when true**, so an ordinary release's payload stays byte-identical to what existing consumers already parse and "absent" reads as false in each of them. The workspace's `bump-dmg-link-publish-on-release` trigger keys off it: pending ⇒ leave the Download-for-Mac link on the last notarized build and add the "newer version available" notice; otherwise ⇒ bump the link and remove the notice.

### ReleaseDmgNotarized
The domain event `release.sh --attach-notarized` emits after the stapled DMG has replaced the pending asset on a published release — `{version, tag, dmg, submission_id}`. It is what re-points lucidos.dev's Download-for-Mac link and clears the pending notice, and it is emitted **only after the upload succeeds**, so the link can never point at an asset that is not yet in place. Consumed by the same `bump-dmg-link-publish-on-release` trigger as *LucidosReleased*, through one reconciler that branches on `dmg_pending` rather than on which event fired.

### Request_id
The `request_event_id` field that links a request event (e.g. `MessageReceived`) to all its terminal events (`ResponseGenerated`, `ResponseCanceled`, `ResponseAborted`, `ResponseFailed`). Carried via `EventMeta::request_event_id`. Used by the UI to group a turn and by the engine to settle stuck-running threads.

### RiskLane
The *command guard*'s classification of a single bash/python command (`RiskLane` enum in `engine/command_guard.rs`). Four lanes (ADR 0002): `Safe` (run), `Catastrophic` (hard-block), `ReversibleDanger` (in-workspace destruction), `IrreversibleDanger` (ask / trigger grant). The static *command classifier* only ever settles `Safe` and `Catastrophic`; the LLM *judge* produces `Safe` / `ReversibleDanger` / `IrreversibleDanger` for the ambiguous middle. `ReversibleDanger` takes a *command checkpoint* (snapshot + one-click Undo, ADR 0002 Phase 4) and runs; on the `IrreversibleDanger` lane the judge also tags a *SideEffectCategory* used for the trigger side-effect grant.

### resolveThreadActions
Frontend (`store/actions/threadActions.ts`) enrichment tier over the codegen'd `availableThreadActions`. Feeds `has_unsent_draft` from the live `composeDrafts` signal (fresh, ahead of the 250 ms compose debounce), applies the external-repo carve-out (a CC change that can't merge into a foreign repo → Archive instead of Apply/Discard), and maps each bare `Action` into a *TaggedAction* `{ kind, category, label, tooltip?, invoke }` whose `invoke` encapsulates the confirm + handler. Both the per-thread buttons (WaitingBanner close buttons, PromptInput Save/Unsave toggle) and the *close cascade* render/drive from these, so a shortcut can only invoke an action whose button is currently available (no enablement drift). The `available_*` / `resolve_*` verb seam marks the DB-vs-client boundary: see *available_thread_actions*.

### resolveGlobalActions
Frontend composer (`store/actions/threadActions.ts`): the top overlay-dismiss action (when the *overlay stack* is non-empty) followed by the focused thread's *resolveThreadActions*. The single "what can the user do right now, globally" selector — the Escape dispatcher consults its dismiss action, the close cascade its `close`-category layers.

### Cron slot
One scheduled occurrence of a *trigger*'s cron expression — the 07:45 of `0 45 7 * * *`, on a given day, in the trigger's timezone. The unit the scheduler dedupes on: a slot fires at most once, however late. A run counts as having served slot S if its *recorded run time* is at or after S, so a 07:49 fire of the 07:45 slot means the 07:45 slot has run. Distinct from the *run* itself, which is the execution that serves the slot.

### Missed-slot catch-up
The scheduler's startup path that fires a *cron slot* whose scheduled time has already passed, when the engine was down, asleep, or restarting across it (`check_and_execute_missed` in `crates/lucidos-engine/src/scheduler/task_runner.rs`). Bounded by `MISSED_TASK_GRACE_MINUTES` (60): only a slot missed within the last hour is caught up. Runs on every task-runner registration — engine start, `TriggerCreated`, `TriggerUpdated`/`TriggerEnabled`, and the health monitor's crash restart — so it is the single choke point every double-fire path passes through. **Fails closed** (`catch_up_decision`): it fires only on a positive showing that the slot is due — no run at or after the slot, and the trigger already existed then. An unreadable run history, an absent `last_run`, or a slot older than the trigger all skip. The no-run half is exact (it compares *recorded run times*, engine clock to engine clock); the trigger-already-existed half is best-effort, because `TriggerCreated` carries only a DB-clock timestamp — see `docs/code-review-priors.md`.

### Recorded run time
The instant the *engine* says a *trigger* ran, on the engine's own clock: `chrono::Utc::now()` stamped by `record_trigger_executed` into `TriggerExecuted.payload.last_run`, and rebuilt into `TriggerConfig.last_run` by `replay_trigger_events`. Deliberately **not** `events.created`, which is the Postgres server clock. The distinction is load-bearing: the *missed-slot catch-up* compares run times against slots it derived from the engine clock, and mixing the two clocks caused the 2026-07-29 double-fire (a macOS sleep left the containerized Postgres clock 280 s behind, so a run landed timestamped *before* the slot it had just served). `events.created` survives only as a fallback for legacy rows with no payload timestamp. See `docs/plans/2026-07-29-cron-slot-catch-up-double-fire.md`.

### Scheduler blocklist
The `ThreadEvent::is_per_token_streaming` predicate (`crates/lucidos-engine/src/engine/thread_events.rs`) consumed by the scheduler subscriber's `BusEvent::Thread` arm in `crates/lucidos-engine/src/scheduler/mod.rs`. Filters out per-token streaming variants — today: `TextStreamed`, `Thinking`, `CodingAgentTextStreamed` — before they reach the trigger matcher. Every other persisted `ThreadEvent` flows through and is subscribable via `on_event:`. Triggers wired to a blocked variant validate and persist but **never fire**.
See also: `system-knowhow/thread-events.md` § "Today the scheduler uses a blocklist", `.claude/rules/system-knowhow.md`.

### SideEffectCategory
The kind of irreversible real-world side-effect a command may perform (`SideEffectCategory` enum in `engine/command_guard.rs`): `Email`, `ExternalApi`, `CloudCli`, `OutOfWorkspaceDestruction`, `Other`. Wire form is snake_case (`email`, `external_api`, …). Only meaningful for the `IrreversibleDanger` *RiskLane*: the *judge* tags each irreversible command with one (`static_side_effect_category` derives it for the shapes the static fallback recognises; unclassifiable → `Other`). It rides on `JudgeVerdict` / `JudgedClassification` and gates the trigger *side-effect grant* (`TriggerConfig.side_effect_grant: Vec<SideEffectCategory>`) — an unattended trigger runs an irreversible command only if its category is granted, else the run fails. The **same category + grant also gate the coding-agent permission flow** (`engine/cc_permission.rs`): an unattended (trigger-rooted) coding-agent thread classifies each permission request with `classify_coding_agent_request` (reusing `static_classify`/`fallback_classify` — no judge), then `decide_unattended` allows benign requests, allows a `SideEffect(cat)` iff `cat` is in the inherited grant, and denies catastrophic / ungranted requests — denying the single request rather than failing the run. Interactive-vs-unattended + the inherited grant come from `resolve_attend_mode` (walks the spawn tree's `MessageOrigin` chain to its root trigger). User-facing concept: *side-effect grant* in `system-knowhow/glossary.md`.

### Session allow
A per-thread permission grant — what the **"Allow for this thread"** button on a permission card records. `AllowScope::Session` in `engine/claude_code.rs`, cached in `PermissionState::session_allows: HashMap<Uuid, HashSet<String>>`. Distinct from the `Narrow` / `Broad` scopes, which persist a `--allowedTools` pattern to `~/.lucidos/cc-allowed-tools` (or `agent-allowed-commands` / `mcp-allowed-tools` for the other lanes) and only work for tools Claude Code actually respects; a session allow is checked **inside the engine, before the agent's own gate**, so it covers every tool and every path — including CC's protected `.claude/` and `.git/`. The pattern is produced by `derive_allow_pattern(.., AllowScope::Session)` and matched exact-string against the same derivation on later prompts: per-file for `Edit`/`Write`/`NotebookEdit` (`Edit(<path>)`), first-token for commands (`Bash(git:*)`), plugin-scoped for `Skill`, bare tool name otherwise, and *none* for Codex's `file_change` (its input carries no stable identifier, so one click would blanket-approve every future out-of-sandbox write).
**Durable, despite the in-memory cache.** The grant is persisted as the resolution event's `persist_scope: "session"`; `cc_permission::hydrate_session_allows` refills a thread's set from the event store on the first prompt after an engine restart, re-deriving the pattern rather than storing it a second time. Only `allowed: true` + `persist_scope: "session"` rehydrate. Implemented for the coding-agent lane; the *command permission card* lane shares the struct but not yet the hydration (ADR 0002, 2026-07-30 addendum).

### Signer
A WebAssembly module that signs outbound proxy requests with credentials (HMAC, OAuth, vendor-specific). Loaded by the `WasmSignerLayer` in the proxy pipeline. Installed under `data/auth-modules/` as a `.wasm` + optional *signer manifest* sidecar — see user-facing *auth module*. Real-artifact tests live in `crates/lucidos-e2e/tests/wasm_signers.rs`; inline-WAT tests live in `crates/lucidos-engine/tests/proxy_wasm_engine.rs`.

### Superseded draft
A compose draft the server no longer holds **and** whose exact content — trimmed text plus image hashes — has already been submitted to its thread **since this device last touched it**. Both halves are load-bearing: ordering (the *draft edit watermark*) covers the ordinary case, and server state (`serverDraft` — this device's knowledge of what the server holds, written ONLY where the server reports its current compose state: a PUT ack, a thread-summary snapshot, a `ThreadComposeChanged`) covers the case ordering cannot see, where a device that re-typed the text while still behind a peer's submission has a stale watermark but its own PUT re-filled the draft server-side. A thread event never writes `serverDraft` even though the projection clears compose in the same transaction as `MessageReceived` — an event can be delivered long after it was written (lagging stream, throttled tab, replay on wake), so it is no evidence of what the server holds now. The submitted-input set is closed: `MessageReceived`, `UserQuestionAnswered { FreeText }`, and `UserQuestionAnswered { MultiSelected }` carrying typed text (the free-form answer path never emits `MessageReceived` — `chat/process/run.rs` reroutes typed text straight to the answer). Agent- and engine-authored entries (`UserPromptInjected`, streaming, tool events) are never submissions. Content match alone is deliberately **not** the test, because posting the same text many times must stay possible: ordering against the *draft edit watermark* is what distinguishes "the draft that got sent" from "the same text, deliberately typed again afterwards". A superseded draft is not unsent work, so it is dropped by every inbound clear path (`hasUnsentLocalDraft` in `store/actions/compose.ts` returns false for it) and actively cleared by `clearSupersededDraft` on the paths that carry no clear of their own — the free-form answer, and event replay on wake / SSE reconnect. Server-side counterpart: **every projection arm that empties the compose fields announces it** with a `ThreadComposeChanged` reporting the emptied state (`compose_cleared_broadcast`) — `MessageReceived`, and `UserQuestionAnswered` when the stored draft is exactly what was submitted (text equal, no attached images, since an answer carries none). Neither path has a compose PUT of its own to announce it, so without the broadcast a peer mirroring the draft would keep it until its next thread-summary reload.
See also: `docs/plans/2026-07-28-superseded-compose-drafts.md`.

### Draft edit watermark
The **server** timestamp captured whenever this device edits a compose draft (`composeEditWatermark` in `store/actions/compose.ts`, stamped by `markLocallyEdited` from the thread's `meta.updatedAt`): the newest `thread_summaries.last_activity` the device had seen for that thread at that moment. It is the ordering reference a *superseded draft* is decided against — a submitted user input counts as evidence only when its server `created` is **strictly** newer. Both sides of that comparison are server-sourced, so client clock skew can never mis-fire the clear, and re-typing text that was just sent is safe because the fresh watermark already sits at or after that submission. Absent watermark = this device never authored the draft, so nothing can supersede it.

### Source of truth
PostgreSQL (the `events` table + projections) plus the filesystem (`data/artifacts/`, `data/apps/`, `data/knowhow/`, `data/triggers/`, `data/config/`, `data/auth-modules/`, `data/scripts/`). In-memory state is **cache or active runtime only** — the engine must be restartable at any time without losing user-visible state.
See also: `CLAUDE.md` § "Engine Statelessness".

### SystemEvent
The workspace-wide event enum. Each variant is its own `SystemEvent::Variant` — grouping is provided by `aggregate()` ("trigger", "app", …), **not** by an `event_type: String` discriminator. `DomainEvent` is one variant among many; never use it as a generic wrapper. Every variant is past-tense (the events-only model — see user-facing *Event*); persistence is set per-variant via `SystemEvent::is_persisted()`.
See also: `.claude/rules/rust.md` § "System events are individual variants".

### TaggedAction
Frontend-only enriched action object produced by *resolveThreadActions*: `{ kind: Action | 'dismiss_overlay', category: 'close' | 'primary' | 'save' | 'dismiss', label, tooltip?, invoke }`. `category` drives button styling and lets the *close cascade* target only `close`-layer actions (so it can't fire an unrelated action by accident); `invoke` runs the action, opening a confirm where the action warrants one. The UI shell of the `Action` enum that *available_thread_actions* returns bare.

### ThreadQueueExecutor
The *Thread Queue* manager's execution seam (`crates/lucidos-engine/src/engine/thread_queue/executor.rs`): `prepare` (admission-time hook, awaited inline — the sub-thread kind emits its eager `MessageReceived` here so the parent's `active_children_count` increments before the spawning tool call returns) and `execute` (run the entry's work; the manager completes the capacity slot when it resolves, panics included). Production installs `EngineThreadQueueExecutor` from `LucidosEngine::set_self_arc`; tests install gated mocks so admission mechanics are testable without an LLM.

### ThreadQueueRequest
The serializable description of one background spawn, persisted verbatim in the `ThreadQueued` event payload and the `thread_queue.request` column so a restart can re-fire entries that never ran to completion. Variants: `EventTrigger`, `Cron`, `SubThread` (the `run_thread` tool), `CodingAgent` (the `run_claude` tool), `AgentChat` (agent/engine-mode `POST /chat/submit` starting a new thread — cross-workspace tasks, `lucidos spawn-thread`). Images travel as content-addressed blob hashes, never inline base64. `kind()` maps a request to its capacity bucket (`ThreadQueueKind`: `event-trigger` / `cron` / `sub-thread` / `coding-agent`).

### thread_queue (projection table)
The *Thread Queue*'s persisted **background** state: one row per live background entry — `status = 'queued'` (waiting) or `'admitted'` (the persisted active-session record). Event-sourced from `ThreadQueued` (upsert; the boot sweep re-queues by re-emitting with `requeued: true`) / `ThreadQueueAdmitted` (status flip) / `ThreadQueueDropped` + `ThreadQueueCompleted` (row delete) in `event_bus_projection_system.rs`. Rows are deleted on completion — the events table keeps the audit trail. Rebuilt into the manager's in-memory queue at boot by `recover_persisted_entries` (before the scheduler starts, so per-trigger FIFO holds across restarts). *User slots* are NOT rows here — see *user slot (Thread Queue)*.

### user slot (Thread Queue)
A user-initiated occupant of the shared capacity pool (a chat response or user-typed *coding-agent thread*), acquired via `ThreadQueue::acquire_user_slot` and held by a `UserSlotGuard` (RAII — releases + drains on drop, even on panic). Prioritized but not exempt (ADR 0008): it counts toward `max_concurrent_total`, drains ahead of background, ignores per-kind/per-trigger caps, and the acquire call *awaits* a free slot at true pool-max. Lives **in-memory only** in the manager's `user_active` / `user_queued` (not the `thread_queue` table) — ephemeral runtime that a restart discards rather than re-firing. The chat handler's spawned task holds the guard across `process_message_with_steps`. Merged into the panel API as `kind: "user-chat"`; the transient `ThreadQueueChanged` event (fieldless, never persisted) refreshes the panel when only user-slot state moves. `reserved_background` (on the *capacity policy*) is the floor background reclaims ahead of user slots so priority can't starve triggers/cron.

### TaskOutcome
How a reaped child process ended, as a typed enum (`crates/lucidos-engine/src/core/shell.rs`): `Exited(i32)` | `Signaled(i32)` | `Unknown`. Replaces the loose `exit_code: Option<i32>` that used to be threaded through the background-task machinery, which conflated four distinct states — exited 0, exited non-zero, died on a signal, and "the engine never learned the status" — so two of them collapsed onto a number an LLM reads as a normal exit. `exit_code()` returns `Some` **only** for `Exited`; `signal()` only for `Signaled`; `describe()` renders the single phrase (`"exit code 101"` / `"killed by SIGKILL (signal 9)"` / `"exit code 141 (probable SIGPIPE)"` / `"exit code unknown"`) that the `bash_output` JSON, the `BackgroundBashCompleted` payload, and the background-task completion summary all share, so those three LLM-facing surfaces cannot disagree. Nothing coerces an unavailable status to `0` or `-1`. Only the *shell's own* death is `Signaled` — a signal that kills a stage inside its pipeline comes back as an `Exited(128 + signum)`, which `describe()` decodes with a `(probable SIGNAME)` hint (same range and wording as `runtime::claude_code::format_exit_status`, with which it shares one `signal_name` table). See also *pipefail shell*.

### pipefail shell
The interpreter engine-spawned shell commands run under (`core::shell::command_shell`): a resolved `bash` invoked with `-o pipefail`, falling back to `/bin/sh` with a logged warning where no bash exists. `pipefail` is load-bearing rather than cosmetic — a POSIX shell reports the exit status of the *last* stage of a pipeline, so `cargo clippy … | tee build.log` returned `tee`'s `0` and a build that exited `101` reached the agent as a clean success (the 2026-07-26 nightly hit this four times in one pipeline, and every step had to cross-check a sidecar `.ec` file to catch it). What `pipefail` guarantees precisely: the pipeline's status is that of the *rightmost failing* stage, and `0` only when every stage succeeded — so a failing stage can never be masked by a later succeeding one, though with several fallible stages the reported code doesn't identify which failed first. Applied at all three shell call sites: `run_bash`, the *background task* registry, and trigger/scheduled scripts. Accepted consequence: a producer SIGPIPE'd by an early-closing consumer (`yes | head -1`) now reports failure instead of `0` — as exit code `141`, since the shell exits normally carrying `128 + signum` when a *pipeline stage* (rather than the shell itself) is signalled, which *TaskOutcome* renders as `exit code 141 (probable SIGPIPE)` rather than a bare number.

### ThreadEvent
The per-thread event enum (`crates/lucidos-engine/src/engine/thread_events.rs`). Every variant is past-tense (the events-only model — see user-facing *Event*); the `is_persisted()` method routes between *persisted event* and *transient event* on emit. Variant added/removed/renamed, payload changed, persistence flipped, or alias added → MUST update `system-knowhow/thread-events.md` in the same change (and `coding-agent-events.md` if the change touches `CodingAgent*` / `UserQuestion*` / `CodingAgentPermission*`).

### Worktree
An isolated git worktree under `<workspace>/.lucidos/worktrees/` where an *agent session* runs. All edits, builds, and test runs stay inside it; scripts resolve paths via `SCRIPT_DIR` so they pick up the worktree's code automatically. Cleaned up by Apply, by the `ExitWorktree` CC tool, or by the background `worktree_cleanup` worker — but that worker's reclamation is **retention-gated**: a non-archived thread's worktree is kept fully warm (no artifact stripping, no removal) while free disk stays above `FREE_DISK_SOFT_BYTES`, so reopening the thread reuses the warm tree instead of paying a cold rebuild. Reclaim runs only once the thread is *archived* (the explicit "done" signal) or disk drops below the soft threshold; live sessions and *stranded worktrees* are handled outside the gate. For *app coding-agent threads*, the worktree is a sparse-checkout (cone mode) of the workspace git narrowed to `data/apps/<id>/` (see *app worktree*); for Lucidos-internal and external-repo sessions, it's a full checkout of the relevant git.

### Worktree-pinned stack
A long-lived dev stack (gateway + engine + served `dist/`) whose paths resolve inside a
*worktree* instead of the real checkout — `LUCIDOS_ENGINE_BIN`, `LUCIDOS_STATIC_DIR` and the
gateway binary all under `<workspace>/.lucidos/worktrees/<thread>/`. A broken state, never a
valid configuration: a worktree is a throwaway copy pinned to ONE commit, so the stack serves
that commit's engine and frontend forever while the checkout-level `vite build --watch`
republishes the real checkout's `dist/`, which the pinned stack never reads. The symptom is
silent — every frontend-only *Apply* appears to do nothing (the 2026-07-26 incident, where the
pinning worktree had even been pruned from git's registry). Self-perpetuating without the
guards: `spawn_engine` inherits the gateway's env into every engine it spawns, and
`reload_gateway` re-execs onto the worktree binary. Refused at launch by
`assert_stack_not_worktree_pinned` (`scripts/lib/workspace.sh`) and at three gateway sites, with
`LUCIDOS_ALLOW_WORKTREE_STACK=1` as the sole opt-out (set by the e2e harness, whose workspace is
disposable). When an Apply strands anyway, the engine emits `FrontendUpdateStranded`. See
ADR 0021 and `docs/plans/2026-07-26-worktree-pinned-stack-guard.md`.

### App worktree
The sparse-checkout *worktree* that backs an *app coding-agent thread*. Created by `git worktree add --no-checkout <path> -b <branch> main` against the workspace git, then `git sparse-checkout init --cone` + `git sparse-checkout set data/apps/<id>` materialises only that app folder plus top-level files (workspace `.gitignore`). Path: `<workspace>/.lucidos/worktrees/thread-<short>/`. Branch: `claude-code/app/<id>/<ts>-<uuid>`. *Apply* ff-merges the branch into the workspace git's `main` and emits `AppUiRefreshRequested` if any iframe-bundled file changed; no push to any remote (workspace git is local by default). Lifecycle helper: `git_ops::create_sparse_app_worktree`.

### Stranded worktree
A *worktree* on disk whose git admin dir (`<repo>/.git/worktrees/<name>`, pointed at by the worktree's `.git` link file) no longer exists — typically from an interrupted `git worktree remove` or a `git worktree prune` that dropped the admin entry while the working dir survived. Every `git` invocation from it then fails with `fatal: not a git repository`, so the cleanup worker's git-based tiers (which lean on `git status` / `git rev-parse`) can't act and `remove_worktree_and_optionally_delete_branch` early-returns. Detected by `worktree_cleanup::worktree_git_admin_missing` (conservative: only `true` when the link target is positively gone, resolving relative gitdirs against the worktree) and removed by `remove_stranded_worktree` (subpath-guarded plain `remove_dir_all`, never touches branch refs — committed work survives in the main repo's branch) after a fixed `STRANDED_GRACE` that does not accelerate under disk pressure. The **resume path** guards against the same hazard from the other side: `git_ops::is_live_worktree_at` (used in `spawn_context`) treats a recorded worktree as reusable only when `git rev-parse --show-toplevel` resolves to the path itself — a stranded tree instead resolves *upward* to the enclosing workspace data repo, so the spawn `clear_stranded_worktree_dir`s the residue and recreates rather than running Claude Code against the data repo. Distinct from an *orphaned temp worktree* (`harden-`/`apply-`/`merge-` left by a crashed apply/harden/merge flow), which is swept separately gated on its change row's status.

### Stale resume
A `--resume` (CC) / `thread/resume` (Codex) that could not attach to the conversation it named — the persisted session id is gone (pruned transcript, agent version upgrade, a mid-flight `CLAUDE_CONFIG_DIR` switch relocating the store; see *account pin*). The recovery is always the same: shadow the dead id with `SessionEnded{StaleResume}` so no later lookup reuses it, keep the worktree and branch, and re-spawn ONCE with no resume id and the conversation reconstructed into the prompt (`prepend_reconstruction`). Detected two ways, in `is_stale_resume_signal` / `is_definitive_session_not_found`: the agent's explicit "no conversation found" error, or — only when the attach was **not** confirmed — an empty, activity-free first Result. A confirmed attach (the agent's `Init` echoes the id we asked for; a failed resume yields a different one) vetoes the second, output-shape inference outright, which is what stops a healthy-but-silent turn being killed.

`SessionEnded{StaleResume}` is the one `SessionEnded` reason that does NOT settle the thread — the projection stays `running` across the retry window so the UI doesn't flash "Aborted". That makes the retry **mandatory** at every call site: a caller that merely logs `STALE_RESUME_ERROR` leaves a thread `running` with no subprocess and no watchdog (the stale-resume arm also drops the `agent_sessions` entry, the only map *external watchdog* scans) — recoverable only by a user click. Distinct from a *phantom session*, which is a live-looking map entry with no run loop; a stale resume leaves no entry at all.

### CodingAgentKind
Rust enum (`Lucidos | App | External`) discriminating the *coding-agent thread* flavor. Serialized as snake_case on `SessionStarted.coding_agent_kind` and persisted in `thread_summaries.coding_agent_kind`. Distinct from `CodingAgent` (which picks the backend product — Claude Code or Codex); a thread of any kind can run on any backend. The `apply_change` path reads it to decide whether to run the `/harden` gate, whether to gate engine restart via `files_require_restart`, and whether to emit `AppUiRefreshRequested` after a successful merge.

### Web search backend
One implementation of the `WebSearchProvider` trait (`llm::web_search`) — the search facility a single configured LLM provider exposes. Three exist: `vertex-grounding` (Gemini with Google Search grounding, pinned to Vertex's *global* endpoint because grounding is a global-endpoint feature and the chat region may serve no Gemini models), `anthropic-server-tool` (the `web_search` server tool on `/v1/messages`, tool version paired to the model family — `web_search_20260209` on Opus 4.6+/Sonnet 4.6+, `web_search_20250305` elsewhere), and `openai-responses` (the `web_search` tool on the Responses API). Each returns the same shape: answer text, then a numbered `Sources:` list. `Ok` means the backend answered — *including* a legitimate "no results"; `Err` is reserved for availability failures, which is what the *web search chain* falls through on. See ADR 0023.

### Web search chain
The ordered set of *web search backends* the engine will try for one `web_search` tool call (`llm::web_search::WebSearchChain`). Resolved over the **configured provider set**, deliberately *not* over the chat model's provider — search is a background capability like memory extraction, and that decoupling is what lets a user on OpenRouter or a local endpoint (neither of which has a search tool) still search via another configured provider. Fixed order `vertex-grounding → anthropic-server-tool → openai-responses`: Vertex first so existing workspaces are unchanged, Anthropic before OpenAI because only OpenAI's charges a per-call fee on top of tokens. Held on the engine behind the same swappable handle as the LLM provider and rebuilt by the same credential subscriber, so adding a key enables search with no restart. An empty chain returns `NO_SEARCH_BACKEND`, naming the three search-capable providers and where to add one. See ADR 0023.

### Update phase
One named step of a **packaged** app update, and the wire contract between `crates/lucidos-app/src/updater.rs` and the page. Serialized internally-tagged on `phase` with kebab-case values — `checking`, `downloading` (carrying `downloaded` plus a nullable `total`), `verifying`, `installing`, `restarting-services`, `relaunching`, and the two terminal frames `cancelled` / `failed` — and delivered on the `app-update-progress` Tauri event. Mirrored in TypeScript as the `AppUpdateProgress` discriminated union (`utils/tauri.ts`), whose in-flight subset `AppUpdateRunning` is what `appUpdateNarration` maps to a sentence, a determinate fraction, and whether a cancel is still honest. Two rules travel with it: frames are **throttled at the source** (one per percentage point, or per MiB when the size is unknown; first chunk and final byte count always sent), and a **null `total` must never be rendered as a percentage** — an unknown size shows bytes alone. The user-facing half of the same concept lives under *New version available / Switch to new version* in `system-knowhow/glossary.md`. Distinct from the gateway's *boot phase* (`crates/lucidos-gateway/src/boot_phase.rs`), which narrates the workspace boot AFTER the client relaunches; the two are consecutive halves of one update, not the same mechanism.

## When to add a term

Add it here if it's dev-only — engine plumbing, DB schema, test infrastructure, build tooling, CC mechanics. If users (or the workspace LLM) would ever encounter it, add it to `system-knowhow/glossary.md` instead (under **Core** if it's general, or under **Advanced — coding agents** if it's only relevant to coding-agent workflows).

## When a term changes

Update this file in the same commit that renames or retires the term — same rule as `system-knowhow/glossary.md`. `/harden` flags drift.
