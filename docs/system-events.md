# System events: behaviour notes

`SystemEvent` (`crates/lucidos-engine/src/engine/event_bus_system_event.rs`) is the catalog of event variants. Its doc comments describe each variant. This page holds what those comments do not: projection effects, emit order and contracts a reader must not break. [`.claude/rules/db.md`](../.claude/rules/db.md) holds the conventions that apply to every event.

## Thread status and permissions

- **Permission resolution never resurrects a thread.** `CodingAgentPermissionResolved`, `CommandPermissionResolved` and `McpPermissionResolved` share one projection arm in `event_bus_projection_thread.rs`. It flips status to `running` only from `waiting_for_user_answer`. A stale click on an idle or terminal thread changes nothing.
- **A question answer is the exception.** `UserQuestionAnswered` keeps its own unconditional move to `running`. An answer can resume an idled thread through `--resume`. A permission resolution never does.
- **A finished session leaves no dangling card.** `CodingAgentIdled` clears any pending `CodingAgentPermissionRequest` through `resolve_pending_permissions_as_session_ended`.
- **Request events flip status to `waiting_for_user_answer`.** That covers `CommandPermissionRequested` and `McpPermissionRequested`. Both are persisted, chat-channel only, and resolved through `POST /api/v1/command-permission/consent` and `POST /api/v1/mcp-permission/consent`.
- **Persist scope.** `Resolved` carries `allowed`, an optional `reason` and an optional `persist_scope`. `narrow` stores `Mcp(server:tool)`, `broad` stores `Mcp(server:*)` in the workspace `mcp-allowed-tools`, and `session` stays in memory.
- **No card for MCP calls in a non-interactive trigger thread**, or when the server's `auto_approve` flag is set.
- **Message events exist on chat and coding-agent threads.** `MessageReceived` is the user typing, whichever agent answers. To filter chat threads only, join `thread_summaries` on `source = 'chat' AND is_coding_agent = false`. Use `source IN ('chat','trigger')` to include triggers.
- **`ChildThreadDetached` is the only parent-and-child event that writes the child's row.** It cuts the edge (ADR 0278). The other three land on the parent only.
- **Serde aliases.** `ThoughtStreamed` also reads `Thinking`, and the `CodingAgent*` variants also read the old `ClaudeCode*` names. Write new code against the current names.

## Command checkpoint and undo (ADR 0002)

- **Two images per checkpoint.** On the `ReversibleDanger` lane the engine snapshots the git-visible working tree twice, as `commit-tree` objects through a throwaway `GIT_INDEX_FILE`. The pre image sits on `refs/lucidos/command-checkpoints/<checkpoint_id>`. The post image sits on `refs/lucidos/command-post-images/<checkpoint_id>`.
- **The diff of the pair names what the command created, overwrote and deleted.** `CommandCheckpointed` is emitted after the command returns, and only when that diff is non-empty. A command that only touched gitignored paths (`.lucidos/`, `data/blobs/`) leaves the images identical. The engine then drops both refs and shows no card, because its Undo could do nothing.
- **Undo restores from the pre image.** It also removes each created file that git still calls unchanged against the post image. Then it emits `CommandCheckpointReverted`, stamped with the checkpoint's `request_event_id` so it groups into the same exchange.
- **The refs survive an undo**, because they back the card's diff viewer. `prune_expired_checkpoints` reclaims pairs older than 30 days.
- **Neither event changes thread status.** The routes are `POST /api/v1/command-checkpoint/undo` and `GET /api/v1/command-checkpoint/diff?checkpoint_id=...`.
- **`restores` and `removes` default to 0** on events written before the counts existed.

## Changes

- **Entity events follow `ChangeApplied`.** Every real merge path calls `emit_entity_events_for_change_apply`: `engine::change_ops::apply_change`, the landing lane, and `apply_now_success`. It derives `App*` and `Artifact*` events by comparing pre-merge git state with post-merge disk state. Frontend caches then refresh when a coding-agent thread lands files.
- **`ChangeApplied` is emitted at most once per `change_id`.** The unique index `events_change_applied_once` enforces it across engines. `emit_change_applied` takes the change's `ApplyClaim`, and every apply claims before it reads the row (ADR 0442).
- **Apply Now's bracket (ADR 0437).** `ApplyNowStarted` and `ApplyNowEnded { outcome }` set and clear `thread_summaries.apply_in_flight`. The apply task emits the end on every exit. Engine startup emits it as `interrupted` for a flag a stop left set. Both are classed `Metadata`.
- **Set aside (ADR 0328).** `ChangeSetAside` and `ChangeBroughtBack` move `changes.status` between `pending` and `set_aside` and leave `resolved_at` NULL. `ChangeProposed { set_aside: true }` inserts straight into `set_aside` and leaves an archived thread archived. The projection rebuild replays all three.
- **Landing lane queue (ADR 0463).** `ChangeQueued` and `ChangeUnqueued` never move `changes.status`. A pending change whose latest of the two is `ChangeQueued` is in the lane (`landing_lane::queued_changes`). The `reason` is `discarded`, `set_aside`, `removed`, `batch_failed` or `landing_failed`. `ChangeApplied.landing_merge_sha` names the change's own landing merge, which Revert undoes.
- **Withheld and withdrawn work (ADR 0400).** `ProposalWithheld` records that a turn end left branch work and proposed none. It writes `coding_agent_unproposed_reason`, leaves a `proposed` row alone and touches no `changes` row. `ChangeWithdrawn` sets `changes.status = 'withdrawn'` and stamps `resolved_at`. `sync_thread_proposal` then lands the thread on `unproposed` and moves it to the inbox. Both are classed `Metadata`.
- **Background bash.** `BackgroundBashStarted` and `BackgroundBashCompleted` are the durable record behind `bash_output`. It falls back to `BackgroundBashCompleted` after the in-memory registry evicts a finished task.

## Operations events

All use aggregate `ops` and `aggregate_id` `global`.

- **Backup.** `BackupProgress` is transient, one per tick. `BackupCompleted` and `BackupFailed` are persisted and are the durable run history, read newest-first by `core::backup::load_recent_runs` with no projection table. Both carry `started_at` and `finished_at`. The latest outcome also lands in the `backup_last_run` preference.
- **Restore is not an engine concern.** The workspace picker (gateway control plane) provisions a new workspace, then runs the one-shot `lucidos-engine restore-archive` subcommand. It does not restore the archive's `user_dir/` over `~/.lucidos`, which would clobber the gateway registry. Progress is the gateway's single-slot `RestoreStatus` at `GET /~/api/v1/control/restore-status`.
- **Recommended cleanup.** `RecommendedCleanupStarted`, then transient `RecommendedCleanupProgress` per worktree, then one of `RecommendedCleanupCompleted` or `RecommendedCleanupFailed`. They report the "Free up space" pass behind `POST /api/v1/disk-usage/cleanup`, which answers 202 at once. A long pass outlives any request, so these events are its only report.
- **`ProxyConfigRejected`** is emitted once at boot, only when `data/config/apis.json` holds entries the engine will not serve (ADR 0135). It fires before the HTTP port binds, so an ordinary boot reaches no SSE subscriber. The user sees the `NotificationCreated` emitted beside it.
- **`ModelNotServedObserved`** is emitted by `aux_purpose::not_served_report` at most once per provider, model and purpose within six hours. At boot `aux_purpose::reach::seed_not_served` seeds the router's `NotServedLedger` from the last six hours through `idx_events_type_created` (ADRs 0403, 0519).
- **`ThreadsDeleted` carries neither `aggregate = 'thread'` nor a `thread_id`**, so no later thread sweep can delete it (ADR 0192). It carries no content (no title, first message or summary), because a row nothing can delete must not re-file what the delete removed. `POST /api/v1/threads/delete` is the only production path that removes an `events` row, and it refuses anything but a signed-in device.

## Memory events

Aggregate `memory`, `aggregate_id` `global`.

- **`MemoryCorrected` is the checkpoint.** The `memory` tool's `correct` and `correct_by_id` actions emit it before they delete anything. It is the only durable record of a correction. Rebuild phase 3 (`engine::memory::correction::replay_corrections`) replays each one, oldest first.
- **A replay is conservative.** It deletes the closest same-source copy and what extraction folded in. It touches only rows written after `recorded_at`, from sources older than the event. The payload carries `search_query`, `wrong_fact`, `removed`, an optional `correction` and `recorded_at`. Flat rows from the retired factory carry only `deleted_summaries`, which the replay matches on text alone.
- **A tree backfill episode runs from `TreeBackfillStarted` to `TreeBackfillEnded` or `TreeBackfillReset`.** `TreeBackfillProgressed` is transient. `Started`, `Completed`, `CapReached`, `CapRaised`, `Ended` and `Reset` are persisted. `summary_tree/spend.rs` reads the cap and spend back from these rows at every seed. Spend is the `summary_compaction` captures since `Started`, priced by `COMPACTOR_MODELS`.
- **Progress counts scopes.** Each in-scope thread plus the workspace is one scope, and `done_milli` adds the built share of each scope under way. The compactor emits `Progressed` at seed, per completed scope, per owed node, and when a scope starts failing or the model wait changes.
- **`TreeBackfillCompleted` follows `mark_ready`.** It fires once the workspace tree and the threads active in the last 7 days are built. Older threads fill in after (`ready: true`).
- **`TreeBackfillReset` follows a switch to Classic that cleared a set flag**, never a no-op clear.
- **`seq` orders frames.** `progress` is the struct `GET /api/v1/memory/tree-backfill` serves, and `seq` orders frames against that snapshot, so the bar never steps back.

## Notifications and presence (all transient)

- **Presence.** `DeviceVisible` and `DeviceHidden` use aggregate `device_presence`. `PresenceCheck` uses aggregate `presence`. None is persisted. `PresenceCheck` is the fan-out check at `NotificationCreated` time and carries the toast content.
  - Every connected page acts on it and POSTs `/api/v1/presence-pong` with its presence outcome. Only an outcome other than `not_shown` withholds the OS push (`system-knowhow/notifications.md` §3, ADR 0440).
- **`NativePushRequested`** uses aggregate `notification`, `aggregate_id` the notification id. The `NotificationCreated` fan-out emits it only on the push-allowed branch, when no page reported handling the check. A connected Tauri app shows a native macOS banner through `show_native_notification`, which needs a packaged `.app`. A desktop window brought forward since it answered shows the in-app toast instead.
  - A tap routes through `dispatchDeepLink`, as a web-push tap does. Browser and PWA pages ignore the frame and get the real web push. The decision runs whenever any client is on SSE, even with zero web-push subscriptions.
- **`NativePushDismissRequested`** is the cross-device counterpart of a read. `mark_notification_read` and `mark_all_notifications_read` emit it inside the same `success` and `count > 0` guards as `NotificationRead` and `NotificationsAllRead`, so a no-op POST emits neither. `aggregate_id` is the notification id, or `all` when `notification_id` is `None`. Only a Tauri desktop app acts on it (`handleNativePushDismiss` gates on `isTauri()`). The open web cannot silently remove a Web Push banner, and Safari revokes a subscription after 3 silent pushes.
  - `sent_at_ms` drives a page-side freshness gate that drops a late SSE-queue flush. See `system-knowhow/notifications.md` §4.

## Thread Queue and capacity

- **The Thread Queue events are persisted** and drive the `thread_queue` projection. Aggregate `thread_queue`, `aggregate_id` the entry id. Every background spawn emits them, so they double as the audit trail of background work. An immediately admitted entry gets `ThreadQueued` and `ThreadQueueAdmitted` back to back.
- **`ThreadQueued.requeued = true`** marks the boot sweep re-queuing an admitted entry that bound no thread.
- **A trigger fire emits `ThreadQueueAdmitted` twice.** The second carries the `thread_id` the fire minted (`ThreadQueue::record_entry_thread`). The projection COALESCEs the id onto the row and keeps the first `admitted_at`. That lets the boot sweep tell a fire that started from one that never did (ADR 0133).
- **A coalesced cron fire emits no `ThreadQueued`**, because it never enters the queue. On recovery, duplicate cron rows for one trigger emit `ThreadQueueDropped` with reason "coalesced on recovery".
- **Run now and Drop carry `actor`.** Engine drain decisions pass `None`.
- **`ThreadQueueChanged` is transient and fieldless**, with aggregate `thread_queue` and `aggregate_id` `global`. It signals the panel to refetch after in-memory user slot moves, which have no persisted event (ADR 0008).
- **`CapacityPolicyChanged` is the stored capacity policy.** Aggregate `capacity_policy`, `aggregate_id` `global`, persisted. The latest event is the policy, there is no config table, and `ThreadQueue::load_policy` reads it at boot. `#[serde(default)]` keeps old payloads readable after the `reserved_background` field arrived (ADR 0008).

## Triggers, plugins and dashboards

- **Trigger CRUD events carry `actor`.** That covers `TriggerCreated`, `TriggerUpdated`, `TriggerDeleted`, `TriggerEnabled` and `TriggerDisabled`, aggregate `trigger`. `SystemEvent::to_payload` merges it through `merge_actor`, the contract `TriggerGroup*` shares. The handlers resolve it through `require_user_actor`.
- **`TriggerExecuted` carries no `actor`.** Its payload is `trigger_id`, `last_run` and `status` (`ok` or `failed`). `replay.rs` rebuilds `TriggerConfig.last_run_status` from it. A legacy event without `status` reads as `None`.
- **`plugin_id` on `TriggerCreated` and `TriggerUpdated` marks a plugin-managed trigger** (ADR 0019). Absent means user-created. Install emits them through `resync_plugin_triggers`, and uninstall emits a `TriggerDeleted` per trigger carrying the id (`delete_plugin_triggers`).
- **Trigger groups.** `TriggerGroupCreated`, `Renamed`, `Reordered` and `Deleted` use aggregate `trigger_group` and carry `actor`. A group is a folder only. A delete is refused while members remain, and then emits nothing.
- **Plugin events** use aggregate `plugin` with `aggregate_id` the plugin id, all persisted. `PluginInstalled` also serves updates and reinstalls. Its `payload.data.id` is top-level, and an older row carries it only inside the raw manifest. It also carries `commit`, the sha of the "Install plugin" commit. A top-level `files_removed` lists paths an update deleted.
- **There is no `PluginModified` event.** The "Modified" badge derives on read by diffing disk against `commit` (`plugin_modification_status`). It clears itself when the edit reverts. A legacy row without `commit` never reads as modified.
- **An update merges a local edit** (`plugins::merge`), so the badge stays on. That needs `commit` to name a byte-exact copy of what the plugin shipped. A merged path is staged from upstream's bytes (`core::commit_data_paths_with_overrides`), and a second commit records the merge. Folding the merge into the install commit would make the next update drop the patch as upstream's own content.
- **`PluginLocalChangesMerged` follows `PluginInstalled`** when the install met a locally edited file. It is persisted because nothing on disk records which files merged. Paths in `conflicted`, `replaced` and `removed` have a copy in `saved_paths`, under `data/artifacts/plugin-local-changes/` with a `.patch` sibling. Paths in `restored` do not, since a deletion has no content.
- **Marketplace events use aggregate `plugin_marketplace`**, `aggregate_id` the `marketplace_id`. `PluginMarketplaceRegistered` is an upsert: the id hashes the canonical source, so a re-registration rewrites `name` and `source`. It fires on every registration call, as `McpServerRegistered` does. Only `engine::tools::plugins::marketplaces` emits it, as the single write path of `data/config/plugin-marketplaces.json`.
- **`PluginCatalogScanStarted` and `PluginCatalogScanned` are transient.** They bookend the scan in `scheduler::plugin_updates` and move the Plugins panel's scanning state. A scan runs at startup, every five minutes, on registration and on a stale page open. Persisting them would add a heartbeat row.
- **Dashboards (ADR 0496).** `DashboardTileAdded`, `DashboardTileRemoved` and `DashboardArranged` are persisted, aggregate `dashboard`, `aggregate_id` `phone` or `desktop`. No projection table exists: `engine/dashboard.rs` folds them on every read, over a seed from the home thread's legacy `WidgetPinned`, `WidgetUnpinned` and `HomeBoardArranged` rows. Nothing writes those rows now.

## Apps, artifacts and knowhow

- **`AppCreated` and `AppUpdated` are broadcast-only.** The durable record of an app change is the git commit, plus `ChangeApplied` for coding-agent applies. `AppOpened` shares aggregate `app` and records use, not a hint.
- **`AppOpened` is persisted** (ADR 0413). `POST /api/v1/app/opened` emits it after `require_user_actor`, for an existing app and never a widget. The client posts from `openApp` on a fresh open only, so a reload restore, a history step and an inline widget do not. The workspace prompt footprint reads the newest per app as its only evidence of use.
- **`KnowhowRead` is persisted** (ADR 0413), aggregate `knowhow`, `aggregate_id` the knowhow id. `GET /api/v1/knowhow/read` emits it on a successful read, at most once per doc per day.
- **`AppDeleted` is persisted** (ADR 0404) with `kind?`. Each delete site reads `kind` from the manifest before it goes. The `app_kinds` projection keeps it, so a removed widget still lists as a widget in the thread filter.
- **Emit sites for app events.** The `AppManager` write paths in `core/apps.rs` serve the `create_app` tool and the HTTP endpoints. `emit_entity_events_for_change_apply` covers coding-agent changes. The chat file tools emit only on an app's `manifest.json` (`app_lifecycle_event`, gated by `data_path_app_manifest_id`): `AppCreated` on first sight and `AppDeleted` on removal, never `AppUpdated`.
- **The end-of-turn pass emits one `AppUpdated` per edited app** (`agentic_loop/run.rs`, `modified_app_uis`), beside the `AppUiRefreshRequested` iframe reload. It skips an app deleted mid-turn, so an edit refreshes the list once per turn.
- **`appsList` is a disk-scan projection** that only these hints keep live. Apps written through `run_bash` or `run_python` have no chokepoint and need a reload. The navigate path self-heals through `openAppById`'s disk re-scan.
- **Artifact events.** `emit_entity_events_for_change_apply` also emits `Artifact*` for any `data/artifacts/<path>` an applied change touched, with `source: Some("change_apply")`. `ArtifactCreated`, `ArtifactUpdated` and `ArtifactImported` carry an optional `writer_thread_id`. The data API takes it only from the token-verified caller. The Tree compactor and memory indexer bill calls about the write to that thread, or to the home thread when it is absent or gone.
- **`ReleaseNoticeResolved` is the only durable trace of the answer.** The `release_notice_cursor` preference is silent, a `PrefAccess::Engine` spec, because this event announces for it. `POST /api/v1/release-notices/resolve` emits it only when the cursor moved, so a second device answering the same notice emits nothing. The frontend refetches on it, which closes the modal on other devices.

## Audit events

Persisted, and carrying `actor` unless noted. The payload shapes are in the `SystemEvent` doc comments.

- **The emit lives in the store's write path, not at the call site.** `RepositoryStore::{register,unregister}`, `WebhookStore::{create,update,delete}`, `McpServerStore::set_tool_disabled` and `ModelStore` emit by construction, so every surface announces. `crates/lucidos-engine/src/core/announced_surfaces.rs` lists which surface is announced and which is deliberately silent, with the reason.
- **`Credential*` events never carry the secret**, only the service name and type. `CredentialRevealed` and `BackupKeyRevealed` follow the same contract. Each is written when the plaintext or key leaves the engine, behind a one-shot 30-second reveal token and an app-`Referer` refusal (ADR 0117). That makes an unexpected reveal findable afterwards.
- **Environment variables carry their `value`**, the inverse of `Credential*`, because they are non-secret. The startup `data/.env` migration writes rows directly and emits nothing.
- **`RepositoryAdded` also feeds the `repo_names` projection.** `actor` is the device for the HTTP CRUD, the acting thread for the tool, and absent for the startup registration.
- **`OAuthAccountConnected` fires on a connect and on a re-authorization**, since re-connecting is how scopes are granted. A token refresh is silent. `McpServerUpdated` means an auto-approve change.
- **Claude gateway events** use aggregate `claude_gateway`, `aggregate_id` the gateway origin. None carries a token, and a refresh is silent. `ClaudeGatewaySignedOut.reason` is `signed-out`, `url-changed` or `rejected`, and the status route answers `sign_in_again` from the last sign-in or sign-out. `ClaudeGatewayManagedSettingsChanged` carries the allowlist and the telemetry ask, never an `env` value, since one can hold a collector's credential.
- **Webhook events** use aggregate `webhook`. `signed` says whether a signature is configured, and no payload carries the token or secret. A delivery emits no event of its own. It emits the webhook's pinned `event_type` as an ordinary domain event with actor `MessageOrigin::Webhook`.
- **Webhook ingress events carry no actor** (ADR 0143). They are edge-triggered, so a standing outage emits nothing per cycle. `down_secs` is measured in SQL beside `down_since` (ADR 0053), so a skewed client clock cannot read as outage time. The engine reports and never repairs.
- **`WebhookDeliveriesSleptThrough` fires once** for a sleep of 30 minutes or more, on the first awake round that probed (ADR 0367). A round the computer slept through is not ingress evidence. The ingress bar never reads it.
- **Webhook refusals (ADR 0235)** are the verification-layer sibling of the ingress pair, which reads a 401 as healthy. `cause` is `disabled` or `verification`. `resolution` is `accepted`, `reconfigured`, `quiet` or `removed`, exhaustive so a declaration cannot strand. They are per hook and edge-triggered, and `declared_refusals` takes the newest event per `aggregate_id`.
- **`McpServerStopped` removes the id from every `thread_summaries.enabled_mcp_servers`**, as `McpServerRemoved` does (ADR 0430). Engine shutdown emits none, so threads keep their enabled servers across a restart.
- **`McpServerDisabledToolsChanged` and `PermissionGrantsChanged` carry the resulting set in full**, never a delta, so a reader needs no folding. The grant event matters most for auditing a widened grant. Both emit only when the set moved. `McpServerStore::set_tools`, a cache refresh, emits nothing.
- **All three grant editors emit through `api::settings::write_grant_file`.** `grant_file` is a typed `core::GrantFile` whose wire value is its file name. The "Always allow" buttons add no event, since their `*PermissionResolved` event names the pattern.
- **`ModelCreated`, `ModelUpdated` and `ModelDeleted`** make `spawn_models_registry_subscriber` reload the in-memory `ModelRegistry`, so `RoutingProvider` picks up a re-routed model without a restart.
- **Data file events.** `PUT`, `DELETE` and `POST /api/v1/data/*` emit `DataFileWritten`, `DataFileDeleted` and `DataFileEdited`. The agent file tools emit them too, with no actor, for paths outside `artifacts/` (`data_file_event` in `engine/tools/files.rs`). `Artifact*` covers `artifacts/`.
- **Device events.** `DeviceHandedOver` is one event for a whole-row move across `devices`, `preferences`, `pinned_apps`, `device_presence` and `push_subscriptions`. The per-row writes stay silent. The daily device sweep emits `DevicePushChanged` and `DeviceDeleted` with no actor.

## Batches and standing applies

- **Apply All.** `ApplyAllBatchStarted` and `ApplyAllBatchCompleted` use aggregate `apply_all_batch`, `aggregate_id` the `batch_id`. The HTTP handler emits `Started`. The driver (`start_apply_all_driver`) advances the batch as `ChangeApplied` and `ChangeApplyFailed` arrive, and emits `Completed` once every member resolves. Without the pair the batch is abandoned at the first conflict.
- **Standing apply.** Aggregate `standing_apply`, `aggregate_id` the `thread_id`. The sweep that armed it is a field, since cancelling a sweep drops many arms, each reporting on its own thread. Only `engine::standing_apply` emits. Every end of an arm emits exactly one of `Fired` or `Dropped`, because clients clear the armed face only on those.

## Landing lane and main check

- **Landing lane (ADR 0463).** Aggregate `landing_lane`, `aggregate_id` the `batch_id`. Only `engine::landing_lane` emits `LaneBatchStarted`, `LaneBatchLanded` and `LaneBatchFailed`. The lane keeps no table. Recovery folds these with `ChangeQueued`, `ChangeUnqueued` and each member's `ChangeApplied`.
- **`LaneBatchStarted`** carries `members`, `base_sha` and `lane_thread_id`. `base_sha` is `main` when the batch formed, where the integration branch `lane/<batch_id>` starts. Any run on the lane thread while the batch is open carries the batch (`landing_lane::lane_duty_for_run`).
- **`LaneBatchLanded`** follows every member's `ChangeApplied`. After a crash between the two, recovery reads `pre_sha` from the reflog of `main`.
- **`LaneBatchFailed`** carries `actor` only for a Cancel (`POST /api/v1/changes/lane/cancel`). Every member gets `ChangeUnqueued { reason: batch_failed }` and stays pending.
- **Main check (ADR 0464).** Aggregate `main_check`, `aggregate_id` the `check_id`. Only `engine::main_check` emits `MainCheckStarted`, `RunLinked`, `Passed`, `Failed`, `Abandoned` and `RedClosed`. It keeps no table. Recovery folds them with every `ChangeApplied` that carries a `landing_merge_sha`.
- **`MainCheckStarted`** runs `scripts/main-check.sh <to_sha>`. `from_sha` is `main` as the last check with a verdict saw it.
- **`MainCheckRunLinked`** records the workflow run. Engine shutdown then detaches, and the next start reattaches with `main-check.sh <to_sha> --attach <run_url> <branch>`.
- **`MainCheckPassed` records flaky tests** that failed once and passed a retry, and the one flaky fix thread it opened. Nothing records that thread's close. Recovery derives it from a landing by that thread, or from its archive or delete.
- **`MainCheckFailed` opens one fix thread.** Main stays red until a `MainCheckRedClosed`, whose `reason` is `fix_landed` or `closed`.
- **`MainCheckAbandoned` is no verdict.** It covers GitHub down, a refused push, or a restart before the run was linked. It starts nothing by itself.

## Other engine and security events

- **`EngineSupervisorRespawned`** has aggregate `engine`, `aggregate_id` the `supervisor_pid`, and no `actor`. The bash supervisor (`scripts/lib/engine_supervisor.sh`) writes `<workspace>/.lucidos/engine.last-death.json` when its child dies with an exit code other than 0, 130 or 138. The next engine emits it and deletes the sidecar at startup (`engine::supervisor_respawn_sidecar::emit_if_present`).
- **`EmailSent` carries only envelope metadata.** The body stays out on purpose, because it is user data that would fan out over SSE to every connected client.
- **Handshake events** use aggregate `handshake_script`, `aggregate_id` the workspace-relative path (ADR 0144). `HandshakeScriptApproved.source` is `authored`, `approved` or `seeded`. `HandshakeScriptScopeBound` fires on the first proxy call for a script whose `base_url` column is still `-`, and the proxy refuses any other host after it. `HandshakeScriptInjectsBound` records the sorted `injects` set (`c:<credential>`, `o:<provider>`) on the first proxy call that would inject one. `credential_base_url_matches` cannot judge a handshake script, because it presents the credential to the provider's token endpoint. This record does instead (ADR 0157 amendment).
- **`CredentialScopeInferred` is written once per credential at startup**, when a row with an empty `base_urls` gets the scope its own `apis.json` entry uses. A row that already has a scope is never rewritten. The inference never appends to one, because `apis.json` is the file the gate defends against (ADR 0161).
- **`ProxyModulesReloaded`** fires from `POST /api/v1/proxy-modules/reload` after the WASM map swap succeeds.

## Transient frontend signals

Unless noted, these are dev-only by construction (`refresh_served_frontend_after_rebuild` early-returns when packaged), carry `sent_at_ms`, and are never persisted. Aggregate `engine`, `aggregate_id` `global`, except `FrontendPreview*` and `AppUiRefreshRequested`.

- **`AppUiRefreshRequested`** (aggregate `app`) fires from `apply_change` for an *app coding-agent thread* when a merged file is iframe-bundled (`git_ops::any_iframe_bundled_file_changed`). The SDK reloads the src of any open iframe of that app.
- **`FrontendUpdateDeferred`** fires from `run_served_frontend_refresh` when a frontend-only Apply's in-process advance is skipped because an engine version change is pending. The rebuilt `dist/` holds a client for the new engine, so the old one cannot serve it. The toast carries no Switch action, since a mixed rebuild may still be `building`. `checkEngineVersion` stays the only Switch surface.
- **`FrontendUpdateStranded`** fires when the post-Apply rebuild wait expires (`REBUILD_WAIT_TIMEOUT`, 60 s): the change built, but the `dist/` this engine serves is not the one republished. It stays distinct from `Deferred`, which means "arrives on Switch". Reusing it would say something false.
- **`FrontendUpdateStranded` fields.** `served_in_worktree` marks a stack pinned to a coding-agent worktree, whose `dist/` freezes while the shared checkout rebuilds elsewhere. `build_error` is what `.build-watch/status.json` last reported. `build_watch_stopped` reads the pidfile beside it, because a status records only the last completed build. `true` outranks `build_error`, since a stopped watch never retries. `false` also means "could not tell".
- **`ServedFrontendAdvanced`** fires on every swap of this engine's boot-pinned snapshot to the shared `dist/` (`advance_served_snapshot`). Two paths swap: the applying engine after its own frontend-only Apply, and `sync_served_frontend_if_safe` (about every 10 s) after another workspace's. The second is gated by `peer_advance_is_safe`: disk and build state, plus git-confirmed engine-source parity with HEAD (`engine_source_matches_head`). A mixed change mid-rebuild defers to the Switch flow. The frontend handler re-runs `syncClientUpdateFromBuild`, which is idempotent. An SSE reconnect re-runs the check, since nothing replays the event.
- **`EngineBuildStateChanged`** carries `state` (`idle`, `building`, `ready`, `failed`) and fires from `engine::background_build` on each background-rebuild transition, latest generation only. It exists because iOS suspends the throttled `checkEngineVersion` poll on a backgrounded PWA, so the build window went unobserved. The handler re-runs the authoritative GET and never trusts `state`. A PWA suspended for the whole build reconciles in `onResume`.
- **`FrontendRefreshStateChanged`** fires when the applying engine starts waiting for the build-watch after a frontend-only Apply, and when the wait ends. A peer-sync takeover sends the end poke itself, since it aborts the task. The "Building frontend" activity follows `frontend_refresh_elapsed_ms` from the re-read, never the poke.
- **`FrontendPreviewStarted` and `FrontendPreviewStopped`** use `aggregate_id` the thread id (ADR 0055). The one preview slot per workspace is identified by the thread whose worktree it serves. `Started` carries the port and never a URL, because the same workspace is `localhost` on the laptop and a Tailscale name on the phone. Only the page builds the href (`previewHref`). Moving the slot emits a stop for the old thread and a start for the new one, in no fixed order. So the stop handler keys on `thread_id`.
