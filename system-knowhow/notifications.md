# Notification Routing

This is the canonical spec for what happens when a `NotificationCreated` event is emitted: who gets an OS push, who gets an in-app toast, whose bell badge changes, and what gets auto-marked-read. The rules apply to every notification source — `send_notification` from the chat LLM, scheduler error notifications, trigger output, push-from-trigger, etc.

Tests reference the section IDs below (e.g. `s2_scenario_4_tab_in_background_tab_push_fires`). A failing test points directly at the broken rule.

## §1: Conceptual model

Lucidos has **three notification surfaces** for the same `NotificationCreated` event:

1. **In-app surface** — the bell badge (unread count) and transient toast popups. The badge is driven by the `NotificationCreated` SSE landing on any connected page; the toast is driven by the `NotificationToastRequested` SSE, which the engine emits only after it decides to suppress the OS push (§3-§4). Two triggers, one notification.
2. **OS surface** — an OS-level notification banner outside the Lucidos UI. **Two transports, picked by client:**
   - **Web push** (browser / PWA) — delivered by the device's push service (APNs / FCM) and rendered by the registered service worker.
   - **Native desktop** (Tauri app) — a native macOS notification driven by the `NativePushRequested` SSE (§4), rendered + tap-routed by the app's `show_native_notification` command via Apple's `UserNotifications` framework (`UNUserNotificationCenter`). The embedded WKWebView can't subscribe to Web Push, so the engine reaches the desktop app over its already-open SSE stream instead of a push service. Requires a packaged `.app` build (inert in `tauri dev`).

   Both transports ride the same server-side `push_allowed` decision (§3) and live on the push-ALLOWED branch (the in-app toast lives on the complementary push-suppressed branch), so a notification reaches any one device through exactly one surface — never a native banner *and* a toast, never web push *and* native.
3. **App-icon badge** — the unread *count* painted on the installed app's **icon** (a PWA's home-screen icon via the Badging API; the Tauri macOS **dock** icon via the dock tile). Distinct from the in-app *bell* badge in item 1, which lives inside the Lucidos UI. The value is per-install: a **workspace PWA** (installed at `/<slug>/`, or a direct engine at `/`) shows ITS OWN workspace's unread count; the **gateway-root PWA** (installed from the picker at `/~/`) and the **Tauri desktop app** show the AGGREGATE total across running workspaces. Unlike items 1–2 this is not gated by the `push_allowed`/PresenceCheck decision — every device always reflects its own count. See "App-icon badge" at the end of §4.

A device is in one of three **presence states** at any moment:

- **Active** — user is looking at Lucidos right now. On desktop: `visibilityState='visible'` AND `document.hasFocus()`. On iOS PWA: `visibilityState='visible'` only (Safari leaves `hasFocus()` false even when the PWA is fully foregrounded). **On the Tauri desktop client this is additionally gated on the *native window* being active (focused AND on-screen).** The embedded WKWebView can't observe macOS `orderOut:` — a window dismissed to the menu-bar tray keeps `visibilityState='visible'` and `hasFocus()=true` — and its `hasFocus()` is unreliable generally, so a trayed (or merely unfocused) client would otherwise wrongly report Active and get a suppressed, invisible in-app toast instead of an OS native banner. The Rust side bridges the authoritative AppKit state to the page via a `native-window-active` event (`crates/lucidos-app/src/lib.rs` → `utils/nativeWindow.ts`); `isPageActive()` returns false when it's inactive. Always Active-eligible in the browser / PWA (no native bridge).
- **Connected-but-hidden** — SSE EventSource is still open (tab exists, page alive) but `isPageActive()` is false: a different tab is selected, the window is behind another app, the iOS PWA is in the multitask switcher, or (Tauri) the native window is trayed to the menu bar / unfocused.
- **Offline** — no live SSE; page is closed or unreachable. Only the OS surface can reach it.

A notification also carries a **source event** (`notifications.event_id`) so the page can check: "is the user looking at the very thing this notification points to?"

The rules below combine these three concepts: **surface × presence × source-event-in-viewport**.

### Advising a user on enabling notifications — read the device first

When a user asks how to turn notifications on, why they "only get in-app toasts", or why a test push didn't land at the OS level, **first read the current request device in `[USER DEVICE & PREFERENCES]` (the `details:` line) and branch on the client — do NOT assume a browser:**

- **`details: Lucidos desktop app …` → the native desktop app (Tauri).** Notifications arrive as **native macOS notifications** (the `NativePushRequested` SSE → `show_native_notification`, see §4). There is **no browser, no in-app permission prompt, and no "site settings"** — macOS governs them under **System Settings → Notifications → Lucidos** (it asks once on first launch; if no banner appears, allow Lucidos there). Flipping the `push_notifications` preference / settings switch is a no-op success on desktop (`initPushSubscription` short-circuits) — the banner needs no further web setup. Native banners require a packaged `.app` build; in a `tauri dev` build they don't appear at all. As on every client, the OS banner only fires when this device is **not** the active one (§2) — if the desktop window is focused you'll get the in-app toast instead, so background the window to test the banner.
- **Any other `details` (a browser or installed PWA) → web push.** The **browser** asks for notification permission (click Allow; if missed, re-grant it from the 🔒 site-settings next to the URL). Delivery is via the device's push service + the registered service worker. Same active-device rule: an OS push only fires when the page isn't the active one — an active page gets the in-app toast.

**Web push requires a secure origin (https or localhost).** On a plain `http://<host>:<port>/` origin (typical for a packaged headless install reached over the LAN) the platform grants no service worker and no `Notification.requestPermission` — push is impossible there, full stop. Enabling push surfaces this as an explicit toast (`pushUnsupportedReason` in `store/actions/push.ts` checks `window.isSecureContext` before the browser-support probes), and startup logs a console warning (`useStartup.ts` — telemetry carve-out, no per-load nag). The fixes are origin-side, not settings-side: open Lucidos over https://, over `http://localhost` (an SSH tunnel to the host counts — localhost is a secure context), or through `tailscale serve` (trusted HTTPS on the tailnet). `http://localhost` itself is exempt and fully works.

The two transports are mutually exclusive per device (§1) — one notification reaches a device through exactly one surface. And the `push_notifications` **preference** (the "on" switch in settings) only records that the user opted in; it is **NOT** the OS/browser permission, which Lucidos cannot toggle on the user's behalf in a browser. Don't conflate "the switch is on" with "the OS will show banners".

## §2: The fan-out rule

**Step A — Global push check (once per notification):** is any device currently active?

The engine runs the PresenceCheck protocol (§3) to find out. After Step A, it has a boolean `push_allowed` and zero or more `PresencePong` records.

- `push_allowed = true` if and only if NO device returned `is_active: true` within the deadline. The engine skips the protocol and sets `push_allowed = true` directly only when **nobody is reachable** — i.e. there are zero open SSE connections (`GET /api/v1/events`) AND zero `device_presence` candidate rows fresher than `PRESENCE_STALE_AFTER` (120s, `crates/lucidos-engine/src/core/device_presence.rs`). The live SSE-connection count is the primary gate; the heartbeat candidates are a secondary signal (see §3 "Trigger").

**Step B — Per-device, in this exact order. First match wins:**

| # | Condition | OS push | In-app toast | Bell badge | Auto-read |
|---|---|---|---|---|---|
| 1 | Active AND on source thread AND source event in viewport | n/a¹ | no | no | yes |
| 2 | Active AND on source thread AND source event NOT in viewport | n/a¹ | yes | yes | no |
| 3 | Active AND on Lucidos, NOT on source thread | n/a¹ | yes | yes | no |
| 4 | Connected-but-hidden (SSE alive but `isPageActive()` false) | `push_allowed`² | no³ | yes | no |
| 5 | Offline (no SSE) | `push_allowed`² | — | re-syncs on next page load via `GET /api/v1/notifications?filter=unread` | no |

¹ Active devices never get an OS push by definition of Step A: at least one device (this one) is active, so `push_allowed = false` for everyone.
² Only sent when Step A returned `push_allowed = true`. Otherwise no push to this device either.
³ Page receives the `NotificationCreated` SSE message and increments the bell badge, but does NOT render a toast — the toast would auto-dismiss before the user returns to the tab, creating a "ghost toast" they'd miss. The bell badge is the durable, on-return signal.

**OS-push transport — web push vs native desktop (Rows 4 & 5).** "OS push" in the matrix above is a *surface*, not a single transport. How it actually reaches a device depends on the client:
- **Browser / PWA** → web push (APNs / FCM) to the device's stored `push_subscriptions` row, rendered by the service worker.
- **Tauri desktop app** → a native macOS notification. The WKWebView can't subscribe to Web Push, so when `push_allowed = true` the engine broadcasts a `NativePushRequested` SSE; the connected desktop page renders the banner (and routes its tap) via the `show_native_notification` command using Apple's `UserNotifications` framework (`UNUserNotificationCenter`) (§4). Both transports fire on the same `push_allowed = true` branch, so the per-device matrix is unchanged — only the delivery channel differs.
- A Tauri app that is **fully quit** is Row 5 (offline) with a caveat: in the bundled desktop build the engine ships *inside* the app, so quitting the app stops the engine too — there's no remote service to push from. Native delivery therefore covers the app-running cases (Row 4, and Row 5 only while a separate engine is still reachable); a quit single-process desktop install has nothing to deliver and re-syncs the bell badge on next launch.

**The OS-surface decision runs for any connected client, not just web-push subscribers.** `send_push_to_all_with_app` used to bail the instant `push_subscriptions` was empty. It no longer does: the PresenceCheck decision (and therefore the toast / native-banner emit) runs whenever any client is reachable — a web-push subscription **or** an open SSE connection / fresh heartbeat. So a desktop-only workspace with zero web-push subscriptions still gets in-app toasts (suppressed branch) and native banners (allowed branch). The engine only short-circuits to "do nothing" when there is no subscription **and** nobody connected.

**Row 1 requires a non-null `event_id`.** `notifications.event_id` is nullable; some notifications (scheduler errors, ad-hoc `send_notification` calls without an event ref, audit events) have no specific source event. When `event_id` is null, Row 1 cannot be evaluated and the device falls through to Row 2 (if thread matches) or Row 3.

**Multi-tab / multi-window per device.** Two Lucidos tabs on the same browser share `device_id` (per-origin localStorage) and each maintain their own SSE connection. Both receive PresenceCheck pings and each POST their own pong. Reconciliation:
- For Step A's `is_active`: logical-OR across pongs from the same device. If ANY tab on a device pongs as active, that device counts as active.
- For Step B's auto-read (Row 1): if ANY tab pongs as "event in viewport on source thread", the auto-read endpoint is hit once. `POST /api/v1/notifications/:id/read` is idempotent — re-marking an already-read notification is a no-op.
- Step B for the in-app surface is evaluated **per tab**, not per device. Each tab checks its own focused thread / viewport on SSE receipt; the device-wide pong reconciliation only matters for Step A.

**Worked example.** macOS Chrome with Lucidos in a background tab; iOS PWA with the screen off in your pocket.
- Step A: Chrome's `device_presence` row was deleted when the tab went background (visibilitychange fired DeviceHidden), but its **EventSource stays open** while backgrounded, so it counts toward the live SSE-connection gate → the engine runs the PresenceCheck. Chrome pongs `is_active: false` (hidden — `hasFocus()` is false). iOS's PWA is suspended with its EventSource closed, so it never pongs. No `is_active` pong arrives within the deadline → `push_allowed = true`.
- Step B for Chrome: row 4 → OS push fires; bell badge updates via SSE when the page comes back into focus.
- Step B for iOS: row 5 → OS push fires via APNs.
- Both devices get a push.

If you reported "Chrome bell only, no OS push" in this scenario, the bug is one of: (a) the visibilitychange event didn't fire DeviceHidden, leaving Chrome's presence row as a stale candidate; (b) Chrome was never subscribed to push at all (no permission grant, no service worker registration); (c) the push was sent but Chrome dropped it. Tests in §5 cover each.

## §3: The PresenceCheck protocol

**Trigger.** When `NotificationCreated` is emitted, the engine decides whether to run the PresenceCheck from two signals (`expected_pong_count` in `crates/lucidos-engine/src/scheduler/push.rs`):

1. **Live SSE-connection count** (`engine.sse_connections.count()` — the number of open `GET /api/v1/events` streams). This is the **primary, authoritative** gate: a connected page can pong regardless of how stale its heartbeat is. It increments when a page opens its EventSource and decrements when the stream is dropped (client disconnects), so it can't go stale while a page is connected.
2. **`device_presence` candidates** — rows fresher than `PRESENCE_STALE_AFTER` (120s — `crates/lucidos-engine/src/core/device_presence.rs`), refreshed by a 30s heartbeat (`device-presence.ts:HEARTBEAT_INTERVAL_MS`) plus a forced refresh on `visibilitychange-while-visible`. A secondary signal that covers the inverse failure: a page that heartbeated within the last 120s but whose SSE connection just dropped (network blip).

The engine runs the PresenceCheck when `max(sse_connections, candidate_count) > 0`, waiting for that many pongs (the deadline short-circuit fires once they all arrive). It skips the protocol and sets `push_allowed = true` directly **only when both are zero** — nobody is reachable (the "phone in your pocket" case).

**Why the SSE gate, not heartbeat freshness alone.** iOS suspends the 30s heartbeat timer while a PWA is foregrounded (and never fires `visibilitychange` because the page never went hidden), so a genuinely-active page's `device_presence` row ages past the 120s window even though its EventSource is open and it would pong `is_active`. Gating only on heartbeat freshness then skipped the PresenceCheck and fired an OS push on top of the active page ("push while the app was foreground for a while"). The live SSE-connection count doesn't depend on the heartbeat surviving, so the active page always gets a chance to pong and suppress the push.

**Ping.** Engine broadcasts a transient SSE event to every connected page. It is a **pure pong trigger** — it carries no toast content (that rides on `NotificationToastRequested`, §4):

```json
{
  "type": "PresenceCheck",
  "data": {
    "notification_id": "<uuid>",
    "event_id": "<uuid or omitted>",
    "deadline_ms": 2000,
    "sent_at_ms": 1700000000000
  }
}
```

The deadline value (`DEADLINE_MS` in `crates/lucidos-engine/src/scheduler/push.rs`) is sized for an iOS PWA reaching the engine over cellular or a Tailscale tunnel. Two RTT bands appear in real traces: steady-state cellular / Tailscale relay rounds the SSE-out + pong-POST trip in 400–800 ms, but the first packet after the phone radio resumes from idle pays the Tailscale (userspace WireGuard) path renegotiation cost — that band routinely lands at 1100–1800 ms. The deadline still governs how long the engine waits for the pong before deciding, but it **no longer races the toast**: the toast is not rendered on PresenceCheck receipt anymore, so a slow pong now degrades to "OS push instead of toast" (never "toast AND push" — see §4). The wait only blocks fan-out when a candidate fails to pong; `notify_one` wakes the engine immediately once every expected device has answered (see `run_presence_check`), so a larger deadline only costs latency when a `device_presence` row is stale (page killed without firing `DeviceHidden`).

`event_id` rides along only so the pong can report `event_in_viewport`. `sent_at_ms` is the engine's wall clock at emit; the page drops PresenceChecks where `Date.now() - sent_at_ms` exceeds `deadline_ms + grace` ("Freshness gate" below). A dropped PresenceCheck now only skips a pong the engine would have discarded anyway — it can no longer leak a toast, since PresenceCheck doesn't render one.

**Freshness gate.** iOS PWAs suspend JS in the background and queue SSE messages until the page becomes visible again. When the user taps the OS push, the queued PresenceCheck flushes AFTER the engine's deadline has long passed. The page-side gate compares `Date.now() - sent_at_ms` against `deadline_ms + 2000ms` (`STALE_GRACE_MS` in `presence-pong.ts`) and drops late pings entirely — no pong. The page reads `deadline_ms` off the payload (not a baked-in constant), so a bump on the engine flows through to the page automatically. (Since PresenceCheck no longer renders a toast, a late ping can at most cost a discarded pong; the *toast's* own staleness is gated separately on `NotificationToastRequested` — see §4.)

**Pong.** Every receiving page synchronously gathers its live state and POSTs `/api/v1/presence-pong`:

```json
{
  "notification_id": "<uuid>",
  "device_id": "<string>",
  "is_active": true,
  "focused_thread_id": "<uuid or null>",
  "event_in_viewport": true
}
```

- `is_active` is `isPageActive()` — visibilityState + hasFocus on desktop, visibilityState only on iOS PWA.
- `focused_thread_id` is the current value of the `focusedThreadId` signal.
- `event_in_viewport` is computed by the page: locate the source event in the DOM (e.g. `document.querySelector('[data-event-id="..."]')`); if absent (virtualized list, source event not rendered) → `false`; if present → `IntersectionObserver` / `getBoundingClientRect()` check.

**Decision.** After `deadline_ms`, the engine has zero or more pongs.
- `push_allowed = !any(pong.is_active for pong in pongs)`. Pongs are grouped by `device_id` and OR'd within a device (see §2 "Multi-tab" note); the OR across devices is the same operation.
- If every candidate device returned a pong before the deadline, the engine short-circuits and decides immediately.
- **`push_allowed = false` → the engine emits a `NotificationToastRequested` SSE** (`emit_toast_requested` in `push.rs`) and sends NO push. **`push_allowed = true` → the engine fans out the OS push** and emits no toast event. These two branches are complementary: a notification produces a toast-request OR a push, never both. This is what makes the in-app toast and the OS push mutually exclusive — they hang off opposite sides of one decision rather than racing (see §4).

**No batching across notifications.** A burst of 10 notifications in 5 seconds produces 10 independent PresenceChecks. Realistic notification volume is low and the checks run in parallel (each notification spawns its own deadline timer), so the burst latency is bounded by a single deadline window (~2 s in the worst-case "stale candidate" branch), not 10 × `DEADLINE_MS`. Batching is a future optimization; the spec does not depend on it.

**Failure handling.**
- A device that received the ping but failed to POST a pong → treated as not-active (most likely the page is dying or the network is unreliable; pushing is the safer side).
- A pong arriving AFTER the deadline → discarded with a `200 OK` ack (don't waste a `409`; this race is normal).
- A pong with an unknown `notification_id` → `404`. The notification was already decided and forgotten.

**Why this works without silent-push risk.** The decision is made server-side BEFORE the push is sent. If the engine decides "send push", the service worker always calls `showNotification()`. No browser ever sees a push that the SW silently swallows. The `userVisibleOnly: true` push subscription contract stays clean and the origin is never penalised by the browser for "ghost" pushes.

**Cost.** Up to one `DEADLINE_MS` (currently 2 s) of added latency on notifications where a reachable device fails to pong before the deadline. Two cases produce a non-ponging-but-counted device: a `device_presence` row still fresh because the page was killed without firing `DeviceHidden`, or an SSE connection that's open at the socket level but whose page can't run JS to pong (e.g. a heavily-throttled or just-suspended background tab). When every expected device pongs, `notify_one` wakes the engine the instant the last pong lands and there's no latency tax — in particular an *active* page pongs within one round-trip, so the common "suppress and toast" path is fast. Notifications when nobody is reachable (no open SSE connection and no fresh heartbeat — the phone-in-your-pocket case) are not delayed at all.

## §4: The in-app surface (page-local)

The bell badge and toast are **two distinct triggers** that decode the same notification:

1. **Bell badge** — driven by SSE `NotificationCreated`. The handler is `handleNotificationSSE` in `notifications.ts`; it reloads the **unread set** (`unreadNotifications` in `store.ts`) from `GET /api/v1/notifications?filter=unread` (capped at the API's 100). Fires on every connected page (active or hidden) so the badge stays in sync. **The badge count is DERIVED, not fetched**: `unreadCount` is a `computed` over `unreadNotifications.length`, so there is no separate count number that can drift from the notifications themselves — the bug where the bell/content-panel icons showed unread while the inbox held none. The reload is **sequence-guarded**: every async load (`loadUnreadNotifications`) claims a monotonic seq and applies only if still the latest issued, and every local optimistic mutation (`markReadOptimistic` / `navigateToNotification` / `markAllRead`) invalidates any in-flight load before it removes from / clears the set. This covers the **in-app auto-read** path (Row 1 below): the same page fires a created-reload then, a beat later, marks the row read — the optimistic removal invalidates the in-flight created-reload, so the created notification can't briefly surface on the badge regardless of network response order. On page reload the set is hydrated fresh from the same endpoint, so a stale badge can't survive a load (there is no cached count anymore).
2. **Toast** — driven by SSE `NotificationToastRequested` (`handleNotificationToastRequested` in `in-app-notification-toast.ts`). The engine emits this event **only after it has decided to suppress the OS push** (§3 "Decision": `push_allowed = false`), carrying the toast content (`title` / `body` / `thread_id` / `event_id` / `app_id` / `tap` / `sent_at_ms`). Active pages render the toast (or auto-read on Row 1); hidden pages ignore it (Row 4). Inactive devices get the OS push instead — and because the push and the toast-request live on opposite branches of one engine decision, a device never gets both.

   The toast used to fire on the §3 PresenceCheck pong handler — synchronously, the instant the page saw the ping. That raced the push: the page rendered the toast at half a round-trip while the engine's push suppression needed the full pong round-trip to beat a fixed deadline. On a slow iOS link the pong lost the race, so the engine fanned out the OS push *on top of* the already-rendered toast. Moving the toast behind the engine's decision removes the race entirely — a slow pong now degrades to "OS push, no toast" (the normal hidden-device outcome), never "toast AND push".

**The toast carries a single explicit `[Open]` button (right / primary) plus the X — never a whole-surface click, never an auto-open, never an `[OK]`.** For `tap.kind === 'modal'` (the default, or a missing `tap`) and `tap.kind === 'navigate'`, the Rows 2/3 toast renders ONE button through the `Toast` component's `action` (rendered right / primary): **`[Open]`** runs `dispatchDeepLink` — opening the notification detail in the content pane for `modal` (the `view-notification` action), or navigating to the destination for `navigate` — and marks the notification read, so a toast the user has acted on never has to be re-read in the Notifications panel. **The two meaningful outcomes are act-now (`[Open]`) or defer (the X):** the toast **persists** (no auto-dismiss) so `[Open]` stays usable, and the close (X) button dismisses **without** marking read, keeping the row unread in the bell badge + panel for later. There is deliberately **no `[OK]` / acknowledge button** — on a toast that has somewhere to go, marking read *without* opening is a footgun (it would bury an unanswered question), so the only "clear it" is `[Open]` (act) and the only "not now" is the X (defer). The whole-toast text is NOT a click target and the detail panel is **never auto-opened** when the toast appears — it opens only on an explicit `[Open]` click (`notification-toast-requested.test.ts` pins this no-auto-open contract; auto-opening the detail on top of the toast is the regression it guards). These toasts also set `noAutofocus`, so an unsolicited toast can't steal keyboard focus mid-typing — `[Open]` stays Tab-reachable but a reflexive Enter can't navigate/open a notification the user never chose to act on. (`view-notification` opens the detail in the content pane — `panelOverlay = { type: 'notification-detail' }`, rendered by `NotificationDetailInline` — not a modal overlay; `tap.kind === 'modal'` is the wire name of the tap, not a UI modal.)

**The notification's `title` is the toast's HEADING — a producer must never restate it in the `body`.** The toast is a single string, so `showInAppNotificationToast` serializes the notification's separate `title` and `body` through `composeToastMessage` (`components/shared/toastMessage.ts`, the inverse of the `parseToastMessage` contract that reads line 1 as the heading and `"• "`-prefixed lines as bullets). A **plain single-line** body stays inline after the title (`"Permission needed: Edit /path"`); a **structured** body — more than one line, or a single `"• "` bullet — starts on line 2 so the title keeps the heading to itself. Producers therefore write the body as *content only*: bullets for a list, a bare sentence for a single item. Restating the title on the body's first line renders it twice (the toast heading, the detail pane's `<h2>`, and the OS push banner title all show the title in their own right) — the "1 change ready to apply: 1 change ready to apply" regression, whose producer had repeated the title to force the heading back when the toast fed the raw body straight to `parseToastMessage`.

**The passive `tap: "none"` kind is RETIRED — every notification is openable.** It was a button-less variant that auto-marked-read on show and auto-dismissed after 5 s; it's been removed so a notification never renders as a dead banner (see `docs/plans/2026-07-02-remove-notification-tap-none.md`). Nothing produces `none` anymore: the `send_notification` tool schema and the SDK `Tap` type no longer offer it, the DB `notifications_tap_valid` CHECK rejects it for new writes, and a migration rewrote existing `{kind:none}` rows to `{kind:modal}`. Historical `NotificationCreated` events keep `{kind:none}` forever (event-sourcing immutability), but the engine's custom `Tap` deserialize coerces them to `Modal` on any replay (so a projection rebuild never re-emits a `none` row), and the frontend `resolveDeepLink` demotes any stray `none` (an old SW message / stale URL) to the openable `view-notification` path — never a passive `mark-read` or a no-op. Row 1 (auto-read because the user is already looking at the source event) is unchanged and applies to every kind.

Push (inactive devices) and toast (active devices) are therefore mutually exclusive **by construction** — but the construction is now the engine's single `push_allowed` decision, not a page-side timing race. The push-suppressed branch emits `NotificationToastRequested`; the push branch fans out the OS push. There is exactly one trigger for the active-device toast (the `NotificationToastRequested` SSE) and it can only fire when the push did not.

**Why not fire the toast on `NotificationCreated` SSE?** iOS PWAs suspend JS while backgrounded and queue SSE messages until the page becomes visible again. When the user taps the OS push, the queued `NotificationCreated` flushes AFTER the user has already landed via deep link — `isPageActive()` returns `true` and the matrix below would pick Row 2/3 incorrectly, producing a duplicate in-app toast on top of the push landing. `NotificationToastRequested` has its own freshness gate (`TOAST_REQUEST_STALE_AFTER_MS` in `in-app-notification-toast.ts`) that drops a toast-request that flushes late from the iOS SSE queue — so a queued toast never pops on top of a resume.

**On `PresenceCheck` received via SSE (and not dropped by the §3 freshness gate), the page only pongs:**

```ts
postJson('/api/v1/presence-pong', {
  notification_id, device_id,
  is_active: isPageActive(),
  focused_thread_id: focusedThreadId.value,
  event_in_viewport: payload.event_id ? isInViewport(payload.event_id) : false,
});
// No toast here — that's the engine's call, delivered via NotificationToastRequested.
```

**On `NotificationToastRequested` received via SSE (and fresh per `TOAST_REQUEST_STALE_AFTER_MS`), the page applies the §4 row matrix:**

```ts
if (!isPageActive()) return;                       // Row 4: hidden — bell badge only.
const onSource = payload.event_id
  && focusedThreadId.value === payload.thread_id
  && isInViewport(payload.event_id);
if (onSource) {
  markReadOptimistic(payload.notification_id);     // Row 1: looking at the source event.
  // no toast
} else {
  showToast(payload);                              // Row 2 / 3: active, scrolled away or other thread.
}
```

**Independence within the matrix.** A notification can produce any combination of (push only / toast only / both / neither):
- All devices hidden → push fans out to all subscriptions. No in-app toast anywhere.
- One device active, others hidden → push suppressed globally; in-app toast on the active device only.
- Multiple devices active → push suppressed globally; in-app toast on every active device whose §4 row resolves to toast.
- Active device pongs as Row 1 (event in viewport) → no push to anyone, no toast on this device (auto-read), toast on any OTHER active device on a different thread.

**Reconnection.** On page load / reload, the unread set is hydrated from `GET /api/v1/notifications?filter=unread` so a notification that arrived while the page was offline correctly shows in the badge (which derives its count from that set). Toasts missed while offline are NOT replayed on reconnect — the unread set is the durable signal.

**Read marks are global.** Reading a notification on one device clears the badge on all other devices via the existing `NotificationRead` event broadcast. Auto-read in Row 1 emits the same event as a manual read tap.

**Cross-device OS-banner dismiss (macOS desktop only).** Beyond clearing the in-app badge, a read also removes the *already-delivered OS banner* on other devices — but only on the native macOS desktop client. When a read flips (`NotificationRead`, or `NotificationsAllRead` for mark-all), the engine broadcasts a transient `NativePushDismissRequested` (`notification_id: Some(id)` for one, `None` for all; carries `sent_at_ms`). A connected Tauri desktop app removes the matching delivered banner(s) via `UNUserNotificationCenter.removeDeliveredNotifications(withIdentifiers:)` / `removeAllDeliveredNotifications` (dropping the stashed deep link so a phantom tap can't route — see the native section below). This is the **one platform where cross-device dismiss is both possible and deterministic**: the desktop app stays SSE-connected, and native notifications have no "must show something" rule. The **open web cannot** do this — Safari revokes a Web Push subscription after 3 silent pushes, and Chrome/Firefox show a default "site updated in background" banner on a silent push — so browser / PWA banners persist until manually swiped (the in-app badge still syncs via `NotificationRead`). The page handler `handleNativePushDismiss` gates on `isTauri()` (browser / PWA ignore the event) and on the `sent_at_ms` freshness budget (which bounds — does not fully eliminate, since `removeAllDeliveredNotifications` is blunt — the window in which a late dismiss-all could clear a banner for a notification created after an all-read); there is **no** `isPageActive()` gate, because removal is a harmless no-op when nothing matches. A **native iOS app** could dismiss via the same UN API, but it is deferred and best-effort (a backgrounded iOS app's SSE is suspended, so it would need a silent/background APNs push to wake it) — see `docs/plans/2026-06-19-ios-native-apns-app.md`. The abandoned web-only approach (replace the banner with a visible "✓ Read on another device" tombstone) is in `docs/plans/2026-05-18-cross-device-notification-dismiss-design.md`.

### Native desktop OS surface (Tauri)

The Tauri desktop app embeds a WKWebView, which has no service worker and can't subscribe to Web Push — so the web-push half of the *OS surface* (§1) never reaches it. The native banner fills that gap, driven page-side from the same SSE stream:

- On the **push-allowed branch** (`push_allowed = true`, §3 "Decision") the engine emits a `NativePushRequested` SSE *alongside* the web-push fan-out. It carries the same content as `NotificationToastRequested` (`title` / `body` / `thread_id` / `event_id` / `app_id` / `tap` / `sent_at_ms`).
- The page handler (`handleNativePushRequested` in `native-push.ts`) gates before touching the OS: **not Tauri → ignore** (browser / PWA already received the real web push on this branch); **stale per `NATIVE_PUSH_STALE_AFTER_MS` → ignore** (late SSE-queue flush, same reasoning as the toast's freshness gate); **`isPageActive()` → ignore** (the OS surface is for non-active devices, and macOS suppresses banners for the frontmost app anyway). It then invokes the app's `show_native_notification` command (`utils/tauri.ts`), passing the deep-link target in the SW-message shape (`notification_id` / `thread_id` / `event_id` / `tap`).
  - **The trayed-window case depends on the native-active bridge (§1).** Without it, a window dismissed to the menu-bar tray (macOS `orderOut:`) keeps the WKWebView reporting `visibilityState='visible'` / `hasFocus()=true`, so `isPageActive()` stays true: the *engine* suppresses the push (the trayed page pongs `is_active:true`) AND this handler early-returns — the user gets neither a banner nor a visible toast, only the bell badge. With the bridge, a trayed/unfocused client reports inactive, so the engine takes the push-allowed branch and this handler shows the native banner. (A window merely behind another app already reports inactive via `hasFocus()`; the bridge makes that deterministic too and is the *only* thing that fixes the trayed `orderOut:` case.)
  - **The bridge is SEEDED on page load, not just transition-driven** (the "notifications only come sometimes" fix). The `native-window-active` cache (`utils/nativeWindow.ts`) defaults to `true` and is otherwise updated only by the transition events the Rust `on_window_event` emits (`Focused` / `CloseRequested` / `show_main_window`). Tauri does **not** replay those events to a listener that registers after the fact, so a freshly (re)loaded page that is actually backgrounded/trayed — crash-watchdog reload (`lib.rs`), the "New version → Refresh" reload, or a cold/unfocused launch — would keep the `true` default until the *next* focus change, pong `is_active:true`, and get its push suppressed into an invisible toast. So `startNativeWindowActiveTracking` first **pulls the authoritative AppKit state** via the `get_native_window_active` command (`focused && visible && !minimized`, any read failure → `false`/inactive, the safe direction) and seeds the cache **before** registering the transition listener. Off-Tauri it's a no-op (the cache stays `true`, web behaviour unchanged).
- **Why a direct `objc2` `UNUserNotificationCenter` path, not a crate.** Two crates were tried and dropped. `tauri-plugin-notification`'s desktop `show()` is fire-and-forget — it never reports the click (its `onAction` is mobile-only) — so it can't drive tap routing. `mac-notification-sys` (the crate `notify-rust` uses on macOS, and what the plugin sits on) drives Apple's **deprecated `NSUserNotification` API**, which no longer delivers on recent macOS (banners silently never appear on macOS 26 "Tahoe"). The shipped path drives Apple's modern **`UserNotifications`** framework (`UNUserNotificationCenter`) directly through `objc2`: build a `UNMutableNotificationContent`, post a `UNNotificationRequest` (no trigger = deliver now), and install a `UNUserNotificationCenterDelegate` to capture taps. See `crates/lucidos-app/src/notifications.rs` (the `show_native_notification` command forwards to it).
- **The delegate implements `willPresent` (banners show even if the app is frontmost).** macOS suppresses a banner for the *frontmost* app unless the `UNUserNotificationCenterDelegate` opts in via `userNotificationCenter:willPresentNotification:` — so without it, a `show()` issued while Lucidos happens to be frontmost is silently dropped (the inverse of the "only sometimes" miss: a *stale-false* active signal makes the page call `show()` when the app is actually focused). The delegate returns `[.banner, .list, .sound]`. This is safe and not double-surfacing: the engine only emits `NativePushRequested` (→ the page's `show()`) on the no-active-device branch, so a banner and an in-app toast can never both fire for one notification.
- Because `NativePushRequested` and `NotificationToastRequested` are emitted on opposite branches of the one `push_allowed` decision, a desktop device never gets both a native banner and a toast for one notification — identical to the web-push/toast exclusivity.
- **Cross-device dismiss (removal counterpart).** The same `objc2` `UNUserNotificationCenter` path also *removes* delivered banners: the `dismiss_native_notification` command (`notifications::dismiss`) calls `removeDeliveredNotifications(withIdentifiers:)` (one) / `removeAllDeliveredNotifications` (all), driven by the engine's transient `NativePushDismissRequested` SSE when a notification is read on any device (see §4 "Cross-device OS-banner dismiss"). It also drops the banner's stashed deep link from the in-process map so a tap on a now-removed banner can't route. The page handler (`handleNativePushDismiss`) gates on `isTauri()` + `sent_at_ms` freshness (no `isPageActive()` gate). Inert in `tauri dev` / off macOS, like `show`.

**Enabling.** There is no web-push subscription to create on desktop, and the macOS `UserNotifications` path has no JS-queryable permission — macOS shows banners per the app's authorization, which the app requests once at startup (`notifications::setup`) and which the user can later change in System Settings → Notifications. So "enabling push" on the Tauri app (the same `initPushSubscription` entry point the LLM `enable_push_notifications` tool and the settings toggle drive) is a no-op success; `handleNativePushRequested` renders banners with no further setup. **Native banners require a packaged `.app` build.** `UNUserNotificationCenter.currentNotificationCenter()` throws for a process with no bundle identifier, and a `tauri dev` build is an unbundled `cargo run` binary — so `notifications::{setup,show}` both short-circuit on `tauri::is_dev()` and native banners are inert in dev *on any macOS version* (the old `NSUserNotification` + Terminal-impersonation hack that used to limp along in dev is gone, since it no longer delivers on recent macOS either). In dev, browser / PWA clients still receive the real web push on the same branch, so the dev notification channel is the browser. A packaged build (`cargo tauri build`) uses the app's own bundle identifier (`app.config().identifier`) and delivers; macOS prompts for notification authorization on first launch.

**A new install starts on the persistent "Alerts" style, not auto-dismissing "Banners".** macOS gives every newly-authorized app a per-app alert style, defaulting to *Banners* — which vanish after ~5 s, often before the user can tap one. The bundle requests *Alerts* instead by declaring `NSUserNotificationAlertStyle` = `alert` in the partial `crates/lucidos-app/Info.plist` the macOS bundler merges (see `docs/desktop-app.md` § Bundle `Info.plist`). macOS reads that only when it first creates the app's Notification Center entry, so it sets the **starting** style and never overrides a choice already made in System Settings → Notifications → Lucidos — a user who prefers banners keeps them, on this install and across updates.

**Tap routing — same router as the web-push tap, delivered DURABLY.** Taps arrive through the delegate's `userNotificationCenter:didReceiveNotificationResponse:` callback (on the main thread). The delegate keys off the response's notification `identifier` (set to the engine `notification_id` at `show` time) to look up the show-time deep link from an in-process map, focuses the main window (the OS also activates the app), then routes it. A dismiss (`UNNotificationDismissActionIdentifier`) drops the link without routing. The page (`setupNativePushTapRouting`, wired once in `useStartup`) runs the link through `parseDeepLinkFromSwMessage` → `dispatchDeepLink` — the **exact** router the web-push service-worker tap uses — so a native tap marks-read and navigates identically to a web-push tap (the `modal` default opens the notification detail in the content pane, navigate deep-links the thread/app).

Delivery is durable, not fire-and-forget (the "deeplink didn't work" fix). The old path *only* `app.emit`'d `native-notification-tapped`; if the page wasn't actively listening at emit time — WKWebView suspended while trayed, a watchdog/version reload mid-tap, or the listener's async registration not yet resolved — Tauri dropped the event with no replay and the tap was lost. Now the delegate **stashes** the deep link into a pending-taps queue *and* fires `native-notification-tapped` as a wake signal; the page **drains** that queue (the `take_pending_native_taps` command) on FOUR triggers: its startup **cold** path, each live **warm** signal, and the window regaining **focus** / **visibility**. The drain is atomic in Rust (`std::mem::take` under a `Mutex`), so a tap routes **exactly once** across all four triggers and never re-fires on a later reload. The queue is soft-capped (FIFO drop) so a long-resident client whose signals are all missed can't grow it unbounded.

The `focus` / `visibilitychange` triggers are the load-bearing ones for a *running* client (the "tap focuses the window but never deep-links" fix). A banner only ever shows while the page is **inactive** (`handleNativePushRequested` gates on `isPageActive()`), so a banner tap **always** lands on a backgrounded/hidden — often JS-throttled — WKWebView. `show_main_window` then **shows the existing window without reloading**, so the startup cold drain never re-runs, and the warm `app.emit` is a fire-and-forget `eval` WebKit can drop onto a just-resumed webview — leaving *no* drain trigger at the exact moment the tap brought the window forward. The `focus` (window becomes key) and `visibilitychange`→visible (un-occluded) events WebKit dispatches **in** the webview on show are eval-independent, so they reliably catch the stash the warm signal missed. `setupNativePushTapRouting` registers them before the warm listener (a `listen` failure can't strand them) and its returned unlisten removes all triggers; all are Tauri-gated, so browser / PWA and `tauri dev` are unaffected.

**Relaunch fallback → modal.** The show-time deep-link map is in-process only, so a tap on a banner delivered by a *previous* client process (the map is empty after relaunch) used to route nothing. Because the UN request `identifier` IS the engine `notification_id`, the delegate now synthesizes a minimal `{ notification_id }` link in that case — enough for a `Tap::Modal` default tap to open the notification detail. A navigate-kind tap degrades gracefully to the modal (the durable tap content from the live session is gone), which matches the default tap behaviour the user expects; the bell badge (`NotificationCreated`) remains the durable signal regardless.

### App-icon badge (Badging API + native dock tile / menu-bar tray)

The unread count is mirrored onto the installed app **icon** (surface 3 in §1), separately from the in-app bell badge. The value depends on the install context, which falls out of the relative manifest scope (`scope: "."` in `manifest.json` resolves against the stamped `<base href>`):

| Context | Badge value | How it's set |
|---|---|---|
| **Workspace PWA** (`/<slug>/` via gateway, or `/` direct engine) | this workspace's unread count | `syncWorkspaceAppBadge()` (live, while open — see "re-assert, never diff" below) + the SW `push` handler reading `app_badge` (closed, Chrome/Android) + iOS reading `app_badge` natively (closed, iOS) |
| **Gateway-root PWA** (installed from the picker at `/~/`) | aggregate total across running workspaces | the picker (`WorkspacePicker.tsx`) sums `WorkspaceStatus.unread_count` each 2s poll and calls `applyAppBadge(total)` |
| **Tauri desktop app** | aggregate total across running workspaces | the desktop process (`desktop.rs`) reads the gateway's fresh `GET /~/api/v1/control/unread-total` aggregate and calls `crate::apply_unread_indicator`, which routes the count to whichever surface exists for the current macOS activation policy: the **dock-tile badge** while a client window is open (Regular — `notifications::set_dock_badge`, objc2 `NSApplication.dockTile().setBadgeLabel`), or the **menu-bar tray-icon title** while the client is menu-bar-only (Accessory, i.e. all windows closed — `notifications::set_tray_title` on the `lucidos-tray` icon), since an Accessory app has no dock tile. Both on the main thread. Event-driven AND polled: the loop recomputes the instant it's **nudged** (the active workspace's webview calls the `nudge_dock_badge` command from `handleNotificationSSE` when a notification SSE arrives — read in-app or from another device) so the count updates without waiting; the periodic `DOCK_BADGE_POLL_INTERVAL` tick is the safety net for BACKGROUND-workspace changes whose SSE this webview never sees |

`applyAppBadge` (`store/actions/app-badge.ts`) is feature-gated (`'setAppBadge' in navigator`) and best-effort — unsupported browsers and the Tauri WKWebView no-op. The workspace-PWA path goes through `syncWorkspaceAppBadge()` in the same module, which is guarded off the picker context (`IS_PICKER`) and off Tauri, so each context sets exactly one value.

**Re-assert, never diff (the bell and the icon must never disagree).** The icon badge is an **externally written surface**: iOS writes it from the push payload's `app_badge` in its parent process without running the page, and the SW `push` handler writes it on Chrome/Android — both while the page is backgrounded or closed. So the page must *re-assert* its own count (an unconditional write of `unreadCount`, the same single source the bell badge and the Unread tab project from) at every point where it (re)establishes the unread truth: `loadUnreadNotifications` after applying a fresh set, the mark-read paths (`removeFromUnread`, `markAllRead`), and page resume (`onResume` in `useStartup.ts`, before the reload so the icon matches the bell even when the engine is unreachable). The `unreadCount` effect in `store/effects.ts` is *additionally* there for instant change-driven updates and the module-init clear — it cannot be the only writer, because a computed whose recomputed value is equal notifies no subscriber: a resume-time reload landing the same count re-runs nothing. That gap is what left an iOS PWA showing **icon 1 / bell 0** after a notification was read on another device (or a tap dropped a row this device never held) — the count went 0 → 0 while the icon kept what the push wrote. A "skip the write when our count didn't change" optimization reintroduces it.

**Known boundary — a CLOSED PWA's icon can go stale.** Reads emit no push, and iOS only updates a web app's badge from a visible push, so a notification read on another device while this PWA is closed leaves its home-screen icon at the last pushed count until either the next push (which carries a fresh `app_badge`) or the user opening/resuming the app (which re-asserts as above). Nothing on the engine side can close that window without sending a spurious visible notification. The **aggregate** is **running workspaces only**: the gateway holds no DB handle (ADR 0014 §1), so it gets each count by HTTP-polling running engines (reusing the count-only `GET /api/v1/notifications?limit=0` probe in its supervise loop); a stopped workspace reports no count and contributes 0. The gateway-root PWA's scope (`/~/`) can't navigate into a workspace, so its badge is always the total; the Tauri count is set from a Rust loop independent of the loaded page, so it stays the total even when the webview is inside one workspace. That loop reads the **fresh** on-demand aggregate (`/~/api/v1/control/unread-total`, a live count fan-out over running engines) rather than the supervise loop's cached `last_unread`, because at nudge time — right after a read — the cached value still shows the pre-read count; using the fresh endpoint for both the nudge and the periodic tick also avoids a flicker where a stale tick would briefly overwrite a freshly nudged value. **Dock badge vs tray title** (macOS): closing all client windows drops the app to the menu-bar tray (Accessory activation policy → out of the Dock and Cmd+Tab; see `crates/lucidos-app/src/lib.rs` `set_menu_bar_only` / `apply_unread_indicator`), where there is no dock tile — so the same unread count moves to the tray-icon title and back to the dock badge when a window is reopened; `apply_unread_indicator` re-routes the last known count (`LAST_UNREAD`) on each transition.

## §4.5: Service worker wedge — mitigation stack

The OS surface (§1) depends on the registered service worker running `notificationclick` when the user taps a push. Chrome on macOS has a long-tail dispatcher bug ([Chromium #370536109](https://issues.chromium.org/issues/370536109), "Push Notifications `notificationclick` not handled in MacOS 15") where the SW handler is silently dropped — the OS notification stays on screen and the tap appears to do nothing. There are two observed variants:

- **Full wedge.** The SW stops dispatching ALL events. No `push`, no `message`, no `notificationclick`. Caught by the liveness probe below.
- **Partial wedge** (observed in live traces, 2026-05-22). The SW still handles `push` and `message` events but `notificationclick` is silently dropped. The next genuine `push` event resurrects the dispatcher and any queued clicks drain in a flurry — explaining the "clicked at T, page navigated at T+113s right after a new notification arrived" pattern. The liveness probe gives a false-positive "healthy" on this variant because `message` flows fine while clicks are dead.

No single mitigation covers both variants; Lucidos stacks three layers:

### Layer 1 — Declarative Web Push envelope + `launch_handler`

Every push payload the engine emits conforms to the [W3C Push API "Declarative Web Push"](https://github.com/w3c/push-api/pull/385) wire format ([WebKit blog](https://webkit.org/blog/16535/meet-declarative-web-push/), shipped in Safari 18.5+):

```json
{
  "web_push": 8030,
  "notification": {
    "title": "...",
    "body": "...",
    "navigate": "https://host/<slug>/?notification=...&thread=...&event=...&tap=...",
    "tag": "<notification_id or lucidos-notification>",
    "data": {
      "notification_id": "...",
      "thread_id": "...",
      "event_id": "...",
      "app_id": "...",
      "tap": { "kind": "modal" | "navigate", ... },
      "navigate": "#notification=...  (HASH form, same params, for the Chrome SW)"
    }
  },
  "app_badge": 3
}
```

Built by `build_push_payload` in `crates/lucidos-engine/src/scheduler/push.rs`. The `web_push: 8030` magic at the top level is the Push API spec's opt-in for declarative parsing (homage to RFC 8030). Safari 18.5+ recognizes the declarative fields, but on iOS the SW `push` handler still fires and must still call `showNotification()` for a visible banner (the seventeenth iteration tested skipping it and produced no notification). On tap, the only reliable payload field available before page JS runs is `notification.navigate`; `notificationclick` is not a reliable delivery channel for installed iOS PWAs.

The top-level **`app_badge`** is the Declarative Web Push app-icon-badge field (sibling of `web_push` / `notification`), set to the **workspace's current unread count** at send time (`0` clears the badge; omitted only when the count can't be read). It is the **only** way a *closed* iOS PWA updates its home-screen badge — iOS reads `app_badge` in its parent process WITHOUT running the service worker. On Chrome/Android the SW `push` handler reads the same field and calls `navigator.setAppBadge()`. Because it carries this engine's own count, a per-workspace PWA badges its own workspace (see "App-icon badge" below).

The PWA manifest declares `launch_handler: { client_mode: "navigate-existing" }` so the existing PWA window is reused (no new tab) when the OS navigates.

**Two navigate URL forms — absolute query for iOS, hash for the Chrome SW cold-open.** `notification.navigate` (consumed by iOS Safari) is an **absolute query URL** built from the subscription's stored service-worker scope, e.g. `https://host/<slug>/?notification=…`; `notification.data.navigate` (consumed by the Chrome SW `notificationclick` handler) is a **scope-relative hash** URL, e.g. `#notification=…`. Same deep-link params, different URL carrier. The split is load-bearing: iOS Safari reuses an already-open PWA window on tap and does **not** apply a same-document (hash-only) navigation to it — it just focuses the window, the URL never updates, and the page-side hash router finds nothing to route (symptom: *"tap nav to thread only focuses the app"*). A query string is a cross-document navigation iOS actually performs, so the page lands on the deep-link URL on load/resume. The URL is absolute because real iOS devices regressed when Lucidos relied on WebKit/APNs accepting a query-only relative `notification.navigate` (`?notification=…`): cold and hot taps displayed a notification but applied no URL. On the Chrome SW side the hash URL is used **only** by the cold `clients.openWindow()` path — when no Lucidos tab is open, the freshly-opened page's cold-start `handleHashLocation` reads the params off the hash. A warm, already-open Chrome tab is NOT routed by URL at all: `routeToDeepLink` focuses it and `postMessage`s the structured deep link straight to the page's `navigator.serviceWorker` 'message' listener (see "warm-tab routing" below). The page-side `parseDeepLinkFromUrl` reads both hash and query (hash wins when both carry a key), so the cold-open dispatcher handles either form.

**Warm-tab routing — postMessage, not `client.navigate()`.** When `notificationclick` finds an already-open top-level Lucidos tab, it `focus()`es it (which also unfreezes a Chrome-frozen page) and then `postMessage`s `{ type: 'lucidos:deep-link', target: <notification.data> }` to it. The page's `onServiceWorkerMessage` handler (`useStartup.ts`) runs `parseDeepLinkFromSwMessage` → `dispatchDeepLink` — the same router the URL path uses. This is deliberately NOT a fragment-only `client.navigate('/#…')`: that call *succeeds* against the warm, SW-controlled tab (so the SW returns thinking it routed) yet routes nothing, because (a) Chrome does not fire `hashchange` for a fragment-only `WindowClient.navigate()`, and (b) the page-side focus/visibilitychange resume safety net does not fire when the tab the user clicked back into was *already* the focused/visible tab. That combination is the "came back to the computer in the morning, tapped a push, the right Chrome tab focused and the notification even marked itself read, but the notification detail never opened / the thread never loaded" report — the SW-side mark-read fetch ran, but the page-side dispatch silently no-op'd. `postMessage` is independent of both `hashchange` and resume events, so it routes deterministically. (iOS never reaches this code — it handles the tap declaratively in the parent process.)

**Warm-tab routing is scope-filtered (gateway multi-workspace).** Behind the workspace gateway (ADR 0014) several workspaces share one origin under distinct prefixes (`/personal/`, `/dev/`, …), each with its own SW registered at `/<slug>/sw.js` scoped to `/<slug>/`. A push for `/personal` is delivered to the `/personal` SW — but `clients.matchAll({ type: 'window', includeUncontrolled: true })` returns **every** same-origin top-level tab, including an open `/dev` tab. `routeToDeepLink` therefore filters candidates with `clientInScope(c.url)` (pathname under the SW's `SCOPE_PATH`) before focusing/`postMessage`ing one: it only ever targets a tab in **its own** workspace. With only an out-of-scope tab open it falls through to `clients.openWindow()` at the scope-resolved deep link, opening a fresh `/personal` window rather than hijacking the `/dev` tab — whose store has no such thread/app, so the tap would otherwise silently "go nowhere". (At the legacy root scope `/`, every same-origin client matches, which is correct — one workspace there.)

**Stored subscription scope is load-bearing for iOS.** The page records the concrete service-worker scope URL (`scope_url`) when it subscribes or refreshes a push subscription. The API keeps it only when it matches the request's workspace prefix and, when the browser sends `Origin`, the same origin; malformed/cross-workspace values are ignored. The engine uses the stored value to build the iOS-visible absolute `notification.navigate` URL, preserving `/<slug>/` behind the workspace gateway without relying on a leading-slash root URL or a query-only relative URL. This avoids both known bad forms: `/?notification=…` escapes the workspace prefix and lands on the origin-root picker (sixteenth iteration), while `?notification=…` is correct by generic URL resolution but was not applied consistently by iOS/WebKit in practice (eighteenth iteration). Existing legacy subscription rows without `scope_url` still use the old query-only fallback until the next page load refreshes them.

Chrome / Firefox don't recognize the `web_push: 8030` magic; they pass the JSON straight to the SW `push` handler. The handler in `sw.js` reads `data.notification.title` / `body` / `tag` / `navigate` / `data` and calls `showNotification(...)` exactly as before, keeping the `navigate` option for [#382298314 "Implement Declarative Web Push"](https://issues.chromium.org/issues/382298314) when Chromium eventually ships it. `notificationclick` then runs as today and routes via the SW. Same payload, two handlers — Safari natively, Chrome via SW.

This single wire format covers both the iOS-PWA path (previously broken — `navigate` was set on `showNotification` options but Safari only honors `navigate` deterministically inside the declarative envelope) AND the future Chrome path that ships #382298314.

### Layer 2 — Liveness probe + recovery (full-wedge coverage)

Every push calls `showNotification` with `requireInteraction: true` so the notification stays visible after the OS event fires — a dropped click leaves the notification on screen for a retry rather than disappearing.

The page periodically pings the SW controller with `{ type: 'lucidos:ping' }`; the SW replies `{ type: 'lucidos:pong' }`. If no pong arrives within `PROBE_TIMEOUT_MS` (5 s), the page calls `recoverServiceWorker()` — `unregister` + re-register + re-subscribe push. The recovery is gated by `RECOVERY_COOLDOWN_MS` (60 s) so flapping can't churn the subscription endpoint. On success the page shows the toast *"Notifications repaired — service worker was unresponsive"*.

**Probe trigger points** (`useStartup.ts`, `checkSwHealth`):
- 5 s after page mount (cold-start).
- On `visibilitychange → visible`, `window focus`, `pageshow` — covers the "user returns to Lucidos" path.
- Every `SW_PROBE_INTERVAL_MS` (5 min) while `document.visibilityState === 'visible'`. Interval is start/stopped on visibility so hidden tabs don't burn CPU wakes.

**Probe blindness on partial wedge.** Because the probe uses `message`, it returns false-positive "healthy" when only `notificationclick` is broken. This layer cannot detect or recover from the partial wedge; Layer 3 exists for that.

### Layer 3 — Engine-scheduled wake-push (partial-wedge coverage, proactive)

Per Google's own [web.dev push-notifications-common-issues guide](https://web.dev/push-notifications-common-issues-and-reporting-bugs), the canonical workaround for a wedged SW is to send it a push — every push event resurrects the worker, and queued `notificationclick` events drain as a side effect. Lucidos does this from the engine, on a fixed delay, so the SW gets unjammed whether or not the user ever returns to the tab.

`crates/lucidos-engine/src/scheduler/push.rs::send_push_to_all_with_app`. After fanning out the real push, the engine inspects each subscription's owning `devices.user_agent`, filters to macOS-Chromium devices (`is_mac_chromium`), dedupes per `device_id` (a multi-tab device produces multiple subscriptions sharing one SW), and for each surviving device spawns a `tokio::spawn` that sleeps `MAC_CHROMIUM_WAKE_DELAY` (3 seconds) then calls `send_wake_push_to_device(device_id, notification_id)`. The wake's payload is byte-identical to the original push plus `wake: true`.

The SW push handler (`sw.js`, `push` event) branches on `data.wake === true`: still calls `showNotification` (Chrome enforces `userVisibleOnly: true` — skipping would count as a silent push against the per-origin budget) but with `renotify: false` + `silent: true`. The *intent* is that the OS replaces the existing notification with identical content in-place — no re-pop, no sound, no banner — while the act of dispatching the push event wakes the SW worker so the queued `notificationclick` events drain. The in-place replacement is **best-effort, not guaranteed**: on macOS, Chrome hands notifications to the native Notification Center, which does [not reliably honour web-`tag` replacement](https://intercom.help/progressier/en/articles/6582394-how-can-a-web-push-notification-replace-previous-notifications-in-the-notification-tray), so a wake can surface as a second visible banner. The most common such duplicate — the user has already *tapped* the original inside the 3 s window — is eliminated by the read-skip below; the residual case (no tap within 3 s, both banners briefly coexist for a genuinely-unread notification) is left as the acceptable cost of the mitigation.

**Skip when already read.** `send_wake_push_to_device` re-fetches the notification at fire time and returns `Ok(0)` *without sending* when it is already `read` (`wake_still_needed` in `push.rs`). The read flag is a precise proxy for "was the SW wedged": if the user tapped the original banner during the delay, `notificationclick` closed it and marked it read — proving the click drained and the SW was never wedged, so the wake has no job and would only resurrect the handled notification as a fresh unread banner (the user-reported "same push twice"). If it is still unread, either the user hasn't tapped yet or the tap was swallowed by a wedged SW — both want the wake. This has to be a *fire-time* check (not schedule-time) because the tap lands during the delay window. Covered by `s4_5_wake_skipped_when_notification_already_read`.

**Why 3 seconds.** Short enough that a tap-and-wait user perceives the click as "working immediately" rather than visibly delayed; long enough that Chrome doesn't coalesce the two pushes into a single dispatch (which would defeat the point — the wake needs to be a separate `push` event to resurrect the worker thread). Real-world trace (2026-05-22, 18:05:57 push → 18:06:02 `handleHashLocation/end` while `visibility: 'hidden'`) confirms the queued click drains inside this window without user attention.

**UA gate is engine-side.** `devices.user_agent` is captured at device registration (`POST /api/v1/devices/register`, called from `registerCurrentDevice` on every page load — see `api/settings.rs::register_device` and `core::DeviceStore::register`) and surfaced through `PushSubscriptionStore::get_push_enabled` alongside the subscription tuple. The engine doesn't ask the page anything per push — it just looks at what's stored. Non-Mac-Chromium devices (Safari, iOS, Firefox, Tauri, Chrome on Windows / Linux) skip the wake entirely, paying nothing extra. Devices with `user_agent = NULL` (legacy rows from before UA capture, or a registration race) are conservatively skipped — see `pick_mac_chromium_wake_targets`.

**Silent-push budget.** Chrome counts a push as "silent" only when `showNotification` is NOT called. We always call it, with identical title/body to the existing notification — Chrome counts it as visible. The pre-existing on-screen notification is replaced in-place (same `tag`) so the user perceives no change.

**Failure modes.** The spawned task lives for `~3 s + a web-push round-trip`. The captured `Arc<LucidosEngine>` keeps the engine struct alive, but the tokio runtime drop on engine shutdown still aborts the task at its next `await` — so survival across a restart is probabilistic (it works because `graceful_shutdown(10 s)` outlasts the 3 s sleep, not because the Arc protects the task). A notification fired in the final ~3 s of a restart will see its wake aborted; the next real push to the device drains the queue (the pre-Layer-3 behaviour). If `send_wake_push_to_device` returns `Ok(0)`, either the notification was read in the meantime (the read-skip above — the common, healthy outcome) or the device unsubscribed between the original push and the wake — logged but not an error. Per-device failures are isolated (one tokio task each).

### Net behaviour

- Safari 18.5+ on macOS / iOS: Layer 1 alone is the intended tap path — the OS processes the declarative envelope. **Correction (seventeenth iteration):** the SW `push` handler still FIRES on iOS (proven by the `[Client/sw] push` breadcrumb) — the earlier "bypasses the SW entirely" claim was wrong, and the SW's `showNotification` IS what renders the visible banner on iOS. **Tested-and-reverted dead end (do NOT retry):** we tried skipping `showNotification` on iOS+declarative (betting the OS would render the declarative notification as a fallback so the tap would be handled natively, dodging the `notificationclick` bug). On-device result: **NO notification appeared at all.** iOS only uses the declarative fallback when the SW push handler *errors/times out* — NOT when it cleanly resolves without displaying — so skipping just produces a silent push (no banner). Reverted; the SW now ALWAYS calls `showNotification`. The `navigate` field is an absolute QUERY URL (cross-document) precisely because iOS will not apply a same-document hash navigation to an already-open PWA window (it would just focus it), and real iOS devices did not reliably apply the later query-only relative form. On tap the OS navigates the window to `https://host/<slug>/?notification=…&thread=…&tap=…`, built from the stored subscription scope. Because that URL is cross-document, the tap is necessarily a **full page reload** of the PWA — there is no reload-free channel (WebKit implements neither `launchQueue`/`launch_handler: focus-existing` nor a same-document declarative navigate to an already-open window, confirmed 2026), so the reload *is* the navigation; the alternatives (hash URL / focus-only) silently drop the deep link, which is the bug the seventh iteration fixed. Two mitigations keep that reload cheap: (1) on a **built deployment** the SW serves the immutable content-hashed `/assets/*` bundles Cache-first (via `cacheFirst`) from `SHELL_CACHE` in `sw.js`, so a reload pulls the JS/CSS graph entirely from disk; the navigation shell (`index.html`) is served **network-first** (`networkFirstShell`, keyed by a normalized `/` request so every scoped `?notification=…` variant shares one cached entry) — fetched fresh when online so it always references the bundles the rebuilt server currently has, falling back to the `install`-precached cached shell when offline or on a transient non-ok response (e.g. a 502 mid engine-restart) — EXCEPT any **503**, the gateway's "engine not serving" signal for a stopped / cold-booting / lazy-starting workspace (ADR 0014 §11): the branded boot splash (ideally marked `X-Lucidos-Boot-Splash`) for a document navigation, or a plain "workspace stopped" body. A 503 is shown as-is rather than replaced by the cached shell, so the user sees the "workspace starting…" page instead of a stale shell that would 503-storm its API calls against the down engine (surfacing as a red connection dot when assets are cached, or a white screen when they aren't). The branch keys on the **503 status**, not the marker header — the gateway is a machine-global daemon that does NOT restart on a CC Apply, so a freshly-built gateway carrying the marker may not be the one actually running; keying on the status keeps the splash working against an older gateway too. (The shell was cache-first through the eleventh iteration, but a long-lived iOS PWA then pinned a stale shell pointing at `/assets/*` bundles a later build had deleted, the SPA fallback served those as `text/html`, and the PWA went all-black — see the thirteenth iteration below.) So only the ~9 KB shell HTML round-trips; the heavy graph stays on disk. The shell branch is gated on `IS_BUILT` + `mode === 'navigate'` + `path === '/'` (so the Vite dev server stays network-fresh for HMR, and app-UI iframe navigations under `/app/<id>/` are excluded — they are their own server-rendered HTML, not the SPA shell). The `/assets/*` branch self-gates by path, since a Vite dev install serves unhashed modules under `/src`,`/@vite`,`/node_modules/.vite` that are never `/assets/*` and must not be cached (HMR + stale code), so dev gets no shell or asset cache; (2) the page-side router dispatches the deep link on the next macrotask after boot rather than a fixed 500 ms delay (`setTimeout(handleHashLocation, 0)`), shaving that wait off every tap regardless of run mode. Mark-read AND deep-link navigation happen page-side: when that URL lands, `handleHashLocation` → `dispatchDeepLink` reads the query params, calls `markReadOptimistic`, AND `handleNavigationRequest` for navigate-kind taps. The router is wired to fire on cold-start (`setTimeout(500)`), warm `hashchange`, **and** every resume signal (`visibilitychange → visible`, `focus`, `pageshow`) — a warm tap is a cross-document load picked up by cold-start, and the resume signals catch any case where iOS updates the URL while the JS runloop is suspended. The dispatcher is idempotent (consumed params are stripped after dispatch, so subsequent calls no-op). See `crates/lucidos-app/src/store/actions/hash-deeplink-router.ts`.
- Chrome on macOS today: Safari's declarative path is ignored (no `web_push: 8030` recognition); the SW `push` handler parses the same envelope and dispatches via `showNotification` + `notificationclick`. On tap, `routeToDeepLink` focuses the open **same-workspace** tab (scope-filtered via `clientInScope` — see warm-tab routing above) and `postMessage`s the deep link to it — or `clients.openWindow()`s the scope-resolved hash URL when no in-scope tab is open. Layer 2 catches the full wedge, Layer 3 schedules an engine-side wake-push 3 s after every notification so the SW gets unjammed proactively. The user experience: "I tapped, OS didn't react immediately, ~3 s later the notification opened the right page." (Pre-Layer-3: "I tapped, OS didn't react, I had to switch back to the tab to recover.")
- Chrome the day [#382298314](https://issues.chromium.org/issues/382298314) ships: Layer 1 takes over automatically with no code change — the same declarative envelope is already on the wire; Layers 2-3 become defense-in-depth.

**Recovery is best-effort.** If `recoverServiceWorker` fails, the next probe retries after the 60 s cooldown. Layer 3 is the final user-visible safety net.

### Troubleshooting: push tap works on one device but not another (stale cached manifest)

**Symptom.** Tapping an OS push **navigates + marks read on one device** (e.g. a freshly-installed PWA) but **silently no-ops both** on another — no navigation AND the notification stays unread — even though both run the **same engine binary and frontend bundle**. The in-app navigation router is fine (tapping the inbox row / an "Open <app>" button works), and the failure is reproducible per-device, not random.

**Root cause.** iOS Safari snapshots `crates/lucidos-app/public/manifest.json` at **"Add to Home Screen" time** and never refreshes it without a reinstall. The `launch_handler: { client_mode: "navigate-existing" }` field — required for iOS to *navigate* an already-open (backgrounded) PWA window on a push tap rather than merely focus it — only landed **2026-05-22** (with the three-layer mitigation, Layer 1 above). A home-screen install created **before** that date carries a cached manifest **without** the field, so on a backgrounded tap iOS focuses the window and leaves the URL untouched; the page-side `handleHashLocation` → `dispatchDeepLink` chain never sees the `/?notification=…&tap=…` deep link, so **both** the navigation and the `markReadOptimistic` it would have driven silently no-op (they ride the same URL-dispatch chain — see Layer 1 / Net behaviour above).

**Why it looks flaky, not deterministic.** The notification often *eventually* flips to read because the Layer-3 wake-push (or the user's next notification) drains queued state later — masking the per-install determinism as intermittency.

**Why it's per-install, not per-version.** The frontend JS (`hash-deeplink-router.ts`, `parseDeepLinkFromUrl`, the resume listeners) loads fresh on every page visit, so even an old install runs current routing code. Only the **manifest** and the **SW registration** are cached at install time — and the manifest is the one that gates already-open-window navigation. So a device can run the newest code and still mis-handle taps purely because of its cached manifest.

**Diagnosis (no dev tooling).** Fire the same notification shape (`Tap::Navigate { to.target = App }`) to a *freshly-installed* PWA and to the *suspect* install via `POST /api/v1/notifications`. If the fresh one navigates + marks read and the suspect one no-ops both, it's the cached manifest — not a code regression. (Engine log line `[Push] Sent notification to https://web.push.apple.com/…` confirms the OS push actually fanned out; if you see `Suppressed OS push` instead, an active device pong'd in and you got an in-app toast, not a push — background the PWA and retry.)

**Fix.** Reinstall the PWA on the affected device: remove it from the home screen, reopen the site in Safari, **Add to Home Screen** again, and re-grant notifications so it re-subscribes (a new APNs endpoint is the confirmation the reinstall took). This re-snapshots the manifest with `launch_handler`. **Every device installed before the manifest change needs this** — there is no server-side way to force iOS to refresh a cached manifest. New installs (post-2026-05-22) are already correct, which is why this never reproduces on a fresh dev PWA.

Until now the desktop app explicitly refused push (`push.ts` toasted "Push notifications are not available in the desktop app") because its embedded WKWebView can't subscribe to Web Push — so when the window was backgrounded the engine's Row 4 path fanned out a web push the desktop had no transport for, and the user got nothing but a bell-badge bump they couldn't see. The fix mirrors the sixth iteration's toast/push split: on the push-ALLOWED branch the engine now emits a `NativePushRequested` SSE (the complement of `NotificationToastRequested` on the suppressed branch), and a connected Tauri page renders a native macOS banner — reached over the open SSE stream instead of a push service. This respects the existing global `push_allowed` suppression (no native banner on the laptop while you're actively using your phone) and reuses the whole §3/§4 machinery rather than adding a page-local decision. Two supporting changes: (1) `send_push_to_all_with_app` no longer bails the instant `push_subscriptions` is empty — it runs the PresenceCheck decision whenever any client is connected, which also fixes a latent gap where a workspace with zero web-push subscriptions got no in-app toasts either; (2) "enabling push" on desktop is a no-op success (no subscription to create, no JS-queryable OS permission).

The first cut rendered the banner via `tauri-plugin-notification`, but that plugin's desktop `show()` is fire-and-forget — `notify-rust` displays the banner and the click is never reported (its `onAction` is mobile-only), so it could not route the tap. The shipped iteration therefore drops the plugin and drives `mac-notification-sys` directly (the crate notify-rust uses under the hood) from a `show_native_notification` command: it shows with `wait_for_click(true)` on a worker thread, and on `NotificationResponse::Click` focuses the main window and emits a `native-notification-tapped` Tauri event carrying the SW-message-shaped deep link. The page (`setupNativePushTapRouting`) routes it through `parseDeepLinkFromSwMessage` → `dispatchDeepLink` — the exact router the web-push service-worker tap uses — so a native tap marks-read and navigates identically to a web-push tap. Regression coverage: `native_push_requested_serializes_with_type_tag` + `native_push_requested_is_transient_on_notification_aggregate` (engine unit), `s4_push_allowed_emits_native_push_requested_sse_with_no_web_subscription` (API e2e — a connected page with NO subscription still gets the native frame), and the `native-push.test.ts` suite (frontend: the not-Tauri / stale / active gates, the SW-message deep-link shape, and a tap routing through `dispatchDeepLink`).

The fifteenth iteration (2026-06-18) fixed **"tapped a notification for one workspace while a different workspace's tab was open and the tap went nowhere"** in the gateway multi-workspace topology (ADR 0014). Each workspace runs its own SW scoped to `/<slug>/`, so a push for `/personal` correctly fires the `/personal` SW's `notificationclick` — but `routeToDeepLink` selected the warm tab with an unfiltered `clients.matchAll({ includeUncontrolled: true }).find(top-level)`, and `includeUncontrolled` returns **every** same-origin tab. With `/dev` open and `/personal` not, `find()` returned the `/dev` tab; the SW `focus()`ed it and `postMessage`d the `/personal` deep link to it, where the `/dev` store has no such thread/app, so `dispatchDeepLink` silently no-op'd — the visible "tap goes to nowhere". Everything else on the path was already scope-correct (`resolveNavigate`, the `showNotification` icons, the `openWindow` fallback URL all resolve against `SCOPE_PATH`); only the warm-tab *selection* ignored scope. The fix adds `clientInScope(c.url)` (pathname under the SW's `SCOPE_PATH`, tolerating a missing trailing slash; root scope matches all) to the `find()` predicate, so the SW only focuses/messages a tab in its own workspace and otherwise `openWindow()`s a fresh in-scope window. iOS was assumed unaffected here (it handles the tap declaratively against `notification.navigate`, resolved against the subscription scope) — but that assumption was **wrong**: the engine built that URL origin-rooted (`/?…`), so on iOS it escaped to the gateway picker. The sixteenth iteration (below) fixes it. Regression coverage: the cross-workspace cases in the `notificationclick` deep-link routing suite in `crates/lucidos-app/src/sw.test.ts` (an out-of-scope tab is never focused/messaged → a new in-scope window opens; with both open only the same-scope tab is messaged; mark-read hits the scope-prefixed endpoint).

The sixteenth iteration (2026-06-18) fixed the iOS half the fifteenth iteration wrongly assumed was already correct: **every push tap on an installed iOS PWA landed on the gateway picker instead of the workspace, and the notification was never marked read** — same-workspace and cross-workspace alike (the user report: *"tap target does not work … probably all deeplinking from push broken in the new multi-ws app"*). The OS resolves `notification.navigate` against the push subscription's scope (= the SW registration scope, `https://host/<slug>/` behind the gateway). The engine built that URL as `/?notification=…` (leading slash) — an RFC 3986 absolute-path reference that **discards** the `/<slug>/` prefix and resolves to the ORIGIN ROOT (`https://host/?…`, the picker), which has no deep-link handling, so the tap went nowhere; and because mark-read on the declarative path is page-side (it rides the same URL dispatch via `handleHashLocation` → `dispatchDeepLink`), the row also stayed unread. Pre-gateway (single workspace at `/`) it worked because root *was* the workspace — which is why this only surfaced in the multi-workspace app. The sixteenth fix made both navigate URLs **scope-relative** in `build_push_payload` (`?…` for iOS, `#…` for the Chrome SW cold-open, `.` for the empty-params fallback): `?…` resolves to `https://host/<slug>/?…` because the subscription scope always carries a trailing slash, keeping the engine slug-agnostic. That was correct by spec, but superseded by the eighteenth iteration after real iOS devices failed to apply the query-only URL at all. The Chrome SW path is unchanged in behavior — `resolveNavigate` in `sw.js` already stripped the leading slash, so it defensively tolerates either form.

The seventeenth iteration (2026-06-19) is testing the fix for the **intermittent** iOS deep-link failure that survived the declarative migration: a push tap "just opens the app where I left it" *some* of the time, deep-links other times. Heavy instrumentation (the `[Client/sw] push` / `notificationclick` + `[Client/deeplink] handle_hash_location` / `dispatch` breadcrumbs on the `/internal/client-log` channel) plus on-device data settled the mechanism. It is a **documented WebKit bug** ([Progressier](https://intercom.help/progressier/en/articles/9213767-why-ios-push-notifications-sometimes-don-t-redirect-to-the-correct-url-in-a-pwa), [Apple Developer Forums 733604](https://developer.apple.com/forums/thread/733604), [firebase-js-sdk #7698](https://github.com/firebase/firebase-js-sdk/issues/7698)): on an installed iPhone/iPad PWA, a tap fails to navigate (just focuses, `notificationclick` never fires) **iff** the PWA is running AND was last launched from its home-screen icon (not from a notification). It WORKS when the app is not running (cold launch) or was last opened by a notification — which is why a working burst self-sustains (open-via-notification begets working taps) and "works after I restart the app" holds (force-quit → next tap cold-launches → works). The breadcrumbs confirmed: zero iPhone `notificationclick` ever; failing taps show only a resume `handle_hash_location {found:false}`; the working burst was a cold-launch-then-chain. The decisive realisation: **the SW `push` handler DOES fire on iOS** (contrary to the prior "bypasses the SW entirely" claim) and our handler called `showNotification`, REPLACING the OS-proposed declarative notification — which converts the tap into the very `notificationclick` path iOS won't fire. The candidate fix tried this iteration (SW-only, UA-gated): on iOS+declarative the SW skipped `showNotification`, betting the OS would render the declarative notification natively and handle the tap via `notification.navigate` — dodging the `notificationclick` path. **Tested on-device → FAILED, and reverted: NO notification appeared at all.** The premise was wrong — iOS uses the declarative push as a fallback only when the SW push handler *errors/times out*, NOT when it cleanly resolves without calling `showNotification`; a clean resolve with no display is just a silent push (no banner). So skipping made it strictly worse than the original bug (no notification vs. a notification that maybe-doesn't-navigate). **Do NOT retry skipping `showNotification` on iOS.** Reverted to always-display (the in-code note lives at the `showNotification` call in `sw.js`). **Net unresolved:** the running+icon-launched deep-link failure remains an unfixed iOS WebKit bug upstream of our code — `notificationclick` never fires and the declarative `navigate` is not applied to an already-running window, so neither the SW path nor the pure-declarative path can convey the tap. No reliable client-side cure exists (the only known "workaround", navigate-on-receipt, hijacks the user's session and is discouraged); options left are an Apple Feedback filing and/or a non-hijacking "you have a pending notification" affordance on resume. The diagnostic breadcrumbs (`[Client/sw] push`, `[Client/deeplink] *`) are kept. Plan: `docs/plans/2026-06-19-ios-pure-declarative-push-tap.md`.

The eighteenth iteration (2026-06-21) fixed the **consistent** iOS failure that replaced the old intermittent one: notifications still displayed, but taps no longer deep-linked or marked read hot OR cold. Cold failure rules out the seventeenth iteration's running-PWA-only WebKit bug. The regression was the sixteenth iteration's query-only `notification.navigate` (`?notification=…`). It avoided the gateway picker by keeping the path scope-relative, but left WebKit/APNs to accept and resolve a relative query string inside the declarative push payload; on-device evidence showed that value could be ignored entirely. The fix records the page's concrete SW scope URL on every push subscribe/refresh (`scope_url`) and builds iOS `notification.navigate` as an absolute scoped URL (`https://host/<slug>/?notification=…`). Existing rows without `scope_url` keep the query-only fallback until the next page load refreshes the subscription. Regression coverage: `declarative_navigate_uses_absolute_scope_url_for_ios`, `declarative_navigate_normalizes_scope_url_before_query_append`, `declarative_notification_data_carries_hash_navigate_url_for_chrome_sw` (engine `push_tests.rs`), the push-subscribe `scope_url` unit assertion, and the updated `notifications.spec.ts` push-log payload assertion.

The nineteenth iteration (2026-07-29) fixed **"the packaged desktop app stopped showing native banners entirely"** — and, for the same single cause, stopped doing anything else over IPC. Nothing on the notification path was wrong: the engine's `NotificationCreated` → `PresenceCheck` → push-allowed → `NativePushRequested` SSE all fired correctly with the window backgrounded, macOS notification authorization was granted, and the page received the frame. The banner never appeared because the `show_native_notification` command was **rejected by Tauri's ACL** before it ran. An in-range lockfile bump (`de287a93a`, tauri 2.10.2 → 2.11.4, shipped in v0.16.0) added a third arm to the ACL gate in `Webview::on_message` — `|| !is_local` — so every IPC request from a non-local URL is now checked as `Origin::Remote`. The packaged client's `frontendDist` makes its app URL `tauri://localhost` while `desktop::launch` navigates the window to the gateway (`http://localhost:<port>`), so the window is remote by that definition and our local-only capability granted it nothing. **Every** command died with it: `listen` (so the tap-routing and panel listeners never registered), `heartbeat` (so the WKWebView watchdog reloaded the window every 60s, 6232 times in one install), the window-drag/titlebar commands, the updater, and the `__panel_*_report` trio the URL preview needs — that last one in dev too, since a previewed third-party page is remote on any build. Dev otherwise looked healthy the whole month, because `devUrl` **is** the app URL there and dev pages take the local branch; only a packaged DMG exercises the remote path. The fix adopts the upstream hardening instead of pinning around it: the app now declares an ACL manifest (`crates/lucidos-app/permissions/app-ipc.json`), `desktop::launch` registers a capability for the gateway origin pinned to the resolved port before it navigates, capabilities are scoped by `webviews` (never `windows`, which would leak a remote grant to the `url-preview-*` webviews inside the main window), and the three panel-report commands get their own any-origin capability limited to those webviews. See ADR 0028. Two things also changed so this class of failure can't hide again: `invoke` now reports IPC failures to the engine log itself (`[Client/ipc]` lines via `postClientLog`, since a packaged `.app` has no console for the old `console.warn` carve-outs to reach), and the heartbeat watchdog backs off exponentially once a reload brings back no heartbeat at all, saying what that means, instead of thrashing once a minute in silence. Regression coverage: the `acl_tests` suite in `crates/lucidos-app/src/lib.rs` resolves the real generated capabilities through tauri's own `Resolved::resolve` + `RuntimeAuthority::resolve_access` (every registered command allowed from the gateway origin; foreign ports/hosts/schemes denied; previews limited to the three reports; a test that reproduces the regression by resolving without the gateway capability), plus `ipcHealth.test.ts` and the watchdog-backoff tests. What still needs a packaged build to confirm: that WKWebView's `Origin` header for our window is exactly `http://localhost:<port>` — the ACL decision for a given origin is unit-tested, the string the OS produces is not.

The fourteenth iteration (2026-06-16) **migrated the native desktop banner off the deprecated `NSUserNotification` API**. The twelfth iteration shipped `mac-notification-sys`, which drives Apple's `NSUserNotification` — deprecated since macOS 11 and progressively gutted; on **macOS 26 ("Tahoe")** it silently stopped delivering, so a backgrounded Tauri desktop app got no banner at all (the user still got the web push in a parallel browser, which is what surfaced the regression). The fix drives Apple's modern **`UserNotifications`** framework (`UNUserNotificationCenter`) directly via `objc2` (no `mac-notification-sys`, no `tauri-plugin-notification` — both sit on the dead API on macOS): `notifications::show` posts a `UNMutableNotificationContent` + `UNNotificationRequest`, and a `UNUserNotificationCenterDelegate` (installed in `notifications::setup` at startup, with an authorization request) handles taps via `didReceiveNotificationResponse`, looking up the deep link by the request `identifier` (the `notification_id`) and emitting the unchanged `native-notification-tapped` event. The hard constraint exposed along the way: `UNUserNotificationCenter` requires a **bundled `.app`** (its `current()` throws for an unbundled binary), so native banners are inert in `tauri dev` **on any macOS version** — `setup`/`show` short-circuit on `tauri::is_dev()`, and dev relies on the browser/PWA web-push path. Verifying native delivery requires a packaged build (`cargo tauri build`). The frontend contract (`NativePushRequested` SSE → `handleNativePushRequested` gates → `show_native_notification` command → `native-notification-tapped` on tap) is unchanged, so `native-push.test.ts` still covers the page side; the obj-c delivery path itself has no automated coverage (it can only be exercised in a packaged build).

The thirteenth iteration (2026-06-11) **reverses the eleventh's shell caching** after it caused the opposite failure: installed **iOS PWAs went all-black**. The eleventh served `index.html` cache-first, but the dev frontend rebuilds constantly (`vite build --watch` on every applied change), and each rebuild emits new content-hashed `/assets/*` bundle names and deletes the old ones. A long-lived PWA holds its service worker — and the cached shell — for a long time (iOS updates SWs lazily and the PWA is rarely fully closed), so the pinned shell kept referencing `/assets/index-<oldhash>.js` that the server had already deleted. The server's SPA fallback answers a missing bundle with `index.html` (200 `text/html`), not a 404, so the page loaded an HTML document as its entry module script, no JS ran, and `#app` painted black on the `#0d1117` background — **unrecoverable**, because with no JS loaded nothing page-side could self-heal. (Desktop tabs on localhost stayed fine: frequently reloaded, they kept fetching fresh shells. Tailscale was a red herring — it is merely *where* the iOS PWAs connect, not the cause.) The fix serves the shell **network-first** (`networkFirstShell` in `sw.js`): when online the SW fetches a fresh `index.html`, so the shell stays in lockstep with the server's current bundles, and falls back to the cached shell only when the fetch fails (offline / engine restarting) or returns non-2xx (a 502 mid-restart serves the last good shell, never pins it). The `/assets/*` graph stays cache-first (immutable by hash), so the reload still pulls the heavy JS/CSS from disk and only the ~9 KB HTML round-trips — the eleventh's "zero network on the critical path" becomes "one small HTML fetch", a deliberate trade of a sub-second fetch for never-black. Belt-and-braces: the `/assets/*` branch now refuses to cache an HTML response (`isHtmlResponse`), so a deleted-bundle SPA fallback can never poison a content-hashed entry under its URL. `install` still precaches the shell, now purely as the offline fallback. Existing black PWAs self-heal on the next relaunch (the new SW byte-differs → installs → claims → serves the fresh shell); a force-quit + reopen makes it immediate. Regression coverage: the rewritten "navigation shell (network-first)" suite in `crates/lucidos-app/src/sw.test.ts` (online always fetches a fresh shell even when one is cached; caches it under the normalized `/` key; offline falls back to the cached shell; a 502 mid-restart serves the cached shell and is never pinned; no-cache 502 passes the network response through) plus the new "/assets/* does NOT cache an HTML SPA-fallback body" test.

### §5.4: Test harness for OS push assertions

Browser e2e need to assert "OS push WAS sent" / "WAS NOT sent" without waiting for FCM/APNs delivery. Plan:
- Test-mode flag (env var or build-time feature) installs an in-memory push-transport stub. Real `web_push` calls instead append to an in-process `push_log` table keyed by `(device_id, notification_id, sent_at)` plus a `payload` column carrying the JSON bytes the real transport would have encrypted and sent. The payload column lets tests assert the Declarative Web Push envelope shape (`{web_push: 8030, notification: {…}}`) in addition to delivery.
- Expose `GET /api/v1/_test/push-log?since=<iso>` (mounted only when test mode is on, behind the same gating as `setup_test_db`).
- E2e helpers: `expectPushSent(page, notificationId, { deviceId?, timeoutMs? })` returns the recorded `PushLogEntry` (including the on-wire `payload` string) so tests can assert envelope shape, and `expectNoPushSent(page, notificationId, waitMs?)` proves suppression. Both poll via Playwright's `APIRequestContext` so the engine's self-signed localhost cert is trusted (Node's stricter `fetch` would reject).

The stub also bypasses the real APNs/FCM credentials, so e2e doesn't need either.

## §6: What this spec doesn't cover

- The notification payload (title, body, tap target) — see existing `NotificationCreated` event payload in `system-knowhow/thread-events.md`.
- The tap routing (`tap = { kind: 'modal' | 'navigate', to?: NavigateUi }`) — already covered by the `notifications.tap` JSONB column and existing handlers; the spec above is orthogonal to where the tap lands. (The passive `'none'` kind is retired — every notification is openable; see §4.)
- Permission grant UX (asking for notification permission) — see `initPushSubscription` in `packages/lucidos-sdk/` and the existing `system-knowhow/js-sdk.md` § `lucidos.notifications`.
- Server-side push delivery to APNs / FCM — covered by `scheduler/push.rs`. The decision to send is the subject of this spec; the actual HTTP POST is not.
- **Targeted notifications** (a notification aimed at one specific device, bypassing fan-out) — not a feature today. `send_notification` fans out to every push subscription. If targeted notifications are added later, this spec gets a §7 amendment.
- **Batching of bursts** — the current spec runs one PresenceCheck per notification (§3 "No batching"). Batching is a future optimization.

## §7: Implementation notes

The decisions above land alongside removals of code paths the old design relied on:

- **Delete `ThreadPresenceStore` + `thread_presence` table + `ThreadFocused` / `ThreadUnfocused` events + the frontend `/api/v1/thread-presence` POST loop.** PresencePong carries `focused_thread_id` live, so the engine no longer needs a persisted thread-focus index. Migration: drop the table.
- **Keep `device_presence` as the candidate index only.** `record_visible` / `record_hidden` / the 30s heartbeat stay — they're how the engine knows whether to RUN the PresenceCheck (no rows in 30s → skip the ping, set `push_allowed = true` directly).
- **Delete `DevicePresenceStore::any_visible()`.** The global suppression query is replaced by the pong-based decision. No callers should remain after the cutover.
- **Test-mode push log endpoint** (`GET /api/v1/_test/push-log`) is gated by a Cargo feature flag `e2e-test-hooks`. The e2e workspace builds with the feature on; production binaries do not include the endpoint at all.
- **Backwards compatibility: synchronous deploy.** The web app pulls the latest bundle on page load, so an active page is always running fresh code that knows how to pong. The fallback (pong missing → engine times out → defaults to push-allowed) covers the brief window between engine restart and the next page load.
