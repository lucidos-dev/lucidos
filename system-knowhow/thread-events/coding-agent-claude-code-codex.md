## Coding agent (Claude Code / Codex) (continued)

| Event | When it fires | Volume | Persisted | Triggerable |
|---|---|---|---|---|
| `MessageHeld` | On a coding-agent thread, an agent-sent message waits for a human reply before delivery. Carries `text`, optional `user_image_hashes`, `mode` and `origin`. It leaves the question and thread status unchanged. | per-action | yes | yes |
| `HeldMessageReleased` | On a coding-agent thread, a held message is released just before its `MessageReceived`. Carries `held_message_id`, referencing `MessageHeld`, so release happens at most once. | per-action | yes | yes |
| `CodingAgentUserMessageSent` | A user message was relayed into the agent's input stream. | one-per-turn | yes | yes |
| `CodingAgentPromptSent` | A prompt was forwarded into a live coding-agent session: an engine-synthesized one (orphan recovery, hardening retrigger, merge-conflict explainer, post-question continuation), or a user follow-up with the user's text and no origin. `input_event_id` names the event that carried the input, absent for an engine prompt with no starter event. A redelivered follow-up (ADR 0506) writes a second one for the same message. Carries `origin: Option<MessageOrigin>`; an automated prompt (hardening retrigger, merge conflict) always carries an engine origin with its reason. Audit-only, not rendered in chat. | per-action | yes | yes (use condition) |
| `CodingAgentInputRead` | The coding agent read an input the engine forwarded. `verbatim: true` marks the read of a slash command forwarded exactly as typed. Carries `input_event_id` (the `MessageReceived` it read, the `ChildThreadCompleted` of a child wake, or the `CodingAgentPromptSent` of an engine prompt with no starter event). Only the agent's own report is a read. Rows written before 2026-10-12 can carry `assumed: true`, a read a since-removed timer settled with no report. Carries `started_turn: true` (omitted when false) when the read opened a new turn, such as a queued message after a Stop; that read sets the thread running again. See [coding-agent-events](../coding-agent-events.md). | per-action | yes | yes |
| `CodingAgentInputDiscarded` | Older threads only: an effort restart interrupted a Claude Code turn before the agent read the input that opened it, so the agent never will. Nothing emits it now (ADR 0542). Carries `input_event_id`, as on `CodingAgentInputRead`. A message, a child's report or an engine prompt stays owed until a `CodingAgentInputRead` names it, and the next session to start delivers it. A continuation or a cache keep-alive is never owed. Not rendered. See [coding-agent-events](../coding-agent-events.md). | per-action | yes | yes |
| `ChildReportTaken` | A coding agent took a child's report mid-turn through its own `lucidos` call (`lucidos threads child-reports`, or a `lucidos background-task wait` that returned early). The engine withdrew the report's queued copy first, so the agent reads it once. Carries `input_event_id`, the `ChildThreadCompleted` card. It follows the card, so a restart does not wake the parent for that card again. Not rendered. See [coding-agent-events](../coding-agent-events.md). | per-action | yes | yes |
| `CodingAgentTextStreamed` | One chunk of the coding agent's assistant text. Join a turn's chunks with no separator: each new text block already starts a new paragraph. A chunk never holds whitespace alone: a paragraph break leads the next chunk instead. Older rows can still hold a bare `"\n\n"`, or two blocks with no break between them. A chunk a Claude Code sub-agent wrote carries `parent_tool_use_id` and is the sub-agent's narration, not the reply. A chunk flagged `progress_note: true` is a progress note: the provider's short summary of longer text the agent wrote before a tool call. The user saw only the summary. | high-volume-streaming | yes | **no (blocked)** |
| `CodingAgentThoughtStreamed` | One chunk of the coding agent's streamed reasoning (CC's `thinking_delta`; Codex's `item/reasoning/*Delta` or `reasoning` item). Coalesced before persistence. Rendered as the live "Thinking" step's content. | high-volume-streaming | yes | **no (blocked)** |
| `CodingAgentToolCalled` | One coding-agent tool invocation. Carries `name`, `args`, optional `description`, `tool_use_id`. A call a Claude Code sub-agent made also carries `parent_tool_use_id`, the id of the `Agent` call that spawned it. A Claude Code call carries `api_call_id`, shared by every tool call of one API call and by its `ContextCaptured`. | per-action | yes | yes (use condition) |
| `CodingAgentToolResult` | The result returned to the coding agent for a prior `CodingAgentToolCalled`. Same `tool_use_id`, `name` and `parent_tool_use_id`. `result` holds the whole output (rows before full storage kept 200 chars). | per-action | yes | yes (use condition) |
| `CodingAgentIdled` | **The coding-agent turn-boundary marker.** Emitted at the end of every coding-agent turn whose Result was not an engine-shutdown abort. Carries `has_changes`, `is_external_repo`, `requires_restart`, `cc_session_id`, `coding_agent`, optional `reason`, optional `worktree_path`, optional `worktree_head_sha`, and `bg_bash_pending`. That last is a history flag: true when the turn idled with a chat-agent `run_bash_background` task running. It **no longer gates proposal or drives any UI**; harden-at-apply covers correctness. Optional `turn_end` records how the agent ended the turn: `status` (`completed`, `interrupted`, `failed` or `synthesized`), `final_answer`, `agent_messages`, `steered_inputs` and `last_item`. Codex fills every field, its exec driver `status` only, and Claude Code none. Read it to tell why a turn ended early. | one-per-turn | yes | yes |
| `SessionHandedOff` | The current session handed off: the thread's next session is its *successor session*, which starts fresh once this session's turn ends. Carries `opening` (`narrative` or `brief`), `message` (the opening the successor session reads first, ending on a "Still running" list of the tasks, event waits and children still at work), optional `checkpoint` and `progress`, optional `plan_path` from the latest session's repository-and-branch plan marker (absent when there is no provable binding), and the implementer it runs on: `coding_agent`, optional `coding_agent_model` and `reasoning_effort`. `cause` says why (see the generated values above) and `starts` says when. A `context-ceiling` handoff carries `crossing`, the session's `ContextCeilingReached` fields (`context_tokens`, `ceiling`, optional `window`), and starts `after-this-turn` when an agent narrative follows re-entry that interrupted running work. After a natural turn end, or with an engine brief, it starts `on-next-input`: the next input starts it, and boot never does. A typed card request starts `now`. A *ceiling re-entry* that ends without a handoff gets a brief one from the engine. Optional `request` holds what the user typed at the *Successor card* (`message`) and who typed it (`by`). The successor session then starts on it as that user's own `MessageReceived`, and the opening goes ahead of it in the agent's first prompt. Pending until the successor session's `SessionStarted`, whose `continuity` is `handoff`. A user's Stop withdraws it, as does an Apply, Discard or Archive that stops a turn. So does a failed turn that began after it, since the successor session never started, and a person's `SessionHandoffWithdrawn`. A recovery or conflict-resolution session leaves it pending. Meanwhile the thread offers no second handoff, owes its parent no report or wake decision, and gets no cache keep-alive. Creates no thread and leaves the branch alone. An eligible automatic handoff sets or keeps `running` across old-session bookkeeping until its successor starts. The turn end that follows proposes nothing and announces nothing: it withdraws a pending change, so no Apply shows before the successor session. A queued change stays put, and so does a set-aside one unless the turn committed past it. | rare | yes | yes |
| `SuccessorThreadSpawned` | Legacy: this thread handed off to a *legacy successor thread*, before handoffs started a *successor session* in the same thread. No new row records it. Lands on the OLD thread. Carries `successor_thread_id` and `base_sha`, this thread's last commit, where the successor's branch starts. `starts_build_chain: true` marks a plan card's handoff, whose successor is a `no-wake` child of this thread, which stays open (a *build chain*). `handoff_consent` (`owner`, `owner-approval` or `carried`) names the authority that let a successor placed under a parent start: its *handoff consent*, which that successor inherits for its own automatic handoffs. Absent for a top-level successor, a build chain member, a machine caller, and any spawn the owner did not authorize. Projects `thread_summaries.successor_thread_id` here and `successor_of` on the successor, and clears this thread's pending parent report: the successor reports in its place. The thread's work then waits as `carried_by_successor`. A thread hands off once: a second one is refused and never recorded. | lifecycle (rare) | yes | yes |
| `HandoffCheckpointReached` | The agent ran a *handoff checkpoint* a flow names, through `lucidos successor offer --at <name>`. Carries `name`, optional `progress` (`{done, total}`), and what the *handoff estimate* read: `context_tokens`, `model`, `reasoning_effort`. `offered: true` marks a `--ask` run, and `pays` is the verdict (absent when the engine could not make a reading). `default_floor: true` marks a `--default-floor` run. Its `floor_rung` and `risk_rung` (`{model, effort}`) are the rungs it named, each absent when none. A later run of the same checkpoint reads it as history: the main-session calls from here to the first turn end with nothing pending (no open question, event wait or unread message), per unit left. Changes no status. | lifecycle (rare) | yes | yes |
| `SuccessorOfferDeclined` | The user chose *Stay here* on the *Successor card*. Carries `input_tokens`, the context size at that moment. The card stays hidden until the thread holds 100k tokens more, and a compaction below that size lifts the hold. Changes no status. | rare | yes | yes |
| `ContextCeilingSet` | The thread's *context ceiling* was set (ADR 0629). Carries `ceiling` (`off`, a size such as `300k`, or a window share such as `30%`) and `source`: `thread` for one set on the thread itself, by a person or an agent, or `trigger` for one copied from the firing trigger at creation. The newest one wins. A thread with none takes the ceiling its parent held when it spawned the thread, else the workspace preference `coding_agent_context_ceiling`. The actor rides the meta: only a person raises a ceiling or turns it off. Changes no status. | rare | yes | yes |
| `ContextCeilingReached` | A live main-session capture crossed the *context ceiling* (ADR 0701). Recorded once per session, independently of *ceiling re-entry* delivery at the next safe boundary. A session whose first capture already exceeds its ceiling is exempt; growth past it during the opening turn fires. Restored and child-agent usage never records a crossing. Carries `context_tokens` (the size at the crossing), `ceiling` (the effective ceiling in tokens, after the window cap and the handoff floor) and optional `window`. Changes no status. | lifecycle (rare) | yes | yes |
| `SessionHandoffWithdrawn` | A person chose *Return to the old session* on the card above the composer, while a `context-ceiling` handoff waited for the next input (ADR 0629). The handoff no longer stands, so the thread's next input resumes the old session. A `ContextCeilingSet` just before it raises the thread's ceiling to the session's size plus 100k, so the session is no longer past it. A `SuccessorOfferDeclined` at the session's size follows it, so the Successor card holds back too. Carries no fields. An agent cannot record it. Changes no status. | rare | yes | yes |
| `SuccessorRequested` | The user chose *Continue with context* on the *Successor card* while the prompt cache was warm. Carries the first request they typed for the successor and the implementer they picked. The agent writes the *handoff narrative*, and its handoff reads this row. Pending until the thread idles. Changes no status. | rare | yes | yes |
| `CodingAgentCompacted` | The coding agent compacted its own context mid-session: Claude Code's `compact_boundary`. Carries `trigger` (`"auto"` or `"manual"`), optional `pre_tokens` and `post_tokens`, and `coding_agent`. Renders as a finished step, so the context counter's drop has a cause on screen. | lifecycle (rare) | yes | yes |
| `CodingAgentModelSubstituted` | Claude Code ran another model than the pinned one the turn asked for, because the account may not run it. Read off Claude Code's Init line, once per process. Carries `requested`, `served` (both model ids) and `coding_agent`. Renders as a finished step. The thread's current model is `served` from then on. The refused model stays on the ladder and in the picker, but no floor rung, risk rung or agent pick uses it until it serves again or the owner takes it off the ladder. A version-free alias such as `default` or `opus` never records one. Changes no status. | lifecycle (rare) | yes | yes |
| `CodingAgentBillingObserved` | Passive billing evidence from the serving CLI. Carries `coding_agent`, `launch_id`, typed `attribution` and `billing_mode`. See [billing evidence](../coding-agent-events/billing-evidence.md#billing-evidence). | per-observation | yes | yes |
| `CodingAgentSettingsChanged` | User changed model or reasoning effort mid-session. Also emitted once at backend init with `cc_session_id`, `claude_config_dir` (where the session's transcripts live) and `claude_config_dir_explicit` (whether `CLAUDE_CONFIG_DIR` was set). That makes them durable before the first `CodingAgentIdled`. The session id lets a mid-turn engine restart still resume. The config-dir fields let the resume replay the same Claude Code profile, even if the user toggled the env var meanwhile. | lifecycle (rare) | yes | yes |
| `CodingAgentPermissionRequest` | A coding agent asked to confirm a tool call, on one of two raise paths. Claude Code's MCP permission-prompt subprocess fires for a path outside the session's working directories, or `.git/` inside the worktree. Those directories are the worktree, the workspace's `data/` tree, `/tmp` and `$TMPDIR`; an in-worktree write, including under `.claude/`, is auto-allowed before any card. Under the `auto` permission mode CC's classifier decides instead. The Codex app-server approval bridge fires for a `command_execution` the command guard does not settle, or an out-of-worktree `file_change`. Inside the agent sandbox every command asks (`approvalPolicy: untrusted`); with it off, only a sandbox-escaping one (`on-request`). The exec escape-hatch protocol emits none. | per-action | yes | yes |
| `CodingAgentPermissionResolved` | The above request was answered, or the engine auto-resolved it. Auto cases: recovery (orphaned after restart); supersession (`allowed: false`, `reason: "Superseded by a new message"` when the user types instead of clicking); a **session-ended clear**. The clear fires when the turn idled with the card still open, e.g. a parallel subagent's card outliving the main turn. Its `reason` starts `"Coding agent session ended before answering"`. Carries `allowed`, optional `reason`, optional `persist_scope` (`narrow` / `broad` / `session`). Flips the thread back to `running` **only from `waiting_for_user_answer`**. A resolution on an idle or terminal thread (a stale click, or the session-ended clear) leaves the status unchanged, so a finished thread never becomes a dead `running`. | per-action | yes | yes |
| `MissingHardeningDetected` | A coding-agent session ended without running `/harden`, so the engine auto-spawned a recovery hardening session. Not a session terminator: the thread stays active until hardening finishes. | lifecycle (rare) | yes | yes |
| `ContinuationRequested` | An interrupted coding-agent turn needs to resume without a new user message. The spawn dispatcher picks it up; the event id is the spawn idempotency key. Delivery is guaranteed two ways. The bus sends each committed request to the dispatcher on a directed channel, not the broadcast, so a lag cannot drop it. And every engine start re-dispatches any unactuated request: no later lifecycle or terminal event, on a thread still `running`. So a request never strands a thread as a running zombie. `reason: String` is one of: `"user_clicked_continue"` (Continue after an engine restart); `"answered_after_idle"` (an `AskUserQuestion` answered after the subprocess was torn down at idle); `"auto_recovery_after_hang"` (a hung-subprocess watchdog found the agent silent past its inactivity limit); `"auto_resume_after_switch"` (recovery resumes an in-flight thread after a user's *Switch to new version*); `"harden_requested"` (the user pressed **Harden** on the *Not ready* strip, or allowed the harden step of a paused thread, and the thread resumes to run `/harden`); `"plan_requested"`, `"build_requested"`, `"handoff_requested"` and `"reports_requested"` (the owner allowed that step on a thread whose automation is paused); `"auto_resume_after_api_error"`. That last one fires when the agent ended a turn on a transient upstream failure it reported itself (`API Error: …`, e.g. a connection closed mid-response). The engine then resumes instead of leaving the thread dead behind the `ResponseFailed`. It is the only BOUNDED reason: at most 3 in a row since the thread's last `MessageReceived` or `ResponseGenerated`, so a broken upstream shows a red dot instead of looping. It is skipped during engine shutdown (post-restart recovery owns those threads) and on a conflict-resolution session (an API drop mid-merge aborts the merge and leaves the change pending). Two watchdogs produce `auto_recovery_after_hang`. The in-loop one sits in `run_session`'s `select!` (10 min, the fast first line). An external scanner task (12 min, ticks every 30 s) catches a `select!` wedged in an event-handler await. They share a gate, and the 2-min grace lets the in-loop one fire first. The gate skips while a tool is in flight (a long `Bash`, an unanswered `AskUserQuestion`), up to a 45-min hung-tool ceiling. Past it, a tool that never returns (a hung sub-agent) fires anyway, after re-confirming the thread is still `running`, so a pending user answer is never killed. A thread may have an in-flight *conflict resolution*: a pending change whose latest merge-lifecycle event is an unpaired `MergeConflictDetected`. Then a **recovery-shaped** continuation (`user_clicked_continue` / `auto_recovery_after_hang` / `auto_resume_after_switch`) re-attaches the merge duty. Never `answered_after_idle`, a different interaction that must not silently land a change. The resumed session runs in the merge worktree with the change bound, so its completion finishes the apply (`ChangeApplied`) or aborts for real. A stray-killed merge session's cleanup skips the failure events, so the pairing stays open for the hand-off. A duty the continuation cannot carry (merge worktree gone, resume failed first) closes loudly with the deferred `MergeResolutionCleared` + `ChangeApplyFailed` pair. Past name `ContinueSignal` is a serde alias for old DB rows. | lifecycle | yes | yes |
| `SideQuestionAsked` | The user asked a *side question* in a Claude Code, Codex or Lucidos Agent thread. Carries `side_question_id: Uuid` (named by the client), `question`, any attached `image_hashes`, and `actor` from `EventMeta`. Records a card beside the thread, never a turn: it moves no status, recency, count or section. **No agent sees it**: `events(action="query")`, triggers, event waits and every context builder leave it out (ADR 0320). | per-action | yes | **no (hidden)** |
