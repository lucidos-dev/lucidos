## Question / permission machinery

An **Always deny** answer sets `standing_deny` on the command or coding-agent
permission resolution. The optional field holds the exact rule stored for the
workspace. An ordinary Deny leaves it absent.

When a coding-agent permission card falls back to asking because the standing
denies are unavailable, its request marks the reason in `grant_offer.withheld`.
See the permission event payloads in [Coding-agent events](../coding-agent-events.md).

Not prefixed `CodingAgent*`, because any agent can use this machinery to ask the user a structured question. Every blocking request below is triggerable, so a trigger can push the user when an agent needs an answer. `triggers.md` has the deep-link pattern (`tap: { kind: 'navigate', to: { target: 'thread', id, event_id } }`).

| Event | When it fires | Volume | Persisted | Triggerable |
|---|---|---|---|---|
| `UserQuestionAsked` | An interactive question was raised by Claude Code's `AskUserQuestion` tool, Codex's `ask_user_question` MCP tool (one question per call), or the chat agent's `ask_user_question` tool. `meta.channel` records the lane: `claude_code` (the coding-agent channel, both backends) or `chat`. Resume goes through `POST /api/v1/threads/{thread_id}/answer-question`. The engine branches on the channel: coding agent gets a resume marker plus a `ContinuationRequested` respawn if needed; chat wakes the in-process tool. Carries `tool_use_id`, `cc_session_id` (empty for chat-channel and Codex rows), `question`, `options: Vec<QuestionOption>`, optional `worktree_path`, `multi_select: bool`, and on a *permission request* the engine raised `permission_request: { action, breadth?, prepared?, choices, lines? }`. Historical grant-file review rows may carry `lines`. `prepared` is the request id when an agent prepared it with `lucidos ask-permission`. `choices` maps each option id to `{ kind: "grant", lifetime, holder, breadth? }` (`breadth` `any` covers every target of the action, absent covers the asked one), `{ kind: "unpause" }` (legacy: the retired step card's option, which does nothing now), `{ kind: "revoke" }` (historical grant-file review option) or `{ kind: "refuse" }`. Older rows can carry a legacy step card, with `action` `harden`, `set-plan-marker`, `build-approved-plan`, `hand-off` or `read-waiting-reports`. Lucidos retires any still open at boot. A *batch* is one with `action` `run-batch` and `batch: { items, digest }`: each item is `{ kind: "card_answer", thread_id, tool_use_id, option_id, option_label, card_digest, plan? }` (a question or permission request card), `{ kind: "permission_card_answer", thread_id, lane, request_id, pick, option_label }` (a tool-permission card, `lane` `command`, `coding_agent` or `mcp`, `pick` `once`, `session` or `deny`), `{ kind: "trigger_grant", trigger_id, definition_digest, side_effects, coding_agents }`, which widens one trigger's grants while its *definition digest* is unchanged, or `{ kind: "workspace_classification", workspaces, origin, evidence }`, which records the *workspace origin* (`agent`, `demo`, `eval`, `e2e` or `user`) of workspaces still `unknown`. `plan` binds an approving pick to `{ repo_root, branch_name, plan_path, marked_at, digest }`, the committed plan text. A row from before ADR 0688 may carry the legacy `owner_approval` instead. | one-per-turn (of the `Asked` kind) | yes | yes |
| `UserQuestionQueued` | A *queued card*: a `UserQuestionAsked` that arrived while the thread already had an open card. The engine records it under this type, so no client, push or voice path shows it. When the open card closes, the engine posts it as a `UserQuestionAsked` with the same `tool_use_id`. Same fields as `UserQuestionAsked`. Only the engine may answer it, with `Canceled` or `Superseded`. | per-action | yes | yes |
| `UserQuestionAnswered` | The user (or the engine, on the orphan-recovery path) supplied an answer. Pairs 1:1 with its `UserQuestionAsked` via `tool_use_id`. Carries `answer: AnswerKind` (`Selected` / `FreeText` / `MultiSelected` / `Canceled` / `Superseded`) and copies `meta.channel` from the `Asked`. `quiet: true` marks a pick of only *quiet options*: the turn ends, nothing wakes the agent, and the thread settles to `idle`. A typed `FreeText` or `MultiSelected` may carry the user's `image_hashes`. The last two kinds resolve the question without an answer. `Canceled` is a dismissal or teardown stamp. `Superseded` is a follow-up that could not be the answer and replaced the question (coding-agent lane only). | one-per-turn | yes | yes |
| `OwnerApprovalRequested` | Legacy: a coding agent asked for the retired single-use card (ADR 0387). Nothing emits it now; `PermissionRequestPrepared` replaced it (ADR 0688). Carries `request_id`, `approval: { verb, target_thread_id?, target_workspace_id?, snapshot_handle? }` and `question`. | per-action | yes | yes |
| `OwnerApprovalSpent` | Legacy: a thread used the retired single-use card on the act it names. Nothing emits it now; `PermissionSpent` replaced it (ADR 0688). Carries `tool_use_id`, `verb` and optional `target_thread_id`, `target_workspace_id` and `snapshot_handle`. | per-action | yes | yes |
| `MachineMadeWorkspaceChanged` | An agent acted on a *machine-made workspace* with no card: the workspace is the agent's (ADR 0676). A stop, start, rename or autostart change comes from `lucidos workspaces`, and a snapshot restore from `lucidos snapshot restore`. Recorded just before the act, which may still be refused. Carries `verb`, `workspace_id` and a `reason`. A restore also carries `snapshot_handle`, and its `reason` is fixed text, since the agent's own goes to the target. Under the target's `allow` policy no restore event is recorded here. | per-action | yes | yes |
| `CommandPermissionRequested` | The **command guard** (ADR 0002) paused a chat bash/python tool call, or an MCP server setup, in the `IrreversibleDanger` lane to ask the user. That lane means a likely real-world side-effect (mutating HTTP, sending mail, a cloud-CLI mutation) or destruction outside the workspace. A static fast-path settles the obvious safe or catastrophic cases; the LLM **judge** (Phase 3) decides the ambiguous middle. The chat mirror of `CodingAgentPermissionRequest`: same `PermissionCard`, but the agent loop blocks in-process (no MCP subprocess). Carries `request_id`, `tool_use_id`, `tool_name` (a bash/python tool; `run_bash` for an MCP server setup, whose `command` is the line the server would run and whose `summary` says it runs again each time the server starts), `command` (the inspected text), `summary` (the card's one-line risk), for bash an optional `grant_head` (the head a grant stores, after a leading `cd` into the workspace root drops), and `grant_offer`: the pattern each grant button stores, keeping only those that cover the command. A secret read offers none and carries `withheld: "secret-read"`. A conservative workspace floor match offers only Allow once and Deny and carries `withheld: "unproven-workspace-destruction"`. An optional `decision_trace` names the deciding layer, the static evidence and the judge's distribution, with no command text. Chat-channel only; flips the thread to `waiting_for_user_answer`. | per-action | yes | yes |
| `CommandPermissionResolved` | The above was answered (Allow once / Deny / Allow for this thread / Always allow) or auto-resolved. Auto reasons: `"Superseded by a new message"` when the user types instead of clicking, or an orphan/cancel reason on restart or Stop. Carries `request_id`, `allowed`, optional `reason`, optional `persist_scope` (`narrow` / `broad` / `session`). Flips the thread back to `running` **only from `waiting_for_user_answer`**; a stale resolution on an idle or terminal thread leaves the status unchanged. | per-action | yes | yes |
| `McpPermissionRequested` | The Lucidos Agent (chat) paused an **MCP server tool** call to ask the user: the MCP mirror of `CommandPermissionRequested`. Same `PermissionCard`; the agent loop blocks in-process. Carries `request_id`, `tool_use_id`, `server_id` (MCP registry key), `server_name` (human label), `tool_name` (bare MCP tool), `arguments_summary`. Chat-channel only; flips the thread to `waiting_for_user_answer`. **Never raised in a trigger thread**, which has nobody to answer: there a call runs silently when the trigger lists the server in `mcp_servers` or the server has `auto_approve` set, and is otherwise refused with a notification. A chat call to an `auto_approve` server also skips it. | per-action (only when the call isn't pre-authorized) | yes | yes |
| `McpPermissionResolved` | The above was answered (Allow once / Deny / Allow for this thread / Always allow this tool / Always allow this server) or auto-resolved (superseded / orphan / cancel). Carries `request_id`, `allowed`, optional `reason`, optional `persist_scope`. Scopes: `narrow` → `Mcp(server:tool)` and `broad` → `Mcp(server:*)`, both standing tool grants for the workspace; `session` → a tool grant held by the thread, which survives a restart. Flips the thread back to `running` **only from `waiting_for_user_answer`**; a stale resolution on an idle or terminal thread leaves the status unchanged. | per-action | yes | yes |
| `ThreadMcpServerEnabled` | This thread switched an *MCP server* on for itself, so its requests now carry that server's tools (ADR 0430). Carries `server_id` and `by`: `agent` (the `mcp` tool's `enable` or `start`), `user` (`POST /api/v1/threads/{id}/mcp-servers/{server_id}/enable`), `trigger` (the firing trigger lists it in `mcp_servers`), or `parent` (a child copied its parent's set at spawn). Emitted only when the server was not already enabled here. Projected into `thread_summaries.enabled_mcp_servers`. Does not change thread status. | per-action | yes | yes |
| `ThreadMcpServerDisabled` | This thread switched an MCP server off for itself (the `mcp` tool's `disable`, or the matching `/disable` route). The process keeps running for other threads. Carries `server_id` and `by`. A stop or a remove switches the server off in every thread through the system events `McpServerStopped` and `McpServerRemoved` instead, so it emits none of these. | per-action | yes | yes |
| `CommandCheckpointed` | The **command guard** (ADR 0002, Phase 4) bracketed a `ReversibleDanger` command (in-workspace deletion or overwrite) with two snapshots of git-visible content. A **pre** image goes on a safety ref before it runs, and a **post** image after. The diff tells the engine which files the command created, overwrote and deleted, so the card offers Undo and a view of the change. Emitted **after** the command returns, and only when the images differ. A command that changed nothing git-visible (often a gitignored target) emits nothing, since Undo would do nothing. A failed snapshot also emits nothing and lets the command run unguarded. Carries `checkpoint_id` (the ref key), `command` (the inspected text), `summary` (the card line), and the counts `restores` / `removes`. Those are what Undo would put back and what it would delete as command-created; both 0 on older events. Does not change thread status. | per-action (only when the guard is on AND a command hits the reversible lane AND it changed something git-visible) | yes | yes |
| `CommandCheckpointReverted` | The user clicked Undo on a `CommandCheckpointed` card (or the engine resolved it). Files the command created were removed, and files it deleted or overwrote came back from the pre image. A path is touched only if it still holds what the command left, so a later edit survives. A checkpoint with no post image restores the whole pre image instead. Both refs are kept, so the card's diff stays viewable. Carries `checkpoint_id`; stamped with the original turn's `request_event_id` so it groups with its checkpoint (the card renders reverted). | per-action | yes | yes |
| `WidgetShown` | **No longer emitted** (ADR 0466): a widget shows in a thread by a *widget embed* in a reply. An old row still draws its *inline widget* at its turn. Carries `app_id`, plus the instance's optional `params` object and `label` (ADR 0415). A row with no `params` is the instance with none. | per-action | yes | yes |
| `WidgetPinned` | **No longer emitted** (ADR 0621): pinning a *widget instance* to a thread is gone, and a widget the user wants in view goes on a *dashboard* through the `DashboardTileAdded` system event below. Home's old rows still read, as the seed of both dashboards (ADR 0496), and draw nothing in a turn. Carries `app_id`, the optional `params` and `label`, and an optional `shown_event_id`. Legacy alias: `WidgetRestored`. | per-action | yes | yes |
| `WidgetUnpinned` | **No longer emitted** (ADR 0621). Home's old rows still read, and take an old pin out of the dashboards' seed. They draw nothing in a turn. Carries `app_id` and the optional `params` and `label`. Legacy alias: `WidgetHidden`. | per-action | yes | yes |
| `InlineWidgetSized` | The user picked a size on a widget card's pill, or `widgets(action="size")` set one when the user named it. Every card of that *widget instance* in this thread draws at the newest size, and a card with none starts at the widget's default size. Carries `app_id`, the optional `params`, and `size`: one the widget declares. No file or commit changes. | per-action | yes | yes |
| `HomeBoardArranged` | **No longer emitted** (ADR 0496): a dashboard arranges through the `DashboardArranged` system event below. An old row, on the home thread only, still reads. It arranged the old Home board for one layout, `phone` or `desktop`, before each had its own tiles. Carries `layout` and `tiles`, in order: each `app_id`, optional `params`, `size` and optional `hidden`. The engine folds these rows with Home's old pins into each *dashboard*'s starting tiles, minus the hidden ones (ADR 0432). | per-action | yes | yes |
| `McpConsentRequested` | Legacy audit-log entry (`tool`, `args`) from the pre-card MCP consent flow. No longer emitted: chat MCP consent uses `McpPermissionRequested` / `McpPermissionResolved`. Kept for replay of historical rows. | lifecycle | yes | yes |
